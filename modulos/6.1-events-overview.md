# 6.1 — Events y Observers: Arquitectura y Flujo

> **Objetivo**: Entender cómo funciona el sistema de eventos de Magento, cuándo usarlo en lugar de Plugins y cómo se estructura el flujo completo desde el dispatch hasta el observer.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [5.6 — Limitaciones de Plugins](5.6-plugin-limitations.md)

---

## Qué son los Events y Observers

Magento implementa el patrón **Observer/Event** — cuando algo importante sucede en el sistema, se "dispara" un evento. Los Observers son clases que escuchan esos eventos y reaccionan.

```
Algo sucede en el sistema
    ↓
$eventManager->dispatch('sales_order_place_after', ['order' => $order])
    ↓
Magento notifica a todos los Observers registrados para ese evento
    ↓
Cada Observer ejecuta su lógica
```

Es completamente desacoplado — el código que dispara el evento no sabe nada de quién lo escucha.

---

## Cuándo usar Observer vs Plugin

| | Observer | Plugin |
|---|---|---|
| **Propósito** | Reaccionar a algo que ya sucedió | Modificar cómo funciona un método |
| **Puede modificar resultado** | No (generalmente) | Sí (after/around plugin) |
| **Acoplamiento** | Bajo — desacoplado por diseño | Medio — ligado a una clase/método |
| **Cuándo** | Eventos de negocio (pedido creado, producto guardado) | Interceptar lógica de un método |
| **Múltiples listeners** | Sí, todos se ejecutan | Sí, encadenados por sortOrder |

**Regla práctica**:
- ¿Necesitas **reaccionar** a algo? → Observer
- ¿Necesitas **modificar** cómo funciona algo? → Plugin

## Los tres componentes

### 1. El Event Manager — quien dispara

```php
use Magento\Framework\Event\ManagerInterface;

class OrderService
{
    public function __construct(
        private readonly ManagerInterface $eventManager
    ) {}

    public function placeOrder(array $orderData): Order
    {
        $order = $this->createOrder($orderData);

        // Disparar evento con datos relevantes
        $this->eventManager->dispatch('mimodulo_order_placed', [
            'order'      => $order,
            'order_data' => $orderData,
        ]);

        return $order;
    }
}
```

### 2. El events.xml — el registro

```xml
<!-- app/code/MiVendor/Blog/etc/events.xml  (global) -->
<!-- o etc/frontend/events.xml  (solo frontend) -->
<!-- o etc/adminhtml/events.xml (solo admin) -->

<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:Event/etc/events.xsd">

    <event name="mimodulo_order_placed">
        <observer name="mivendor_blog_send_confirmation"
                  instance="MiVendor\Blog\Observer\SendOrderConfirmation"/>
    </event>

    <event name="mimodulo_order_placed">
        <observer name="mivendor_blog_update_inventory"
                  instance="MiVendor\Blog\Observer\UpdateInventory"/>
    </event>

</config>
```

### 3. El Observer — quien reacciona

```php
namespace MiVendor\Blog\Observer;

use Magento\Framework\Event\ObserverInterface;
use Magento\Framework\Event\Observer;

class SendOrderConfirmation implements ObserverInterface
{
    public function __construct(
        private readonly \MiVendor\Blog\Service\EmailService $emailService
    ) {}

    public function execute(Observer $observer): void
    {
        // Obtener datos del evento
        $order = $observer->getEvent()->getOrder();

        // Tu lógica
        $this->emailService->sendConfirmation($order);
    }
}
```

## Flujo completo de ejecución

```
1. Código llama: $eventManager->dispatch('evento_nombre', $data)

2. EventManager busca en events.xml todos los observers del evento

3. Para cada observer registrado:
   a. Instancia la clase via DI
   b. Llama a execute(Observer $observer)
   c. El Observer accede a los datos via $observer->getEvent()->getData()

4. Todos los observers se ejecutan en el orden declarado en events.xml

5. El código que disparó el evento continúa — no espera respuesta de los observers
```

---

## Acceder a los datos del evento

```php
public function execute(Observer $observer): void
{
    $event = $observer->getEvent();

    // Acceder por nombre de clave
    $order    = $event->getOrder();          // getXxx() por nombre de clave
    $product  = $event->getProduct();
    $customer = $event->getCustomer();

    // Alternativa — acceso genérico
    $order = $event->getData('order');
    $all   = $event->getData();              // todo como array

    // El observer en sí también tiene acceso directo
    $order = $observer->getData('order');    // shortcut
}
```

Los métodos mágicos `get{Key}()` se generan automáticamente por `DataObject` — si pasas `['order' => $order]` en el dispatch, puedes acceder con `$event->getOrder()`.

## Áreas y events.xml

Al igual que `di.xml`, `events.xml` puede vivir en diferentes ubicaciones:

```
etc/events.xml           → aplica en TODAS las áreas
etc/frontend/events.xml  → solo en el área frontend
etc/adminhtml/events.xml → solo en el área adminhtml
etc/webapi_rest/events.xml → solo en la API REST
```

Ejemplo — Observer que solo se ejecuta en el frontend:

```xml
<!-- etc/frontend/events.xml -->
<event name="catalog_product_load_after">
    <observer name="mivendor_track_product_view"
              instance="MiVendor\Blog\Observer\TrackProductView"/>
</event>
```

---

## Deshabilitar un Observer de otro módulo

```xml
<!-- Tu events.xml puede deshabilitar observers externos -->
<event name="sales_order_place_after">
    <observer name="nombre_exacto_del_observer_externo" disabled="true"/>
</event>
```

## Resumen

```
Componentes:
  EventManager::dispatch('nombre', $data)  → dispara el evento
  etc/events.xml                           → registra observers
  Observer implements ObserverInterface    → reacciona al evento

Observer siempre implementa:
  public function execute(Observer $observer): void

Acceder a datos:
  $observer->getEvent()->getOrder()   → magic getter por nombre de clave
  $observer->getEvent()->getData('x') → acceso genérico

Áreas:
  etc/events.xml          → global
  etc/frontend/events.xml → solo frontend
  etc/adminhtml/events.xml → solo admin

Observer vs Plugin:
  Observer → reaccionar sin modificar resultado
  Plugin   → modificar comportamiento de un método
```

## Ejercicios

### Ejercicio 1 — Observer completo: enviar notificación al crear un post

Crea un Observer completo que se ejecute cuando se dispara el evento `mivendor_blog_post_created` y envíe una notificación por email al autor del post. El evento pasa `['post' => $post, 'author_email' => $email]`.

<details>
<summary>Ver solución</summary>

```xml
<!-- app/code/MiVendor/Blog/etc/events.xml -->
<?xml version="1.0"?>
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:Event/etc/events.xsd">
    <event name="mivendor_blog_post_created">
        <observer name="mivendor_blog_notify_author_on_publish"
                  instance="MiVendor\Blog\Observer\NotifyAuthorOnPublish"/>
    </event>
</config>
```

```php
<?php
// app/code/MiVendor/Blog/Observer/NotifyAuthorOnPublish.php
namespace MiVendor\Blog\Observer;

use Magento\Framework\Event\Observer;
use Magento\Framework\Event\ObserverInterface;
use Magento\Framework\Mail\Template\TransportBuilder;
use Psr\Log\LoggerInterface;

class NotifyAuthorOnPublish implements ObserverInterface
{
    public function __construct(
        private readonly TransportBuilder $transportBuilder,
        private readonly LoggerInterface  $logger,
    ) {}

    public function execute(Observer $observer): void
    {
        try {
            // Obtener datos del evento
            $event       = $observer->getEvent();
            $post        = $event->getPost();
            $authorEmail = $event->getAuthorEmail();

            if (empty($authorEmail)) {
                return;
            }

            // Construir y enviar el email
            $transport = $this->transportBuilder
                ->setTemplateIdentifier('blog_post_created_email')
                ->setTemplateVars([
                    'post_title' => $post->getTitle(),
                    'post_id'    => $post->getId(),
                ])
                ->setTemplateOptions(['area' => 'frontend', 'store' => 1])
                ->setFromByScope('general')
                ->addTo($authorEmail)
                ->getTransport();

            $transport->sendMessage();

            $this->logger->info('Notificación enviada al autor', [
                'post_id' => $post->getId(),
                'email'   => $authorEmail,
            ]);

        } catch (\Exception $e) {
            // Los Observers NO deben lanzar excepciones que interrumpan el flujo principal
            $this->logger->error('Error al notificar autor', [
                'error' => $e->getMessage(),
            ]);
        }
    }
}
```

```bash
php bin/magento cache:flush

# Verificar el Observer registrado:
grep -r "mivendor_blog_post_created" app/code/MiVendor/Blog/etc/ --include="events.xml"
```

**Puntos clave**:
- El Observer nunca lanza excepciones — captura y loguea para no interrumpir el flujo
- Accede a los datos con `$event->getPost()` (magic getter por nombre de clave)
- `execute()` devuelve `void` — no puede devolver valores al código que disparó el evento

</details>

### Ejercicio 2 — Observer vs Plugin: elegir la herramienta correcta

Para cada escenario, determina si debes usar Observer o Plugin y justifica la elección.

```
A. Cuando se guarda un producto, actualizar el índice de búsqueda.

B. Cuando alguien llama a ProductRepository::getById(), agregar
   un campo "stock_label" al resultado.

C. Cuando se completa un pedido, enviar un email de confirmación.

D. Cuando se llama a Customer::authenticate(), loguear el intento
   de login con IP y timestamp.

E. Cuando se elimina un cliente, eliminar también sus posts del blog.

F. Antes de que se guarde un producto, validar que el SKU no contiene
   caracteres especiales.
```

<details>
<summary>Ver solución</summary>

```
A. Actualizar índice al guardar producto → Observer
   Razón: Es una reacción a un evento ya ocurrido (producto guardado).
   Evento: catalog_product_save_after
   El reindexado no modifica el resultado del save().

B. Agregar campo al resultado de getById() → Plugin (after)
   Razón: Necesitas modificar el objeto retornado por el método.
   Un Observer no puede modificar el resultado de retorno.
   Usa: afterGetById en ProductRepositoryInterface.

C. Email de confirmación al completar pedido → Observer
   Razón: Reacción a un evento de negocio, sin modificar el flujo.
   Evento: sales_order_place_after o checkout_submit_all_after.

D. Loguear intentos de login → Plugin (before o after)
   Razón: Aunque es "reacción", necesitas acceso a los argumentos
   del método (username, password attempt). Un Observer puede no
   tener estos datos. Usa: beforeAuthenticate o afterAuthenticate.
   Alternativa válida: Observer de customer_login o customer_login_failed.

E. Eliminar posts al eliminar cliente → Observer
   Razón: Reacción desacoplada a la eliminación. El módulo de clientes
   no debería saber nada de tu módulo de blog.
   Evento: customer_delete_after o customer_delete_commit_after.

F. Validar SKU antes de guardar → Plugin (before)
   Razón: Necesitas poder lanzar una excepción que DETENGA el guardado.
   Un Observer se ejecuta después de que el flujo ya inició.
   Usa: beforeSave en ProductRepositoryInterface y lanza
   \Magento\Framework\Validation\ValidationException si falla.
```

</details>
