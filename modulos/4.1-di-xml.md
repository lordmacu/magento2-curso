# 4.1 — DI en Magento: di.xml y el ObjectManager

> **Objetivo**: Entender cómo funciona el contenedor de inyección de dependencias de Magento — el sistema más poderoso y central del framework. Todo lo demás (plugins, preferences, observers) se construye sobre este fundamento.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [3.4 — File Structure del Módulo](3.4-module-file-structure.md)

---

## El DI de Magento vs Laravel

🔄 **Laravel**: El IoC container de Laravel es implícito — declaras el tipo en el constructor y Laravel lo resuelve automáticamente. La configuración extra va en Service Providers con `$app->bind()`.

Magento funciona igual en el fondo, pero **toda la configuración es explícita en XML**:

```php
// Laravel — el container resuelve automáticamente por tipo
public function __construct(ProductRepository $repo) {}

// Magento — igual, también resuelve por tipo automáticamente
public function __construct(
    private readonly ProductRepositoryInterface $productRepository
) {}
// Pero la implementación concreta de la interfaz se configura en di.xml
```

La diferencia clave: en Magento **puedes cambiar qué implementación se inyecta sin tocar el código** — solo modificando `di.xml`.

## El ObjectManager

El ObjectManager es el corazón del DI en Magento. Es el contenedor que sabe cómo construir cualquier clase.

```php
// Así funciona internamente (NUNCA lo uses directamente en producción):
$objectManager = \Magento\Framework\App\ObjectManager::getInstance();
$producto = $objectManager->get(\Magento\Catalog\Model\Product::class);
$nuevo    = $objectManager->create(\Magento\Catalog\Model\Product::class);
```

- `get()` — devuelve un **singleton** (misma instancia siempre)
- `create()` — devuelve una **nueva instancia** cada vez

⚠️ **Nunca uses el ObjectManager directamente en tu código**. Siempre recibe las dependencias vía constructor. La única excepción válida es en `registration.php` y scripts de instalación.

## Constructor Injection — la forma correcta

```php
namespace MiVendor\Blog\Model;

use Magento\Catalog\Api\ProductRepositoryInterface;
use Magento\Customer\Api\CustomerRepositoryInterface;
use Psr\Log\LoggerInterface;

class PostService
{
    public function __construct(
        // Magento resuelve estas dependencias automáticamente
        private readonly ProductRepositoryInterface  $productRepository,
        private readonly CustomerRepositoryInterface $customerRepository,
        private readonly LoggerInterface             $logger,
        // Tipos primitivos necesitan configuración en di.xml:
        private readonly string $apiEndpoint = '',
        private readonly int    $maxRetries  = 3,
    ) {}

    public function getPost(int $id): array
    {
        $this->logger->info('Obteniendo post', ['id' => $id]);
        // usar $this->productRepository, etc.
    }
}
```

Magento lee el constructor via reflection, resuelve cada tipo y los inyecta. No necesitas registrar nada para que esto funcione con clases concretas.

## di.xml — La configuración del container

### Estructura básica

```xml
<?xml version="1.0"?>
<!-- app/code/MiVendor/MiModulo/etc/di.xml -->
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:ObjectManager/etc/config.xsd">

    <!-- Aquí van: preferences, plugins, arguments, virtualTypes -->

</config>
```

---

## Preferences — mapear interfaces a implementaciones

El uso más común de `di.xml`: decirle a Magento qué clase concreta usar cuando alguien pide una interfaz.

```xml
<config>
    <!-- Cuando alguien pida PostRepositoryInterface, inyecta PostRepository -->
    <preference for="MiVendor\Blog\Api\PostRepositoryInterface"
                type="MiVendor\Blog\Model\PostRepository"/>

    <!-- Magento usa esto internamente para todo el core: -->
    <preference for="Magento\Catalog\Api\ProductRepositoryInterface"
                type="Magento\Catalog\Model\ProductRepository"/>
</config>
```

```php
// En tu clase:
public function __construct(
    private readonly PostRepositoryInterface $postRepository  // ← interfaz
) {}
// Magento inyecta PostRepository (la implementación) gracias al preference
```

### Sobreescribir una implementación del core

```xml
<!-- Reemplazar la implementación de Magento con la tuya -->
<preference for="Magento\Catalog\Api\ProductRepositoryInterface"
            type="MiVendor\MiModulo\Model\ProductRepository"/>
```

⚠️ Esto es un **override completo** — tu clase reemplaza a la de Magento para todos. Úsalo solo cuando no haya otra opción (plugins suelen ser mejores).

## Arguments — inyectar valores en el constructor

Cuando necesitas inyectar valores primitivos (strings, ints, arrays) o una instancia específica:

```xml
<config>
    <type name="MiVendor\Blog\Model\PostService">
        <arguments>
            <!-- String -->
            <argument name="apiEndpoint" xsi:type="string">https://api.ejemplo.com</argument>

            <!-- Integer -->
            <argument name="maxRetries" xsi:type="number">5</argument>

            <!-- Boolean -->
            <argument name="debugMode" xsi:type="boolean">false</argument>

            <!-- Null -->
            <argument name="optionalDep" xsi:type="null"/>

            <!-- Objeto específico -->
            <argument name="cache" xsi:type="object">Magento\Framework\Cache\Frontend\Decorator\Logger</argument>

            <!-- Array de strings -->
            <argument name="allowedTypes" xsi:type="array">
                <item name="simple"       xsi:type="string">simple</item>
                <item name="configurable" xsi:type="string">configurable</item>
                <item name="virtual"      xsi:type="string">virtual</item>
            </argument>

            <!-- Array de objetos (muy usado para pools, chains, etc.) -->
            <argument name="validators" xsi:type="array">
                <item name="stock"  xsi:type="object">MiVendor\Blog\Validator\StockValidator</item>
                <item name="price"  xsi:type="object">MiVendor\Blog\Validator\PriceValidator</item>
            </argument>
        </arguments>
    </type>
</config>
```

```php
// El constructor recibe exactamente lo configurado en di.xml:
public function __construct(
    private readonly string $apiEndpoint,   // "https://api.ejemplo.com"
    private readonly int    $maxRetries,    // 5
    private readonly bool   $debugMode,     // false
    private readonly array  $allowedTypes,  // ['simple', 'configurable', 'virtual']
    private readonly array  $validators,    // [StockValidator, PriceValidator]
) {}
```

## Scope del di.xml — global vs por área

```
etc/di.xml           →  aplica en TODAS las áreas
etc/frontend/di.xml  →  aplica SOLO en el frontend (mergea con el global)
etc/adminhtml/di.xml →  aplica SOLO en adminhtml
etc/webapi_rest/di.xml → aplica SOLO en la API REST
```

Ejemplo práctico — diferente implementación de logger según el área:

```xml
<!-- etc/frontend/di.xml -->
<config>
    <type name="MiVendor\Blog\Model\PostService">
        <arguments>
            <argument name="logger" xsi:type="object">MiVendor\Blog\Logger\FrontendLogger</argument>
        </arguments>
    </type>
</config>

<!-- etc/adminhtml/di.xml -->
<config>
    <type name="MiVendor\Blog\Model\PostService">
        <arguments>
            <argument name="logger" xsi:type="object">MiVendor\Blog\Logger\AdminLogger</argument>
        </arguments>
    </type>
</config>
```

## Shared vs Non-Shared (Singleton vs Transient)

Por defecto todas las clases son **shared** (singleton) — el ObjectManager devuelve siempre la misma instancia:

```xml
<!-- Singleton (defecto) — misma instancia siempre -->
<type name="MiVendor\Blog\Model\PostService" shared="true"/>

<!-- Non-shared — nueva instancia cada vez que se pide -->
<type name="MiVendor\Blog\Model\Post" shared="false"/>
```

**Regla práctica**:
- Services, Repositories, Helpers → `shared="true"` (no guardan estado por request)
- Models (entidades de datos) → `shared="false"` (cada uno representa un registro diferente)

En la práctica, Magento usa Factories para los Models — nunca pides el Model directamente sino su Factory (más en [4.4](4.4-factory-classes.md)).

## Cómo Magento resuelve el DI — el proceso completo

```
1. Tu clase pide PostRepositoryInterface en el constructor

2. ObjectManager busca en di.xml si hay un <preference> para esa interfaz
   → Encuentra: type="MiVendor\Blog\Model\PostRepository"

3. Para construir PostRepository, lee su constructor
   → Necesita: ResourceModel\Post, PostFactory, LoggerInterface...

4. Resuelve recursivamente cada dependencia

5. Si hay <arguments> en di.xml para PostRepository, los aplica

6. Si shared=true, guarda la instancia para reutilizarla
   Si shared=false, crea una nueva cada vez

7. Devuelve la instancia completamente construida
```

## setup:di:compile — compilar el container

```bash
php bin/magento setup:di:compile
```

Este comando:
1. Lee todos los `di.xml` de todos los módulos
2. Resuelve el grafo completo de dependencias
3. Genera código PHP optimizado en `generated/`
4. Las Factories, Proxies e Interceptors se generan aquí

En **modo developer** esto ocurre on-demand (más lento pero sin compilar).
En **modo production** es obligatorio ejecutarlo antes del deploy.

```bash
# Ver qué genera:
ls generated/code/Magento/Catalog/Model/
# ProductFactory.php
# Product/Interceptor.php  (si hay plugins)
# ProductRepository/Proxy.php (si hay proxies)
```

## Resumen

```
ObjectManager   →  el container — resuelve y construye clases
Constructor DI  →  la forma correcta de recibir dependencias
preference      →  interface → implementación concreta
arguments       →  inyectar primitivos, arrays, instancias específicas
shared          →  true=singleton (default), false=nueva instancia
di.xml global   →  todas las áreas
di.xml por área →  solo frontend, adminhtml, etc.

NUNCA uses ObjectManager directamente en tu código
SIEMPRE inyecta las dependencias en el constructor
```
