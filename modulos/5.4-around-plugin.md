# 5.4 — Around Plugin: Control Total del Método

> **Objetivo**: Dominar el Around Plugin — el más poderoso y el más peligroso. Entender cuándo es la única opción y cuándo es un error usarlo en lugar de before/after.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [5.3 — After Plugin](5.3-after-plugin.md)

---

## Qué hace un Around Plugin

Envuelve completamente el método interceptado. Tú decides:
- Si llamar al método original o no
- Cuándo llamarlo
- Qué retornar independientemente del resultado original

Es el equivalente al middleware en otros frameworks.

---

## Firma del método

```php
public function around{NombreMetodo}(
    SubjectType $subject,   // instancia de la clase interceptada
    callable $proceed,      // función para llamar al método original (o al siguiente plugin)
    ...$args                // los argumentos del método original
): ResultType
```

- `$proceed` es la función que ejecuta el método original (o el siguiente around plugin en la cadena)
- Debes retornar el mismo tipo que el método original
- Si no llamas `$proceed(...)`, el método original **nunca se ejecuta**

---

## Ejemplo básico — envolver con lógica

```php
namespace MiVendor\Blog\Plugin;

use Magento\Catalog\Api\ProductRepositoryInterface;
use Magento\Catalog\Api\Data\ProductInterface;
use Psr\Log\LoggerInterface;

class MeasureProductLoadTimePlugin
{
    public function __construct(
        private readonly LoggerInterface $logger
    ) {}

    public function aroundGetById(
        ProductRepositoryInterface $subject,
        callable $proceed,
        int $productId,
        bool $editMode = false,
        ?int $storeId = null,
        bool $forceReload = false
    ): ProductInterface {
        $start = microtime(true);

        // Llamar al método original
        $result = $proceed($productId, $editMode, $storeId, $forceReload);

        $elapsed = round((microtime(true) - $start) * 1000, 2);
        $this->logger->debug("getById tomó {$elapsed}ms", ['product_id' => $productId]);

        return $result;
    }
}
```

## Ejemplo — caché con around

El caso de uso más legítimo para `around`: implementar una capa de caché que evita llamar al método original si el resultado ya está en caché.

```php
namespace MiVendor\Blog\Plugin;

use Magento\Catalog\Api\ProductRepositoryInterface;
use Magento\Catalog\Api\Data\ProductInterface;
use Magento\Framework\App\CacheInterface;
use Magento\Framework\Serialize\SerializerInterface;

class CacheProductRepositoryPlugin
{
    private const CACHE_LIFETIME = 3600;

    public function __construct(
        private readonly CacheInterface      $cache,
        private readonly SerializerInterface $serializer
    ) {}

    public function aroundGetById(
        ProductRepositoryInterface $subject,
        callable $proceed,
        int $productId,
        bool $editMode = false,
        ?int $storeId = null,
        bool $forceReload = false
    ): ProductInterface {
        // En edit mode o force reload, no usar caché
        if ($editMode || $forceReload) {
            return $proceed($productId, $editMode, $storeId, $forceReload);
        }

        $cacheKey = "product_{$productId}_{$storeId}";
        $cached = $this->cache->load($cacheKey);

        if ($cached) {
            // Retornar desde caché sin llamar al método original
            return $this->serializer->unserialize($cached);
        }

        // Llamar al método original
        $result = $proceed($productId, $editMode, $storeId, $forceReload);

        // Guardar en caché
        $this->cache->save(
            $this->serializer->serialize($result),
            $cacheKey,
            ['product_cache'],
            self::CACHE_LIFETIME
        );

        return $result;
    }
}
```

## Ejemplo — control de acceso

```php
namespace MiVendor\Blog\Plugin;

use Magento\Catalog\Api\ProductRepositoryInterface;
use Magento\Catalog\Api\Data\ProductInterface;
use Magento\Customer\Model\Session;
use Magento\Framework\Exception\AuthorizationException;

class RestrictProductAccessPlugin
{
    public function __construct(
        private readonly Session $customerSession
    ) {}

    public function aroundGetById(
        ProductRepositoryInterface $subject,
        callable $proceed,
        int $productId,
        bool $editMode = false,
        ?int $storeId = null,
        bool $forceReload = false
    ): ProductInterface {
        // Verificar acceso antes de ejecutar
        if (!$this->customerSession->isLoggedIn() && in_array($productId, $this->getRestrictedIds())) {
            throw new AuthorizationException(
                __('Debes iniciar sesión para ver este producto.')
            );
        }

        return $proceed($productId, $editMode, $storeId, $forceReload);
    }

    private function getRestrictedIds(): array
    {
        return [42, 99, 150]; // IDs de productos restringidos
    }
}
```

## La cadena de around plugins

Cuando hay múltiples around plugins, se anidan como matrioskas:

```
Around Plugin A (sortOrder=10)
  └── Around Plugin B (sortOrder=20)
        └── Around Plugin C (sortOrder=30)
              └── Método original
```

Cada `$proceed` llama al siguiente around en la cadena, no directamente al método original:

```php
// Plugin A
public function aroundGetById($subject, callable $proceed, $id): ProductInterface
{
    // antes de B y del método original
    $result = $proceed($id);  // ← llama a Plugin B
    // después de B y del método original
    return $result;
}

// Plugin B
public function aroundGetById($subject, callable $proceed, $id): ProductInterface
{
    // antes del método original
    $result = $proceed($id);  // ← llama a Plugin C
    // después del método original
    return $result;
}
```

## ⚠️ Cuándo NO usar Around Plugin

Around es el plugin más peligroso porque:
1. **Impacto en performance**: agrega overhead por cada método interceptado
2. **Si olvidas llamar `$proceed`**: el método original nunca se ejecuta, rompiendo la cadena
3. **Dificulta el debugging**: el stack trace se vuelve más complejo

```
❌ NO uses around si puedes usar before o after:

Quiero ejecutar lógica antes          → before plugin
Quiero modificar argumentos           → before plugin
Quiero modificar el resultado         → after plugin
Quiero logging pre/post               → before + after plugin

✅ USA around solo cuando:
Necesitas evitar llamar al método original (caché, feature flag)
Necesitas hacer algo antes Y después usando el mismo estado local
Necesitas try/catch alrededor del método original
Necesitas control de acceso que puede detener la ejecución
```

## Around con try/catch — manejo de errores

```php
public function aroundSave(
    ProductRepositoryInterface $subject,
    callable $proceed,
    ProductInterface $product
): ProductInterface {
    try {
        $result = $proceed($product);

        // Solo si el save fue exitoso
        $this->eventManager->dispatch('blog_product_saved_success', [
            'product' => $result
        ]);

        return $result;

    } catch (\Exception $e) {
        $this->logger->error('Error guardando producto', [
            'sku'   => $product->getSku(),
            'error' => $e->getMessage()
        ]);

        // Puedes re-lanzar o manejar el error
        throw $e;
    }
}
```

## Around con feature flag

```php
public function aroundGetById(
    ProductRepositoryInterface $subject,
    callable $proceed,
    int $productId,
    bool $editMode = false,
    ?int $storeId = null,
    bool $forceReload = false
): ProductInterface {
    // Feature flag: si está desactivado, comportamiento normal
    if (!$this->config->isFeatureEnabled('new_product_loader')) {
        return $proceed($productId, $editMode, $storeId, $forceReload);
    }

    // Nuevo comportamiento
    return $this->newProductLoader->load($productId, $storeId);
}
```

## Resumen

```
Around Plugin:
  - Envuelve completamente el método
  - $proceed(...) llama al siguiente plugin o al método original
  - Si no llamas $proceed, el método original NO se ejecuta
  - Mismo tipo de retorno que el método original

Firma:
  public function around{Metodo}(SubjectType $subject, callable $proceed, ...$args): ResultType

Usar SOLO cuando:
  → Necesitas evitar el método original (caché, feature flags)
  → Necesitas try/catch alrededor del método
  → Necesitas estado compartido entre pre y post ejecución
  → Control de acceso que puede bloquear la ejecución

Para todo lo demás: before o after son más simples y seguros
```

## Ejercicios

### Ejercicio 1 — Feature flag con around

Crea un Around Plugin sobre `ProductRepositoryInterface::getById()` que use una variable de entorno `BLOG_USE_NEW_LOADER`. Si está en `1`, retorna un producto "simulado" con nombre "Nuevo Loader". Si no, llama al método original normalmente.

<details>
<summary>Ver solución</summary>

```php
// Plugin/FeatureFlagLoaderPlugin.php
namespace MiVendor\Blog\Plugin;

use Magento\Catalog\Api\ProductRepositoryInterface;
use Magento\Catalog\Api\Data\ProductInterface;
use Magento\Catalog\Api\Data\ProductInterfaceFactory;

class FeatureFlagLoaderPlugin
{
    public function __construct(
        private readonly ProductInterfaceFactory $productFactory
    ) {}

    public function aroundGetById(
        ProductRepositoryInterface $subject,
        callable $proceed,
        int $productId,
        bool $editMode = false,
        ?int $storeId = null,
        bool $forceReload = false
    ): ProductInterface {
        if (getenv('BLOG_USE_NEW_LOADER') === '1') {
            // Nuevo comportamiento — sin llamar al original
            $product = $this->productFactory->create();
            $product->setName('Nuevo Loader - Producto ' . $productId);
            $product->setId($productId);
            return $product;
        }

        // Comportamiento original
        return $proceed($productId, $editMode, $storeId, $forceReload);
    }
}
```

```xml
<type name="Magento\Catalog\Api\ProductRepositoryInterface">
    <plugin name="mivendor_blog_feature_flag_loader"
            type="MiVendor\Blog\Plugin\FeatureFlagLoaderPlugin"
            sortOrder="1"/>
</type>
```

```bash
# Activar el nuevo loader:
export BLOG_USE_NEW_LOADER=1

# Desactivar:
unset BLOG_USE_NEW_LOADER
```

</details>

### Ejercicio 2 — Try/catch con notificación

Crea un Around Plugin sobre `ProductRepositoryInterface::save()` que capture cualquier excepción durante el guardado, la loguee y la re-lance. Adicionalmente, si el guardado fue exitoso, dispara el evento `mivendor_blog_product_saved`.

<details>
<summary>Ver solución</summary>

```php
// Plugin/SafeProductSavePlugin.php
namespace MiVendor\Blog\Plugin;

use Magento\Catalog\Api\ProductRepositoryInterface;
use Magento\Catalog\Api\Data\ProductInterface;
use Magento\Framework\Event\ManagerInterface;
use Psr\Log\LoggerInterface;

class SafeProductSavePlugin
{
    public function __construct(
        private readonly LoggerInterface $logger,
        private readonly ManagerInterface $eventManager,
    ) {}

    public function aroundSave(
        ProductRepositoryInterface $subject,
        callable $proceed,
        ProductInterface $product
    ): ProductInterface {
        try {
            $result = $proceed($product);

            $this->eventManager->dispatch('mivendor_blog_product_saved', [
                'product' => $result,
            ]);

            return $result;

        } catch (\Exception $e) {
            $this->logger->error('Error guardando producto', [
                'sku'   => $product->getSku(),
                'error' => $e->getMessage(),
            ]);
            throw $e; // re-lanzar para no silenciar el error
        }
    }
}
```

```xml
<type name="Magento\Catalog\Api\ProductRepositoryInterface">
    <plugin name="mivendor_blog_safe_save"
            type="MiVendor\Blog\Plugin\SafeProductSavePlugin"
            sortOrder="20"/>
</type>
```

</details>
