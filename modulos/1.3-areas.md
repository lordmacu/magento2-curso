## Recapitulando: ¿qué es un Area?

En el módulo anterior vimos que un Area es un **contexto de ejecución**. Ahora lo vemos a fondo con código real.

Cuando Magento arranca, una de las primeras cosas que hace es determinar en qué Area está corriendo. Esta decisión afecta **todo**:

- Qué archivos `di.xml` se cargan
- Qué layouts y templates están disponibles
- Qué plugins, observers y preferences aplican
- Qué configuración de sistema es visible
- Qué routers están activos

🔄 **Laravel**: Es equivalente a tener un middleware que cambia la configuración global de tu app según si la petición viene de `/api/*`, `/admin/*` o rutas normales. Pero en Magento no es un middleware — es un sistema de bootstrap completo que cambia qué clases se instancian.

## Las 6 Areas de Magento

```
Magento\Framework\App\Area

const AREA_GLOBAL      = 'global';       // Base, se carga siempre
const AREA_FRONTEND    = 'frontend';     // La tienda pública
const AREA_ADMINHTML   = 'adminhtml';    // El panel de administración
const AREA_CRONTAB     = 'crontab';      // Tareas programadas
const AREA_WEBAPI_REST = 'webapi_rest';  // API REST
const AREA_WEBAPI_SOAP = 'webapi_soap';  // API SOAP (legacy)
const AREA_GRAPHQL     = 'graphql';      // API GraphQL
```

### `frontend` — La tienda pública

```
Activa cuando: URL no empieza por /rest/, /graphql, /admin/
Ejemplos de URLs: /, /catalog/product/view, /checkout/cart

Características:
✓ Full Page Cache activo (Varnish o built-in)
✓ Layouts del storefront disponibles
✓ Sesión del cliente (login, carrito)
✓ Precio visible según grupo de cliente
✓ Blocks, templates del storefront
```

### `adminhtml` — El panel de administración

```
Activa cuando: URL empieza por /admin/ (o la ruta custom configurada)
Ejemplos: /admin/catalog/product, /admin/sales/order

Características:
✓ Sin Full Page Cache
✓ Autenticación de usuario admin requerida
✓ ACL (Access Control List) activo
✓ UI Components (grids, formularios)
✓ Acceso a toda la configuración del sistema
```

### `webapi_rest` — API REST

```
Activa cuando: URL empieza por /rest/
Ejemplos: /rest/V1/products, /rest/V1/carts/mine/items

Características:
✓ Sin templates ni layouts — solo JSON
✓ Autenticación via Bearer Token o OAuth
✓ Respuestas serializadas automáticamente
✓ Versionado (/V1/, /V2/, etc.)
```

### `graphql` — API GraphQL

```
Activa cuando: URL es /graphql (POST)
Ejemplo body: query { products { items { name } } }

Características:
✓ Sin templates — solo JSON
✓ Schema definido en archivos schema.graphqls
✓ Resolvers PHP manejan cada query/mutation
✓ Autenticación via header Authorization
```

### `crontab` — Tareas programadas

```
Activa cuando: bin/magento cron:run
Ejemplos: reindexado, envío de emails, limpieza de logs

Características:
✓ Sin contexto HTTP — no hay request ni response
✓ Sin sesión de usuario
✓ Acceso completo a todos los servicios
✓ Puede correr múltiples grupos en paralelo
```

### `global` — El área base

```
Se carga siempre, en todos los contextos, como capa base.
El área activa se superpone encima de global.

Un di.xml en etc/ (sin subdirectorio de área) aplica a todos los contextos.
```

## Estructura de archivos por área en tu módulo

Esta es la convención de directorios que Magento respeta:

```
app/code/MiVendor/MiModulo/etc/
│
├── di.xml              ← GLOBAL: aplica en frontend + adminhtml + webapi + graphql + cron
├── module.xml          ← GLOBAL: siempre
├── config.xml          ← GLOBAL: valores default de System Config
│
├── frontend/
│   ├── di.xml          ← solo storefront
│   ├── routes.xml      ← rutas /blog/*, /mi-modulo/*, etc.
│   └── events.xml      ← observers solo en storefront
│
├── adminhtml/
│   ├── di.xml          ← solo panel admin
│   ├── routes.xml      ← rutas /admin/mi-modulo/*
│   ├── menu.xml        ← entrada en el menú del admin
│   └── events.xml      ← observers solo en admin
│
├── webapi_rest/
│   └── di.xml          ← solo API REST
│
├── graphql/
│   └── di.xml          ← solo GraphQL
│
└── crontab/
    └── di.xml          ← solo cron jobs
```

💡 **TIP**: No necesitas crear todos los subdirectorios. Solo crea los que realmente usas. Si un archivo `di.xml` no existe para un área, simplemente no se carga nada extra para ese contexto.

## Usar Areas en tu módulo: casos reales

### Caso 1: Plugin que solo aplica en el storefront

Quieres agregar datos extra a un producto solo cuando lo solicita la tienda (no el admin, no la API):

```xml
<!-- etc/frontend/di.xml — solo storefront, no afecta admin ni API -->
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:ObjectManager/etc/config.xsd">
    <type name="Magento\Catalog\Model\Product">
        <plugin name="mimodulo_product_data_frontend"
                type="MiVendor\MiModulo\Plugin\Frontend\ProductPlugin"
                sortOrder="10"/>
    </type>
</config>
```

Si lo pusieras en `etc/di.xml` (global), el plugin correría también en el admin y en la API REST, lo cual puede ser innecesario o problemático.

### Caso 2: Diferente implementación según contexto

En el storefront el precio incluye IVA, en la API no:

```xml
<!-- etc/di.xml (global — implementación por defecto) -->
<preference for="MiVendor\MiModulo\Api\PrecioInterface"
            type="MiVendor\MiModulo\Model\Precio\Base"/>

<!-- etc/frontend/di.xml — override solo en storefront -->
<preference for="MiVendor\MiModulo\Api\PrecioInterface"
            type="MiVendor\MiModulo\Model\Precio\ConIva"/>

<!-- etc/webapi_rest/di.xml — override solo en API REST -->
<preference for="MiVendor\MiModulo\Api\PrecioInterface"
            type="MiVendor\MiModulo\Model\Precio\SinIva"/>
```

### Caso 3: Observers por área

```xml
<!-- etc/frontend/events.xml — se dispara solo cuando navega la tienda -->
<event name="catalog_product_load_after">
    <observer name="mimodulo_track_view"
              instance="MiVendor\MiModulo\Observer\Frontend\TrackProductView"/>
</event>

<!-- etc/adminhtml/events.xml — se dispara solo en el admin -->
<event name="catalog_product_save_after">
    <observer name="mimodulo_sync_erp"
              instance="MiVendor\MiModulo\Observer\Admin\SyncToErp"/>
</event>

<!-- etc/events.xml — se dispara en TODOS los contextos -->
<event name="customer_login">
    <observer name="mimodulo_log_login"
              instance="MiVendor\MiModulo\Observer\LogLogin"/>
</event>
```

### Caso 4: Inyectar argumentos diferentes por contexto

```xml
<!-- etc/di.xml (global) — logger genérico -->
<type name="MiVendor\MiModulo\Model\MiServicio">
    <arguments>
        <argument name="logger" xsi:type="object">Psr\Log\LoggerInterface</argument>
        <argument name="modo" xsi:type="string">normal</argument>
    </arguments>
</type>

<!-- etc/adminhtml/di.xml — logger específico del admin -->
<type name="MiVendor\MiModulo\Model\MiServicio">
    <arguments>
        <argument name="logger" xsi:type="object">MiVendor\MiModulo\Logger\AdminLogger</argument>
        <argument name="modo" xsi:type="string">admin</argument>
    </arguments>
</type>
```

## Leer el área activa en código PHP

```php
namespace MiVendor\MiModulo\Model;

use Magento\Framework\App\State;
use Magento\Framework\App\Area;

class MiServicio
{
    public function __construct(
        private readonly State $appState
    ) {}

    public function ejecutar(): string
    {
        try {
            $area = $this->appState->getAreaCode();
        } catch (\Magento\Framework\Exception\LocalizedException $e) {
            // Área no seteada aún (durante el bootstrap)
            return 'no-area';
        }

        return match($area) {
            Area::AREA_FRONTEND    => 'Estamos en la tienda',
            Area::AREA_ADMINHTML   => 'Estamos en el admin',
            Area::AREA_WEBAPI_REST => 'Estamos en la API REST',
            Area::AREA_GRAPHQL     => 'Estamos en GraphQL',
            Area::AREA_CRONTAB     => 'Estamos en cron',
            default                => "Área desconocida: {$area}",
        };
    }
}
```

## El problema del CLI y `setAreaCode()`

Los comandos de `bin/magento` NO tienen un área seteada automáticamente. Si tu comando usa servicios que la requieren (emails, precios, URLs), debes setearlo manualmente:

```php
namespace MiVendor\MiModulo\Console\Command;

use Symfony\Component\Console\Command\Command;
use Symfony\Component\Console\Input\InputInterface;
use Symfony\Component\Console\Output\OutputInterface;
use Magento\Framework\App\State;
use Magento\Framework\App\Area;

class ProcesarPedidosCommand extends Command
{
    protected static $defaultName = 'mimodulo:procesar-pedidos';

    public function __construct(
        private readonly State $appState,
        string $name = null
    ) {
        parent::__construct($name);
    }

    protected function configure(): void
    {
        $this->setDescription('Procesa pedidos pendientes');
    }

    protected function execute(InputInterface $input, OutputInterface $output): int
    {
        // ⚠️ Obligatorio si usas servicios de precios, URLs, emails, layouts
        $this->appState->setAreaCode(Area::AREA_FRONTEND);

        $output->writeln('Procesando pedidos...');
        // ... tu lógica aquí

        return Command::SUCCESS;
    }
}
```

⚠️ **Error más común en comandos CLI**:
```
Magento\Framework\Exception\LocalizedException: Area code is not set
```
Solución: agregar `$this->appState->setAreaCode(Area::AREA_FRONTEND)` al inicio de `execute()`.

💡 **TIP**: Si tu comando ya tiene el área seteada (por ejemplo, desde un test previo o un comando padre), `setAreaCode()` lanzará `LocalizedException: Area code is already set`. Usa este patrón para evitarlo:

```php
try {
    $this->appState->setAreaCode(Area::AREA_FRONTEND);
} catch (\Magento\Framework\Exception\LocalizedException $e) {
    // Ya estaba seteado, ignorar
}
```

## Area Emulation: ejecutar código en otro contexto

A veces desde un cron (área `crontab`) necesitas renderizar un email o calcular precios, operaciones que requieren contexto `frontend`. Para esto existe **Area Emulation**:

```php
namespace MiVendor\MiModulo\Cron;

use Magento\Framework\App\Area;
use Magento\Store\Model\App\Emulation;

class EnviarEmailsPromocion
{
    public function __construct(
        private readonly Emulation $emulation,
        private readonly \Magento\Framework\Mail\Template\TransportBuilder $transportBuilder
    ) {}

    public function execute(): void
    {
        $storeId = 1; // ID de la tienda

        // Emular contexto frontend para la tienda 1
        $this->emulation->startEnvironmentEmulation($storeId, Area::AREA_FRONTEND);

        try {
            // Aquí puedes usar servicios que requieren contexto frontend:
            // - Renderizar templates de email
            // - Obtener URLs absolutas
            // - Calcular precios con formato de moneda
            $this->enviarEmailPromocion($storeId);

        } finally {
            // SIEMPRE restaurar — el finally garantiza que se ejecuta incluso con excepción
            $this->emulation->stopEnvironmentEmulation();
        }
    }

    private function enviarEmailPromocion(int $storeId): void
    {
        // lógica de email aquí
    }
}
```

💡 **TIP**: El patrón `try/finally` es **obligatorio** con emulation. Si falta el `stopEnvironmentEmulation()`, el área queda corrupta para el resto del proceso, causando errores difíciles de debuggear.

## Cómo Magento carga los di.xml: el orden exacto

```
Paso 1: Carga etc/di.xml de TODOS los módulos (en orden de prioridad)
Paso 2: Detecta el área activa
Paso 3: Carga etc/{area}/di.xml de TODOS los módulos
Paso 4: Fusiona: el área sobreescribe el global cuando hay conflicto

Resultado: un container DI configurado para este contexto específico
```

Ejemplo de fusión:

```xml
<!-- etc/di.xml — descuento = 0 para todos -->
<type name="MiVendor\MiModulo\Model\PrecioCalculador">
    <arguments>
        <argument name="descuento" xsi:type="number">0</argument>
    </arguments>
</type>

<!-- etc/frontend/di.xml — sobreescribe solo para frontend -->
<type name="MiVendor\MiModulo\Model\PrecioCalculador">
    <arguments>
        <argument name="descuento" xsi:type="number">5</argument>
    </arguments>
</type>
```

| Contexto | Valor de `descuento` |
|---|---|
| `frontend` | 5 (del frontend/di.xml) |
| `adminhtml` | 0 (del global di.xml) |
| `webapi_rest` | 0 (del global di.xml) |
| `crontab` | 0 (del global di.xml) |

## Areas y multistore: no confundirlos

Son dos conceptos **independientes**:

```
Area = frontend
    │
    ├── Store View 1: Mexico  → idioma ES, moneda MXN, precios propios
    ├── Store View 2: USA     → idioma EN, moneda USD, precios propios
    └── Store View 3: España  → idioma ES-EU, moneda EUR, precios propios
```

El **Area** determina qué código se ejecuta.
El **Store View** determina con qué datos (precios, traducciones, configuración).

Ambos cambian la experiencia, pero de maneras distintas. Profundizaremos en Store Views en el módulo 1.8.

## Resumen

| Area | URL / Trigger | Cache | Auth | Layouts |
|---|---|---|---|---|
| `global` | Base siempre | — | — | — |
| `frontend` | `/`, `/catalog/*`, etc. | FPC activo | Sesión cliente | Sí |
| `adminhtml` | `/admin/*` | Sin cache | Admin obligatorio | Sí (admin) |
| `webapi_rest` | `/rest/*` | Sin cache | Token/OAuth | No |
| `graphql` | `/graphql` | Parcial | Header Auth | No |
| `crontab` | `cron:run` | Sin cache | Sin auth | No |

### Reglas prácticas del día a día

```
¿Tu di.xml/plugin/observer aplica en TODOS los contextos?
    → etc/di.xml  (sin subdirectorio)

¿Solo en la tienda?
    → etc/frontend/di.xml

¿Solo en el admin?
    → etc/adminhtml/di.xml

¿Solo en la API REST?
    → etc/webapi_rest/di.xml

¿Tienes un comando CLI que usa servicios?
    → Setea $this->appState->setAreaCode() al inicio de execute()

¿Desde cron necesitas renderizar templates o emails?
    → Usa $this->emulation->startEnvironmentEmulation()
```
