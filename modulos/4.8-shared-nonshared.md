# 4.8 — Shared vs Non-Shared: Singleton vs Transient

> **Objetivo**: Entender cuándo Magento reutiliza instancias y cuándo crea nuevas, cómo controlarlo y los bugs que aparecen cuando usas el modo incorrecto.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [4.7 — Preferences](4.7-preferences.md)

---

## El comportamiento por defecto

Por defecto, el ObjectManager trata todas las clases como **shared** (singleton) — siempre devuelve la misma instancia para una clase dada durante el ciclo de vida de la request.

```php
// Ambas variables apuntan a la MISMA instancia
$repoA = $objectManager->get(PostRepository::class);
$repoB = $objectManager->get(PostRepository::class);

var_dump($repoA === $repoB); // true
```

Esto es eficiente para servicios sin estado — se construyen una vez y se reutilizan.

---

## Shared = true (Singleton)

```xml
<!-- Explícito, aunque es el default -->
<type name="MiVendor\Blog\Model\PostRepository" shared="true"/>
```

**Cuándo es correcto**:
- Services (lógica de negocio sin estado por request)
- Repositories
- Helpers y Utilities
- Loggers
- Cualquier clase que no guarde estado mutable entre llamadas

```php
// ✅ Correcto como singleton — no guarda estado mutable
class PostRepository
{
    public function __construct(
        private readonly ResourceModel\Post $resource,
        private readonly PostFactory        $postFactory,
    ) {}

    // Cada llamada trabaja con sus propios datos locales
    public function getById(int $id): Post
    {
        $post = $this->postFactory->create(); // nueva instancia local
        $this->resource->load($post, $id);
        return $post;
    }
}
```

---

## Non-Shared = false (Transient)

```xml
<type name="MiVendor\Blog\Model\Post" shared="false"/>
```

Con `shared="false"`, cada llamada a `$objectManager->get()` o a la Factory devuelve una **nueva instancia**.

**Cuándo es correcto**:
- Models/Entidades que representan un registro específico
- Objetos que guardan estado mutable
- Objetos que necesitan inicialización limpia cada vez

---

## El bug clásico: estado compartido en singleton

```php
// ❌ PELIGROSO como singleton — guarda estado mutable
class ShoppingCart
{
    private array $items = [];

    public function addItem(string $sku, int $qty): void
    {
        $this->items[] = ['sku' => $sku, 'qty' => $qty];
    }

    public function getItems(): array
    {
        return $this->items;
    }
}
```

Si `ShoppingCart` es singleton y dos partes del código lo usan en la misma request:

```php
// Primer uso — agrega items del cliente A
$cart->addItem('SKU-001', 2);

// Segundo uso — la misma instancia, ya tiene los items del cliente A
$cart->addItem('SKU-002', 1);
$cart->getItems(); // ['SKU-001' x2, 'SKU-002' x1] — datos mezclados
```

Solución — declarar como non-shared:

```xml
<type name="MiVendor\Blog\Model\ShoppingCart" shared="false"/>
```

O mejor aún — usar Factory:

```php
// Cada vez que necesitas un carrito nuevo:
$cart = $this->cartFactory->create(); // instancia limpia
```

## Shared en Factories y el ObjectManager

```php
// get() — respeta shared config
$objectManager->get(PostRepository::class);  // shared=true → misma instancia
$objectManager->get(Post::class);            // shared=false → nueva instancia

// create() — SIEMPRE crea instancia nueva, ignora shared
$objectManager->create(Post::class);         // siempre nueva instancia
$objectManager->create(PostRepository::class); // también nueva (aunque shared=true)
```

Por eso las Factories usan `create()` internamente — garantizan instancia nueva independientemente de la configuración `shared`.

---

## Configurar shared por tipo de argumento

Puedes controlar `shared` a nivel de argumento individual:

```xml
<type name="MiVendor\Blog\Service\PostService">
    <arguments>
        <!-- Esta instancia específica de Cache es non-shared para este servicio -->
        <argument name="cache" xsi:type="object" shared="false">
            Magento\Framework\Cache\Frontend\Decorator\Logger
        </argument>

        <!-- Esta es shared (default) -->
        <argument name="repository" xsi:type="object">
            MiVendor\Blog\Model\PostRepository
        </argument>
    </arguments>
</type>
```

## Verificar el comportamiento en la práctica

```php
// Script de diagnóstico (pub/debug.php temporal)
use Magento\Framework\App\Bootstrap;
require __DIR__ . '/../app/bootstrap.php';

$bootstrap = Bootstrap::create(BP, $_SERVER);
$om = $bootstrap->getObjectManager();

// Verificar shared
$a = $om->get(\MiVendor\Blog\Model\PostRepository::class);
$b = $om->get(\MiVendor\Blog\Model\PostRepository::class);
echo "PostRepository shared: " . ($a === $b ? 'SÍ' : 'NO') . "\n";

// Verificar non-shared
$c = $om->get(\MiVendor\Blog\Model\Post::class);
$d = $om->get(\MiVendor\Blog\Model\Post::class);
echo "Post shared: " . ($c === $d ? 'SÍ' : 'NO') . "\n";
```

## Tabla de decisión

| Tipo de clase | shared | Por qué |
|---|---|---|
| Repository | `true` | Sin estado mutable, se reutiliza |
| Service / Manager | `true` | Sin estado mutable, se reutiliza |
| Logger | `true` | Sin estado mutable |
| Helper | `true` | Sin estado mutable |
| Model / Entity | `false` | Representa un registro concreto |
| DTO / Data Object | `false` | Lleva datos específicos |
| Cart / Basket | `false` | Estado mutable por sesión |
| Form / Request Object | `false` | Datos únicos por request |

---

## Resumen

```
shared="true"   → singleton, misma instancia en toda la request  (DEFAULT)
shared="false"  → nueva instancia cada vez que se solicita

Cuándo usar false:
  - El objeto guarda estado mutable
  - Representa un registro o entidad concreta
  - Necesita inicialización limpia en cada uso

Señal de alarma:
  - Un singleton con propiedades mutables (private array $items)
  - Dos partes del código comparten datos sin querer
  → Cambiar a shared="false" o usar Factory

Regla de oro:
  Services/Repos → shared=true
  Models/Entities → shared=false (o mejor aún, usa siempre Factory)
```

## Ejercicios

### Ejercicio 1 — Identificar el bug de singleton con estado mutable

Este código tiene un bug producido por el comportamiento singleton del DI. Identifícalo y corrígelo.

```php
class NotificationQueue
{
    private array $messages = [];

    public function add(string $message): void
    {
        $this->messages[] = $message;
    }

    public function flush(): array
    {
        $messages = $this->messages;
        $this->messages = [];
        return $messages;
    }
}

// Uso en OrderController:
class OrderController
{
    public function __construct(
        private readonly NotificationQueue $queue,
        private readonly OrderService $orderService,
    ) {}

    public function placeAction(): void
    {
        $this->queue->add('Pedido recibido');
        $this->orderService->process(); // internamente también llama a $queue->add()
        $notifications = $this->queue->flush();
        // ¿Cuántos mensajes tiene $notifications?
    }
}
```

<details>
<summary>Ver solución</summary>

**El bug**: `NotificationQueue` es singleton por defecto — `OrderController` y `OrderService` comparten la **misma instancia**. Si `OrderService` también agrega mensajes a la queue, ambos módulos los ven todos juntos en `flush()`. Esto puede ser el comportamiento deseado o un error — depende del diseño.

**Si el bug es que NO quieres estado compartido** (cada instancia tiene su propia lista):

```xml
<!-- etc/di.xml — hacer la queue non-shared -->
<type name="MiVendor\Blog\Model\NotificationQueue" shared="false"/>
```

Ahora `OrderController` y `OrderService` cada uno tendrán su propia instancia de `NotificationQueue` con su propia lista `$messages`.

**Si sí quieres estado compartido** (una queue global por request): el código actual está bien — es el comportamiento singleton por defecto.

**La señal de alarma**:
- Una clase tiene `private array $property = []` y métodos que la modifican
- Esa clase se usa desde múltiples lugares en la misma request
- Si compartes datos entre esos lugares sin querer → `shared="false"` o usa Factory

</details>

### Ejercicio 2 — ¿Shared o non-shared? Clasificar estas clases

Determina si cada una de estas clases debería ser `shared="true"` o `shared="false"`:

```
1. CurrencyConverter    — convierte monedas usando tasas de cambio del día
2. OrderDraft          — objeto que representa un pedido en construcción (tiene addItem, setAddress)
3. TaxCalculator       — calcula impuestos dado un precio y una región
4. SearchResult        — contiene la lista de productos encontrados en una búsqueda
5. EmailSender         — envía emails vía SMTP, sin estado mutable
6. ImportRow           — representa una fila del CSV que se está importando
```

<details>
<summary>Ver solución</summary>

```
1. CurrencyConverter  → shared="true"
   Sin estado mutable — mismo resultado para la misma entrada en toda la request.

2. OrderDraft         → shared="false"  ✱ o mejor usar Factory
   Guarda estado mutable (items, dirección). Cada pedido necesita su propia instancia.

3. TaxCalculator      → shared="true"
   Sin estado mutable — función pura, toma input y devuelve output.

4. SearchResult       → shared="false"  ✱ o mejor usar Factory
   Contiene datos de una búsqueda específica. Una búsqueda diferente = objeto diferente.

5. EmailSender        → shared="true"
   Service sin estado mutable. Se reutiliza sin problema.

6. ImportRow          → shared="false"  ✱ o mejor usar Factory
   Representa un registro específico (fila del CSV). Necesita ser nuevo para cada fila.
```

**Regla de oro**: si puedes describir la clase como "el servicio que hace X" → shared. Si la describes como "un objeto que representa Y" → non-shared (o Factory).

</details>
