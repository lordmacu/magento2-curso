# 4.7 — Preferences: Reemplazar una Clase del Core

> **Objetivo**: Entender qué es un Preference, cuándo es la herramienta correcta para sobreescribir comportamiento del core, cuándo NO usarlo, y cómo hacerlo correctamente para evitar conflictos con otros módulos.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [4.6 — Virtual Types](4.6-virtual-types.md)

---

## Qué es un Preference

Un Preference le dice al ObjectManager: "cuando alguien pida la clase X, dale la clase Y en su lugar". Es un reemplazo global y completo.

```xml
<!-- etc/di.xml -->
<preference for="Magento\Catalog\Model\Product"
            type="MiVendor\MiModulo\Model\Product"/>
```

A partir de esto, **cualquier clase** de todo Magento que pida `Magento\Catalog\Model\Product` recibirá `MiVendor\MiModulo\Model\Product`.

---

## El uso legítimo: mapear interfaces a implementaciones

El uso más común y correcto de Preference es vincular una interfaz con su implementación concreta — especialmente para tus propios Service Contracts:

```xml
<!-- Tu módulo define la interfaz y su implementación -->
<preference for="MiVendor\Blog\Api\PostRepositoryInterface"
            type="MiVendor\Blog\Model\PostRepository"/>

<preference for="MiVendor\Blog\Api\Data\PostInterface"
            type="MiVendor\Blog\Model\Post"/>
```

```php
// Cualquier clase que pida PostRepositoryInterface recibe PostRepository:
public function __construct(
    private readonly PostRepositoryInterface $postRepository  // ← recibe PostRepository
) {}
```

Esto es arquitectura limpia — el código depende de abstracciones, no de implementaciones concretas.

---

## Sobreescribir una clase del core

Cuando necesitas cambiar el comportamiento de una clase de Magento:

```php
// app/code/MiVendor/MiModulo/Model/Product.php
namespace MiVendor\MiModulo\Model;

class Product extends \Magento\Catalog\Model\Product
{
    // Sobreescribir un método específico
    public function getPrice(): float
    {
        $price = parent::getPrice();

        // Tu lógica custom: aplicar descuento por volumen
        if ($this->getQty() >= 10) {
            $price *= 0.9;
        }

        return $price;
    }

    // Agregar un método nuevo
    public function getFormattedSku(): string
    {
        return strtoupper($this->getSku());
    }
}
```

```xml
<!-- etc/di.xml -->
<preference for="Magento\Catalog\Model\Product"
            type="MiVendor\MiModulo\Model\Product"/>
```

---

## ⚠️ El gran problema con Preferences en clases concretas

**Solo puede haber un Preference** por clase en todo el sistema. Si dos módulos definen un Preference para la misma clase, el que se carga último gana y el otro se ignora completamente.

```xml
<!-- Módulo A -->
<preference for="Magento\Catalog\Model\Product"
            type="VendorA\ModuloA\Model\Product"/>

<!-- Módulo B — instalado después -->
<preference for="Magento\Catalog\Model\Product"
            type="VendorB\ModuloB\Model\Product"/>
```

```
Resultado: VendorB\ModuloB\Model\Product gana
           VendorA\ModuloA\Model\Product se ignora completamente
           → Las customizaciones de Módulo A se pierden silenciosamente
```

Por eso los Plugins son casi siempre la mejor opción para modificar comportamiento del core — permiten que múltiples módulos coexistan. Los Preferences en clases concretas están considerados **anti-pattern** salvo casos muy específicos.

---

## Cuándo SÍ usar Preference

```
✅ Mapear interfaces propias a implementaciones (PostRepositoryInterface → PostRepository)
✅ Implementar una interface del core con tu propia clase
✅ Reemplazar una clase del core cuando:
   - No hay eventos ni plugins disponibles para lo que necesitas
   - Necesitas cambiar el tipo de retorno o la firma del método
   - Es una clase que ningún otro módulo instalado sobreescribe
   - Controlas todo el stack (proyecto interno, sin módulos de terceros)
```

## Cuándo NO usar Preference

```
❌ Para añadir lógica antes/después de un método → usa Plugin
❌ Para modificar el resultado de un método → usa Plugin (around)
❌ Para reaccionar a un evento de negocio → usa Observer
❌ Si puede haber conflicto con otros módulos → usa Plugin
❌ En marketplaces o módulos distribuibles → casi nunca
```

## Preference para implementar una interface del core

Caso correcto: Magento define una interfaz y espera que los módulos la implementen:

```php
// Tu implementación de una interface del core
namespace MiVendor\Shipping\Model\Carrier;

use Magento\Shipping\Model\Carrier\AbstractCarrier;
use Magento\Shipping\Model\Carrier\CarrierInterface;

class MiTransportista extends AbstractCarrier implements CarrierInterface
{
    protected $_code = 'mitransportista';

    public function collectRates(
        \Magento\Quote\Model\Quote\Address\RateRequest $request
    ): ?\Magento\Shipping\Model\Rate\Result {
        $result = $this->_rateResultFactory->create();
        $method = $this->_rateMethodFactory->create();

        $method->setCarrier($this->_code);
        $method->setCarrierTitle($this->getConfigData('title'));
        $method->setMethod('standard');
        $method->setMethodTitle('Envío Estándar');
        $method->setPrice(50.00);
        $method->setCost(50.00);

        $result->append($method);
        return $result;
    }

    public function getAllowedMethods(): array
    {
        return ['standard' => 'Envío Estándar'];
    }
}
```

```xml
<preference for="Magento\Shipping\Model\Carrier\CarrierInterface"
            type="MiVendor\Shipping\Model\Carrier\MiTransportista"/>
```

## Preference + Plugin: el patrón correcto

Cuando sí necesitas un Preference para una clase concreta, combínalo con Plugin para que otros módulos puedan seguir extendiendo:

```php
// Tu clase con Preference
namespace MiVendor\MiModulo\Model;

class ProductRepository extends \Magento\Catalog\Model\ProductRepository
{
    public function getById($productId, $editMode = false, $storeId = null, $forceReload = false)
    {
        $product = parent::getById($productId, $editMode, $storeId, $forceReload);

        // Tu lógica custom que NO puede ir en un Plugin
        // (porque necesitas acceso a estado interno privado del padre)
        $this->enriquecerConDatosExternos($product);

        return $product;
    }
}
```

Los Plugins de otros módulos sobre `ProductRepository` siguen funcionando porque actúan sobre la interfaz, no sobre la clase concreta.

## Verificar qué Preference está activo

```bash
# Ver la preference configurada para una clase/interfaz
php bin/magento dev:di:info "Magento\Catalog\Model\Product"

# Output:
# DI configuration for the class Magento\Catalog\Model\Product
# Preference: MiVendor\MiModulo\Model\Product   ← aquí ves cuál ganó

# Ver todos los preferences definidos en un di.xml específico:
grep -r "preference" app/code/MiVendor/ --include="di.xml"
```

---

## Resumen

```
Preference = reemplazo global de una clase/interface en todo el sistema

✅ Uso correcto:
   Interface → Implementación propia (Service Contracts)
   Clase del core → Solo cuando Plugin no es suficiente

❌ Problema:
   Solo un Preference por clase — conflicto con otros módulos
   Solución preferida: Plugin (coexisten múltiples)

Sintaxis:
<preference for="Clase\O\Interface\Original"
            type="Tu\Clase\Reemplazo"/>

Tu clase debe:
  - Extender la clase original (si reemplazas clase concreta)
  - Implementar la interface (si reemplazas interface)
  - Mantener compatibilidad de firma de métodos públicos
```
