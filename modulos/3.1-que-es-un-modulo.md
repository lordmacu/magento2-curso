# 3.1 — ¿Qué es un Módulo? Anatomía y Convenciones

> **Objetivo**: Entender qué es exactamente un módulo en Magento, cuál es su estructura mínima, cómo se registra y por qué todo en Magento funciona así.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [2.5 — Composer en Magento](2.5-composer.md)

---

## El módulo es la unidad fundamental

🔄 **Laravel**: El código se organiza en `app/Http/Controllers`, `app/Models`, `app/Services`... todo en un solo espacio. Si instalas un paquete, va a `vendor/` pero se integra vía Service Providers.

En Magento **no existe "la app"** como unidad. Todo es un módulo — el catálogo, el checkout, el carrito, la autenticación, la búsqueda. Son 200+ módulos del core, más los tuyos. Cada módulo es completamente autocontenido: tiene su propio routing, sus propias rutas de DB, sus propios templates, su propio DI.

```
Magento no es "una aplicación con módulos"
Magento es "una colección de módulos que juntos forman una aplicación"
```

## Anatomía de un módulo

Un módulo mínimo necesita solo dos archivos:

```
app/code/MiVendor/MiModulo/
├── registration.php      ← Le dice a Magento que este módulo existe
└── etc/
    └── module.xml        ← Nombre, versión y dependencias
```

Un módulo completo (con todas las capacidades):

```
app/code/MiVendor/MiModulo/
│
├── registration.php              ← Registro obligatorio
│
├── etc/
│   ├── module.xml                ← Metadatos del módulo
│   ├── di.xml                    ← Inyección de dependencias (global)
│   ├── config.xml                ← Valores de configuración por defecto
│   ├── acl.xml                   ← Permisos de admin
│   ├── crontab.xml               ← Cron jobs
│   ├── frontend/
│   │   ├── di.xml                ← DI solo para el área frontend
│   │   ├── routes.xml            ← URLs del frontend
│   │   └── events.xml            ← Observers del frontend
│   ├── adminhtml/
│   │   ├── di.xml                ← DI solo para el área admin
│   │   ├── routes.xml            ← URLs del admin
│   │   ├── events.xml            ← Observers del admin
│   │   └── system.xml            ← Configuración en el panel de admin
│   └── webapi.xml                ← Endpoints REST/SOAP
│
├── Api/                          ← Service Contracts (interfaces públicas)
│   ├── ProductoRepositoryInterface.php
│   └── Data/
│       └── ProductoInterface.php
│
├── Model/                        ← Lógica de negocio y persistencia
│   ├── Producto.php              ← Model (ORM)
│   ├── ResourceModel/
│   │   ├── Producto.php          ← Acceso a base de datos
│   │   └── Producto/
│   │       └── Collection.php    ← Colecciones (queries múltiples)
│   └── ProductoRepository.php   ← Implementación del Repository
│
├── Controller/                   ← Controllers del frontend
│   └── Post/
│       └── View.php
│
├── Console/                      ← Comandos CLI
│   └── Command/
│       └── SincronizarCommand.php
│
├── Observer/                     ← Observers de eventos
│   └── ProcesarPedido.php
│
├── Plugin/                       ← Plugins (interceptors)
│   └── ProductPlugin.php
│
├── Block/                        ← Blocks (lógica de presentación)
│   └── Post/
│       └── View.php
│
├── ViewModel/                    ← ViewModels (alternativa moderna a Block)
│   └── PostViewModel.php
│
├── Helper/                       ← Helpers (uso minimal, preferir ViewModel)
│   └── Data.php
│
├── Setup/                        ← Migraciones de base de datos
│   ├── InstallSchema.php         ← (legacy)
│   └── Patch/
│       ├── Data/
│       │   └── InsertDefaultData.php
│       └── Schema/
│           └── CreateProductoTable.php
│
├── view/
│   ├── frontend/
│   │   ├── layout/               ← Layout XML del frontend
│   │   │   └── blog_post_view.xml
│   │   ├── templates/            ← Templates .phtml
│   │   │   └── post/
│   │   │       └── view.phtml
│   │   └── web/
│   │       ├── css/              ← CSS/LESS del módulo
│   │       ├── js/               ← JavaScript
│   │       └── images/
│   └── adminhtml/
│       ├── layout/
│       ├── templates/
│       └── ui_component/         ← UI Components del admin
│
├── i18n/                         ← Traducciones
│   ├── es_MX.csv
│   └── en_US.csv
│
└── composer.json                 ← Si se distribuye como paquete Composer
```

## Los dos archivos obligatorios

### registration.php

```php
<?php
// app/code/MiVendor/MiModulo/registration.php

use Magento\Framework\Component\ComponentRegistrar;

ComponentRegistrar::register(
    ComponentRegistrar::MODULE,    // tipo: MODULE, THEME, LANGUAGE, LIBRARY
    'MiVendor_MiModulo',           // nombre del módulo: Vendor_Nombre
    __DIR__                        // directorio raíz del módulo
);
```

Este archivo es incluido automáticamente por Composer gracias a:
```json
// composer.json del proyecto
"autoload": {
    "files": ["app/etc/NonComposerComponentRegistration.php"]
}
```

`NonComposerComponentRegistration.php` hace un `glob` de todos los `registration.php` en `app/code/` y los incluye.

### module.xml

```xml
<?xml version="1.0"?>
<!-- app/code/MiVendor/MiModulo/etc/module.xml -->
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:Module/etc/module.xsd">

    <module name="MiVendor_MiModulo" setup_version="1.0.0">
        <sequence>
            <!-- Módulos que deben cargarse ANTES que el tuyo -->
            <module name="Magento_Catalog"/>
            <module name="Magento_Customer"/>
        </sequence>
    </module>

</config>
```

`setup_version` es la versión para el sistema de migraciones. Se incrementa cuando cambias el schema de la DB.

## Convenciones de nomenclatura

### Nombre del módulo

```
{Vendor}_{NombreModulo}

✅ Correcto:
MiEmpresa_Catalogo
Magento_Checkout
Amasty_SpecialPromo

❌ Incorrecto:
miempresa_catalogo         (minúsculas)
MiEmpresaCatalogo          (sin guión bajo)
Mi_Empresa_Catalogo        (más de un guión bajo en Vendor)
```

### Namespace PHP

```php
// El namespace sigue exactamente la estructura de directorios:
// app/code/MiVendor/MiModulo/Model/Producto.php
namespace MiVendor\MiModulo\Model;
```

### Nombres de clases

```
Model\Producto              ← Entidad principal
Model\ResourceModel\Producto ← Acceso a DB
Model\ResourceModel\Producto\Collection ← Colección
Model\ProductoRepository    ← Repository
Api\ProductoRepositoryInterface ← Service Contract
Api\Data\ProductoInterface  ← Data Object Interface
Controller\Post\View        ← Controller (ruta: /post/view)
Plugin\ProductPlugin        ← Plugin
Observer\NombreObserver     ← Observer
Console\Command\NombreCommand ← CLI Command
Block\NombreBlock           ← Block
ViewModel\NombreViewModel   ← ViewModel
Setup\Patch\Data\NombrePatch ← Data Patch
Setup\Patch\Schema\NombrePatch ← Schema Patch
```

## El ciclo de vida de un módulo

```
1. registration.php se carga → Magento sabe que existe

2. app/etc/config.php se lee → ¿está habilitado? (1 = sí, 0 = no)

3. etc/module.xml se lee → versión, dependencias (sequence)

4. setup:upgrade se corre → aplica Setup/Patch/* si hay nuevos

5. etc/di.xml se lee → se registran preferences, plugins, observers

6. El módulo está activo y funcional
```

## Habilitar y verificar un módulo

```bash
# Habilitar
php bin/magento module:enable MiVendor_MiModulo

# Qué hace internamente:
# 1. Agrega 'MiVendor_MiModulo' => 1 en app/etc/config.php
# 2. Nada más — hasta que corras setup:upgrade

# Aplicar (obligatorio después de habilitar)
php bin/magento setup:upgrade
php bin/magento cache:flush

# Verificar que está activo
php bin/magento module:status MiVendor_MiModulo
# MiVendor_MiModulo : Module is enabled

# Ver la versión instalada
php bin/magento module:status --enabled | grep MiVendor
```

## Módulos del core como referencia

Cuando necesites implementar algo, busca cómo lo hace el core de Magento:

```bash
# Módulos más simples y bien estructurados para estudiar:
vendor/magento/module-store/           # Stores, websites, store views
vendor/magento/module-cms/             # Páginas y bloques CMS
vendor/magento/module-contact/         # Formulario de contacto — muy simple
vendor/magento/module-newsletter/      # Suscripciones — patrón completo
vendor/magento/module-catalog/         # El más complejo — para cuando ya sepas más
```

```bash
# Buscar cómo implementa Magento algo específico:
grep -r "CommandList" vendor/magento/framework/Console/ --include="*.php" -l
grep -r "registration.php" vendor/magento/ --include="*.php" -l | head -5
```

## Resumen

```
Módulo mínimo:
  registration.php  →  registra el módulo en Magento
  etc/module.xml    →  nombre, versión, dependencias

Convención de nombre:  Vendor_Nombre  (PascalCase, un guión bajo)
Namespace PHP:         Vendor\Nombre\  (sigue la estructura de carpetas)

Para activar:
  module:enable Vendor_Nombre
  setup:upgrade
  cache:flush
```

## Ejercicios

### Ejercicio 1 — Inspeccionar un módulo del core

Examina el módulo `Magento_Contact` (el formulario de contacto) — es uno de los más simples del core. Identifica: qué archivos tiene, qué hace cada uno y cuál es su estructura.

<details>
<summary>Ver solución</summary>

```bash
# Ver la estructura completa del módulo Contact
ls vendor/magento/module-contact/

# Output esperado:
# Block/         Controller/    Model/         etc/
# Test/          composer.json  registration.php  view/

# Los archivos obligatorios:
cat vendor/magento/module-contact/registration.php
cat vendor/magento/module-contact/etc/module.xml

# Ver sus dependencias (sequence):
grep -A5 "<sequence>" vendor/magento/module-contact/etc/module.xml

# Ver sus routes (URLs que registra):
cat vendor/magento/module-contact/etc/frontend/routes.xml
# → registra la ruta /contact

# Ver su Controller principal:
ls vendor/magento/module-contact/Controller/
# Index/    Post/

# Ver la configuración por defecto:
cat vendor/magento/module-contact/etc/config.xml
# → enabled = 1 por defecto
```

**Lo que deberías ver**:
- `registration.php` registra el módulo como `Magento_Contact`
- `module.xml` declara dependencias de `Magento_Cms`, `Magento_Customer`, etc.
- `etc/frontend/routes.xml` registra la URL `/contact`
- `Controller/Index/Index.php` renderiza el formulario
- `Controller/Post/Post.php` procesa el envío
- `etc/config.xml` tiene `<enabled>1</enabled>` como default

</details>

### Ejercicio 2 — Crear los archivos mínimos de un módulo

Crea la estructura mínima para un módulo `MiVendor_Prueba` — solo los dos archivos obligatorios — y verifícalo.

<details>
<summary>Ver solución</summary>

```bash
# Crear la estructura de directorios
mkdir -p app/code/MiVendor/Prueba/etc
```

```php
<?php
// app/code/MiVendor/Prueba/registration.php
use Magento\Framework\Component\ComponentRegistrar;

ComponentRegistrar::register(
    ComponentRegistrar::MODULE,
    'MiVendor_Prueba',
    __DIR__
);
```

```xml
<?xml version="1.0"?>
<!-- app/code/MiVendor/Prueba/etc/module.xml -->
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:Module/etc/module.xsd">
    <module name="MiVendor_Prueba" setup_version="1.0.0"/>
</config>
```

```bash
# Habilitar y verificar
php bin/magento module:enable MiVendor_Prueba
php bin/magento setup:upgrade
php bin/magento cache:flush

# Verificar que está activo
php bin/magento module:status MiVendor_Prueba
# → MiVendor_Prueba : Module is enabled
```

Con solo estos dos archivos, el módulo está registrado y activo. Puedes agregar `di.xml`, controllers, models, etc. según necesites.

</details>
