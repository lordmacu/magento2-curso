# 6.2 — events.xml: Registrar y Configurar Observers

> **Objetivo**: Dominar el archivo `events.xml` — su sintaxis completa, las opciones de configuración disponibles y los patrones de uso más comunes.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [6.1 — Events y Observers](6.1-events-overview.md)

---

## Estructura básica

```xml
<?xml version="1.0"?>
<!-- app/code/MiVendor/Blog/etc/events.xml -->
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:Event/etc/events.xsd">

    <event name="nombre_del_evento">
        <observer name="identificador_unico"
                  instance="MiVendor\Blog\Observer\MiObserver"/>
    </event>

</config>
```

---

## Atributos del `<observer>`

```xml
<observer
    name="identificador_unico"       <!-- Obligatorio: único en todo el sistema -->
    instance="Vendor\Module\Observer\ClaseObserver"  <!-- Obligatorio: clase PHP -->
    method="execute"                 <!-- Opcional: método a llamar (default: execute) -->
    disabled="false"                 <!-- Opcional: deshabilitar sin eliminar -->
    shared="true"                    <!-- Opcional: singleton (default: true) -->
/>
```

### `name` — identificador único global

```xml
<!-- Convención: {vendor}_{module}_{descripcion} -->
<observer name="mivendor_blog_send_order_confirmation"
          instance="MiVendor\Blog\Observer\SendOrderConfirmation"/>

<!-- ❌ Muy genérico — puede colisionar con otro módulo -->
<observer name="order_observer"
          instance="..."/>
```

### `method` — método custom (raramente necesario)

```xml
<!-- Por defecto Magento llama execute() — casi nunca cambies esto -->
<observer name="mivendor_blog_custom"
          instance="MiVendor\Blog\Observer\MultiEventObserver"
          method="handleOrderPlaced"/>
```

### `disabled` — deshabilitar observers externos

```xml
<!-- Deshabilitar un observer del core sin modificarlo -->
<event name="sales_order_place_after">
    <observer name="magento_analytics_order_observer" disabled="true"/>
</event>
```

### `shared` — instancia compartida

```xml
<!-- shared=false → nueva instancia del Observer por cada dispatch -->
<observer name="mivendor_blog_stateful_observer"
          instance="MiVendor\Blog\Observer\StatefulObserver"
          shared="false"/>
```

Úsalo cuando el Observer guarda estado entre llamadas y no quieres que se comparta.

---

## Múltiples observers por evento

Puedes registrar tantos observers como necesites para el mismo evento. Se ejecutan en el orden en que aparecen en los archivos `events.xml` de todos los módulos (según `sequence` del módulo).

```xml
<event name="catalog_product_save_after">
    <observer name="mivendor_blog_reindex_search"
              instance="MiVendor\Blog\Observer\ReindexSearch"/>

    <observer name="mivendor_blog_clear_cache"
              instance="MiVendor\Blog\Observer\ClearProductCache"/>

    <observer name="mivendor_blog_notify_erp"
              instance="MiVendor\Blog\Observer\NotifyErp"/>
</event>
```

---

## Múltiples eventos en un archivo

```xml
<config>
    <!-- Evento de guardado de producto -->
    <event name="catalog_product_save_after">
        <observer name="mivendor_blog_product_saved"
                  instance="MiVendor\Blog\Observer\ProductSaved"/>
    </event>

    <!-- Evento de eliminación de producto -->
    <event name="catalog_product_delete_after">
        <observer name="mivendor_blog_product_deleted"
                  instance="MiVendor\Blog\Observer\ProductDeleted"/>
    </event>

    <!-- Evento de pedido completado -->
    <event name="sales_order_place_after">
        <observer name="mivendor_blog_order_placed"
                  instance="MiVendor\Blog\Observer\OrderPlaced"/>
    </event>
</config>
```

---

## Un Observer para múltiples eventos

Un mismo Observer puede escuchar múltiples eventos registrándolo en cada uno:

```xml
<event name="catalog_product_save_after">
    <observer name="mivendor_blog_product_changed_save"
              instance="MiVendor\Blog\Observer\ProductChanged"/>
</event>

<event name="catalog_product_import_finish_after">
    <observer name="mivendor_blog_product_changed_import"
              instance="MiVendor\Blog\Observer\ProductChanged"/>
</event>
```

```php
// El mismo Observer maneja ambos eventos
class ProductChanged implements ObserverInterface
{
    public function execute(Observer $observer): void
    {
        // getData() funciona para ambos eventos
        // aunque los datos disponibles pueden variar
        $product = $observer->getEvent()->getProduct();
        $this->processChange($product);
    }
}
```

## events.xml por área

Elige el área correcta según cuándo debe ejecutarse el observer:

```
etc/events.xml            → CLI, cron, todos los contextos
etc/frontend/events.xml   → Solo requests del frontend (tienda)
etc/adminhtml/events.xml  → Solo requests del panel admin
etc/webapi_rest/events.xml → Solo requests REST API
```

### Ejemplo práctico

```xml
<!-- etc/frontend/events.xml — tracking de visitas, solo frontend -->
<event name="catalog_product_view_load_before">
    <observer name="mivendor_blog_track_product_view"
              instance="MiVendor\Blog\Observer\TrackProductView"/>
</event>
```

```xml
<!-- etc/adminhtml/events.xml — auditoría de cambios, solo admin -->
<event name="catalog_product_save_after">
    <observer name="mivendor_blog_audit_product_change"
              instance="MiVendor\Blog\Observer\AuditProductChange"/>
</event>
```

```xml
<!-- etc/events.xml — sincronización con ERP, todos los contextos -->
<event name="sales_order_place_after">
    <observer name="mivendor_blog_sync_order_erp"
              instance="MiVendor\Blog\Observer\SyncOrderWithErp"/>
</event>
```

## Validar el events.xml

```bash
# Magento valida contra el XSD al limpiar caché
php bin/magento cache:flush

# Si hay error de sintaxis XML verás:
# [ERROR] Invalid Document: etc/events.xml

# Validar manualmente con xmllint:
xmllint --noout --schema vendor/magento/framework/Event/etc/events.xsd \
    app/code/MiVendor/Blog/etc/events.xml
```

## Buscar observers registrados para un evento

```bash
# Buscar todos los observers de un evento en todo el proyecto
grep -r "sales_order_place_after" \
    app/code/ vendor/magento/ \
    --include="events.xml" -l

# Ver el detalle de cada archivo encontrado
grep -r -A3 "sales_order_place_after" \
    app/code/ vendor/magento/ \
    --include="events.xml"
```

## Errores comunes

### Observer no se ejecuta

```bash
# Causa 1: caché de configuración
php bin/magento cache:flush

# Causa 2: el área no coincide
# Si registraste en etc/frontend/events.xml pero el dispatch ocurre en CLI → no se ejecuta

# Causa 3: el nombre del evento está mal escrito
# Magento no da error si un evento no tiene observers — simplemente no pasa nada
grep -r "nombre_evento" vendor/magento/ --include="*.php" | grep "dispatch("
```

### Nombre de observer duplicado

```
[ERROR] Observer "mivendor_blog_observer" already exists for event "catalog_product_save_after"
```

El `name` del observer debe ser único globalmente entre todos los módulos para el mismo evento. Usa el prefijo `{vendor}_{module}_` para evitar colisiones.

---

## Resumen

```xml
<!-- Estructura completa -->
<config>
    <event name="nombre_evento">
        <observer
            name="vendor_module_descripcion"     <!-- único global -->
            instance="Vendor\Module\Observer\Clase"
            method="execute"                     <!-- opcional, default: execute -->
            disabled="false"                     <!-- para deshabilitar externos -->
            shared="true"                        <!-- default: singleton -->
        />
    </event>
</config>
```

```
Ubicación según área:
  etc/events.xml           → global (CLI, cron, todos)
  etc/frontend/events.xml  → solo tienda
  etc/adminhtml/events.xml → solo admin
  etc/webapi_rest/events.xml → solo API REST

Deshabilitar observer externo:
  <observer name="nombre_exacto" disabled="true"/>

Buscar observers de un evento:
  grep -r "nombre_evento" app/code/ vendor/magento/ --include="events.xml"
```

## Ejercicios

### Ejercicio 1 — Registrar observers por área correctamente

Tienes estos tres requisitos. Para cada uno, indica en qué archivo `events.xml` debe ir el registro y por qué.

1. Un observer que trackea visitas a páginas de producto para analytics — solo cuando un cliente visita la tienda.
2. Un observer que audita cambios a productos — solo cuando un admin edita productos desde el panel.
3. Un observer que sincroniza pedidos con un ERP externo — debe ejecutarse sin importar el origen (frontend, admin o API REST).

<details>
<summary>Ver solución</summary>

```xml
<!-- 1. etc/frontend/events.xml — SOLO en el área frontend (tienda) -->
<!-- Razón: Las visitas de clientes solo ocurren en el frontend.
     Si se pusiera en etc/events.xml, también se dispararía en el admin
     cuando un administrador previsualiza un producto, contaminando las estadísticas. -->
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:Event/etc/events.xsd">
    <event name="catalog_product_view_load_before">
        <observer name="mivendor_blog_track_product_visit"
                  instance="MiVendor\Blog\Observer\TrackProductVisit"/>
    </event>
</config>
```

```xml
<!-- 2. etc/adminhtml/events.xml — SOLO en el área admin -->
<!-- Razón: La auditoría de cambios hechos por admins solo tiene sentido
     cuando el contexto es el panel de administración.
     Si se pusiera en global, también auditaría actualizaciones
     de productos vía API (importaciones, actualizaciones batch). -->
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:Event/etc/events.xsd">
    <event name="catalog_product_save_after">
        <observer name="mivendor_blog_audit_admin_product_change"
                  instance="MiVendor\Blog\Observer\AuditAdminProductChange"/>
    </event>
</config>
```

```xml
<!-- 3. etc/events.xml — GLOBAL (todos los contextos) -->
<!-- Razón: Los pedidos pueden crearse desde el frontend, desde el admin
     (órdenes manuales) o vía REST API (integraciones). La sincronización
     con el ERP debe ocurrir siempre, independientemente del origen. -->
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:Event/etc/events.xsd">
    <event name="sales_order_place_after">
        <observer name="mivendor_blog_sync_order_erp"
                  instance="MiVendor\Blog\Observer\SyncOrderWithErp"/>
    </event>
</config>
```

</details>

### Ejercicio 2 — Deshabilitar un observer del core sin modificarlo

El observer `magento_analytics_order_observer` del módulo `Magento_Analytics` genera peticiones HTTP salientes en cada pedido. En tu entorno de staging quieres deshabilitarlo. Escribe el `events.xml` correcto.

<details>
<summary>Ver solución</summary>

```bash
# Primero: encontrar el nombre exacto del observer y el evento al que está registrado
grep -r "magento_analytics" vendor/magento/module-analytics/etc/ --include="events.xml" -A2

# Output ejemplo:
# <event name="sales_order_place_after">
#     <observer name="magento_analytics_order_observer" instance="..."/>
# </event>
```

```xml
<!-- app/code/MiVendor/MiModulo/etc/events.xml -->
<?xml version="1.0"?>
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:Event/etc/events.xsd">

    <event name="sales_order_place_after">
        <!-- disabled="true" desactiva el observer sin modificar el código del módulo original -->
        <observer name="magento_analytics_order_observer" disabled="true"/>
    </event>

</config>
```

```bash
php bin/magento cache:flush

# Verificar que ya no está activo:
grep -r "magento_analytics_order_observer" \
    app/code/ vendor/magento/ --include="events.xml" | grep "disabled"
# → deberías ver tu línea con disabled="true"
```

**Notas importantes**:
- Si usas `etc/events.xml` global, deshabilita el observer en todos los contextos
- Si quieres deshabilitarlo solo en staging vs producción, debes gestionar esto a nivel de deploy (feature flags en config.php o env.php)
- El `name` debe ser **exactamente igual** al original — si está mal escrito, Magento no da error y el observer sigue activo

</details>
