## El problema con los Blocks "fat"

Antes de ViewModels, la lógica de presentación iba en el Block. Esto creaba Blocks pesados con decenas de dependencias:

```php
// ❌ Block "fat" — demasiadas responsabilidades
class ProductView extends Template
{
    public function __construct(
        Context $context,
        ProductRepositoryInterface $productRepository,
        PriceCurrencyInterface $priceCurrency,
        ReviewFactory $reviewFactory,
        StockRegistryInterface $stockRegistry,
        InventoryReservations $inventoryReservations,
        RelatedProductsBlock $relatedBlock,
        // ... 15 dependencias más
        array $data = []
    ) { ... }
}
```

**El problema**: El Block hereda de `Template` (que ya tiene Context con ~20 servicios). Cada dependencia adicional hace el constructor más pesado y el testing más difícil.

🔄 **Laravel**: Similar a los View Composers — clases independientes que preparan datos para las vistas.

---

## ViewModels: la solución

Un ViewModel es una clase PHP simple que:
- No hereda de nada especial (solo implementa `ArgumentInterface`)
- Contiene la lógica de presentación
- Se inyecta en el Block (o directamente en el template) desde el layout XML

```php
<?php
// Block/Post/ViewModel/PostData.php
namespace MiVendor\Blog\Block\Post\ViewModel;

use Magento\Framework\View\Element\Block\ArgumentInterface;
use MiVendor\Blog\Api\PostRepositoryInterface;
use Magento\Framework\App\RequestInterface;

class PostData implements ArgumentInterface
{
    public function __construct(
        private readonly PostRepositoryInterface $postRepository,
        private readonly RequestInterface $request
    ) {}

    public function getPost(): ?\MiVendor\Blog\Api\Data\PostInterface
    {
        $postId = (int) $this->request->getParam('id');
        try {
            return $this->postRepository->getById($postId);
        } catch (\Magento\Framework\Exception\NoSuchEntityException $e) {
            return null;
        }
    }

    public function getPostUrl(\MiVendor\Blog\Api\Data\PostInterface $post): string
    {
        return '/blog/' . $post->getUrlKey();
    }

    public function formatPublishedDate(\MiVendor\Blog\Api\Data\PostInterface $post): string
    {
        return (new \DateTime($post->getCreatedAt()))->format('d \d\e F, Y');
    }
}
```

---

## Registrar el ViewModel en el layout XML

```xml
<!-- view/frontend/layout/blog_post_view.xml -->
<block class="Magento\Framework\View\Element\Template"
       name="blog.post.view"
       template="MiVendor_Blog::post/view.phtml">
    <arguments>
        <argument name="view_model"
                  xsi:type="object">MiVendor\Blog\Block\Post\ViewModel\PostData</argument>
    </arguments>
</block>
```

---

## Usar el ViewModel en el template

```php
<?php
/** @var \Magento\Framework\View\Element\Template $block */
/** @var \MiVendor\Blog\Block\Post\ViewModel\PostData $viewModel */
$viewModel = $block->getData('view_model');
$post = $viewModel->getPost();
?>

<?php if ($post): ?>
<article class="blog-post">
    <h1><?= $block->escapeHtml($post->getTitle()) ?></h1>

    <time><?= $block->escapeHtml($viewModel->formatPublishedDate($post)) ?></time>

    <div class="post-content">
        <?= /* @noEscape */ $post->getContent() ?>
    </div>

    <a href="<?= $block->escapeUrl($viewModel->getPostUrl($post)) ?>">
        <?= $block->escapeHtml(__('Read more')) ?>
    </a>
</article>
<?php endif; ?>
```

**El Block puede ser `Magento\Framework\View\Element\Template`** directamente — no necesitas crear una clase Block propia si toda la lógica está en el ViewModel.

## ViewModel vs Block: cuándo usar cada uno

```
Block (con clase PHP):
  ✅ Cuando necesitas ciclo de vida (_prepareLayout, _beforeToHtml)
  ✅ Cuando necesitas agregar hijos dinámicamente
  ✅ Cuando necesitas caché de block configurable
  ✅ Cuando el block se reutiliza en muchos lugares y tiene lógica compleja

ViewModel:
  ✅ La forma moderna para la mayoría de los casos
  ✅ Lógica de presentación sencilla
  ✅ Un template necesita datos de múltiples fuentes
  ✅ Testing más fácil (no depende del contexto de layout)
  ✅ Reutilizable en múltiples blocks/templates
```

---

## ViewModel compartido entre templates

El mismo ViewModel puede usarse en varios blocks — Magento lo instancia como singleton:

```xml
<!-- En homepage: últimos 3 posts -->
<block class="Magento\Framework\View\Element\Template"
       name="blog.homepage.recent"
       template="MiVendor_Blog::homepage/recent-posts.phtml">
    <arguments>
        <argument name="view_model" xsi:type="object">
            MiVendor\Blog\ViewModel\RecentPosts
        </argument>
        <argument name="limit" xsi:type="number">3</argument>
    </arguments>
</block>

<!-- En sidebar: últimos 5 posts -->
<block class="Magento\Framework\View\Element\Template"
       name="blog.sidebar.recent"
       template="MiVendor_Blog::sidebar/recent-posts.phtml">
    <arguments>
        <argument name="view_model" xsi:type="object">
            MiVendor\Blog\ViewModel\RecentPosts
        </argument>
        <argument name="limit" xsi:type="number">5</argument>
    </arguments>
</block>
```

```php
// El ViewModel lee el limit del block:
class RecentPosts implements ArgumentInterface
{
    public function getPosts(int $limit): array
    {
        // ...
    }
}
```

```php
// En el template — lee limit del $block y lo pasa al ViewModel:
$viewModel = $block->getData('view_model');
$limit = (int) $block->getData('limit');
$posts = $viewModel->getPosts($limit);
```

## Testing de ViewModels

Uno de los grandes beneficios: los ViewModels son clases PHP puras, fáciles de testear:

```php
// Test/Unit/ViewModel/PostDataTest.php
class PostDataTest extends \PHPUnit\Framework\TestCase
{
    public function testGetPostReturnsNullWhenNotFound(): void
    {
        $postRepository = $this->createMock(PostRepositoryInterface::class);
        $postRepository->method('getById')
            ->willThrowException(new NoSuchEntityException());

        $request = $this->createMock(RequestInterface::class);
        $request->method('getParam')->willReturn('999');

        $viewModel = new PostData($postRepository, $request);
        $this->assertNull($viewModel->getPost());
    }
}
```

Con un Block tradicional necesitarías mockear el `Context` completo — mucho más complejo.

---

## Resumen

```
ViewModel = clase PHP simple que implementa ArgumentInterface
No hereda de Template — sin Context, sin complejidad del Block

Registrar en XML:
  <argument name="view_model" xsi:type="object">VendorModule\ViewModel\MiViewModel</argument>

Usar en template:
  $viewModel = $block->getData('view_model');

Ventajas:
  - Separación de responsabilidades limpia
  - Testeable sin mockear el layout
  - Reutilizable en múltiples templates
  - El Block puede ser Template genérico (sin clase propia)
```

## Ejercicios

### Ejercicio 1 — ViewModel para datos de configuración

Crea `MiVendor\Blog\ViewModel\BlogConfig` que exponga configuración del módulo leída de `ScopeConfigInterface`:
- `isEnabled()` → `mivendor_blog/general/enabled`
- `getPostsPerPage()` → `mivendor_blog/general/posts_per_page`
- `isSeoEnabled()` → `mivendor_blog/seo/canonical_enabled`

<details>
<summary>Ver solución</summary>

```php
<?php
namespace MiVendor\Blog\ViewModel;

use Magento\Framework\View\Element\Block\ArgumentInterface;
use Magento\Framework\App\Config\ScopeConfigInterface;
use Magento\Store\Model\ScopeInterface;

class BlogConfig implements ArgumentInterface
{
    public function __construct(
        private readonly ScopeConfigInterface $scopeConfig
    ) {}

    public function isEnabled(): bool
    {
        return $this->scopeConfig->isSetFlag(
            'mivendor_blog/general/enabled',
            ScopeInterface::SCOPE_STORE
        );
    }

    public function getPostsPerPage(): int
    {
        return (int) $this->scopeConfig->getValue(
            'mivendor_blog/general/posts_per_page',
            ScopeInterface::SCOPE_STORE
        ) ?: 10;
    }

    public function isSeoEnabled(): bool
    {
        return $this->scopeConfig->isSetFlag(
            'mivendor_blog/seo/canonical_enabled',
            ScopeInterface::SCOPE_STORE
        );
    }
}
```

```xml
<!-- En el layout XML donde necesitas la configuración -->
<block class="Magento\Framework\View\Element\Template"
       name="blog.index"
       template="MiVendor_Blog::index.phtml">
    <arguments>
        <argument name="blog_config" xsi:type="object">
            MiVendor\Blog\ViewModel\BlogConfig
        </argument>
    </arguments>
</block>
```

```php
<?php
/** @var \Magento\Framework\View\Element\Template $block */
/** @var \MiVendor\Blog\ViewModel\BlogConfig $blogConfig */
$blogConfig = $block->getData('blog_config');
?>

<?php if (!$blogConfig->isEnabled()): ?>
    <p><?= $block->escapeHtml(__('Blog is currently disabled.')) ?></p>
<?php else: ?>
    <!-- contenido del blog -->
    <?php if ($blogConfig->isSeoEnabled()): ?>
        <link rel="canonical" href="...">
    <?php endif; ?>
<?php endif; ?>
```

### Ejercicio 2 — Refactorizar Block a ViewModel

Este Block existente tiene demasiada lógica. Extrae la lógica de datos a un ViewModel y deja el Block como `Magento\Framework\View\Element\Template`.

```php
// Block existente a refactorizar:
class RecentPosts extends Template
{
    public function __construct(
        Context $context,
        private readonly PostRepositoryInterface $postRepository,
        private readonly SearchCriteriaBuilder $searchCriteriaBuilder,
        private readonly SortOrderBuilder $sortOrderBuilder,
        array $data = []
    ) {
        parent::__construct($context, $data);
    }

    public function getRecentPosts(): array
    {
        $sort = $this->sortOrderBuilder->setField('created_at')->setDescendingDirection()->create();
        $criteria = $this->searchCriteriaBuilder
            ->addFilter('is_active', 1)
            ->setSortOrders([$sort])
            ->setPageSize((int) $this->getData('limit') ?: 5)
            ->create();
        return $this->postRepository->getList($criteria)->getItems();
    }
}
```

<details>
<summary>Ver solución</summary>

```php
<?php
// ViewModel/RecentPosts.php
namespace MiVendor\Blog\ViewModel;

use Magento\Framework\View\Element\Block\ArgumentInterface;
use MiVendor\Blog\Api\PostRepositoryInterface;
use Magento\Framework\Api\SearchCriteriaBuilder;
use Magento\Framework\Api\SortOrderBuilder;
use Magento\Framework\Api\SortOrder;

class RecentPosts implements ArgumentInterface
{
    public function __construct(
        private readonly PostRepositoryInterface $postRepository,
        private readonly SearchCriteriaBuilder $searchCriteriaBuilder,
        private readonly SortOrderBuilder $sortOrderBuilder
    ) {}

    public function getPosts(int $limit = 5): array
    {
        $sort = $this->sortOrderBuilder
            ->setField('created_at')
            ->setDirection(SortOrder::SORT_DESC)
            ->create();

        $criteria = $this->searchCriteriaBuilder
            ->addFilter('is_active', 1)
            ->setSortOrders([$sort])
            ->setPageSize($limit)
            ->create();

        return $this->postRepository->getList($criteria)->getItems();
    }
}
```

```xml
<!-- Sin clase Block propia — usar Template genérico -->
<block class="Magento\Framework\View\Element\Template"
       name="blog.recent.posts"
       template="MiVendor_Blog::sidebar/recent-posts.phtml">
    <arguments>
        <argument name="view_model" xsi:type="object">
            MiVendor\Blog\ViewModel\RecentPosts
        </argument>
        <argument name="limit" xsi:type="number">5</argument>
    </arguments>
</block>
```

```php
<?php
// En el template:
$viewModel = $block->getData('view_model');
$limit = (int) $block->getData('limit');
$posts = $viewModel->getPosts($limit);
?>
<?php foreach ($posts as $post): ?>
    <h4><?= $block->escapeHtml($post->getTitle()) ?></h4>
<?php endforeach; ?>
```

**Resultado**: Block eliminado del codebase. El XML puede configurar `limit` sin modificar PHP.

</details>
