# 4.5 — Proxies: Lazy Loading de Dependencias Pesadas

> **Objetivo**: Entender qué son los Proxies en Magento, cuándo usarlos para diferir la inicialización de dependencias costosas y cómo afectan el rendimiento.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [4.4 — Factory Classes](4.4-factory-classes.md)

---

## El problema: dependencias que se construyen aunque no se usen

El DI de Magento construye **todas** las dependencias del constructor al instanciar una clase, aunque nunca se usen en esa request.

```php
class PostController
{
    public function __construct(
        private readonly PdfGenerator     $pdfGenerator,    // ← pesado, conecta a LibreOffice
        private readonly EmailService     $emailService,    // ← pesado, conecta a SMTP
        private readonly PostRepository   $postRepository,  // ← ligero, solo DB
    ) {}

    public function execute(): ResultInterface
    {
        // En el 99% de las requests solo usamos esto:
        $posts = $this->postRepository->getList();

        // PdfGenerator y EmailService se construyeron igual aunque no se usen
        return $this->resultPageFactory->create();
    }
}
```

Si `PdfGenerator` conecta a un servicio externo en su constructor, esa conexión se hace en **cada request**, aunque nunca generes un PDF.

---

## La solución: Proxy

Un Proxy es una clase generada automáticamente que **envuelve** la clase real y la instancia **solo cuando se llama por primera vez** a un método.

```
Sin Proxy:   instanciar PostController  →  instancia PdfGenerator inmediatamente
Con Proxy:   instanciar PostController  →  instancia PdfGenerator\Proxy (ligero)
                                            PdfGenerator\Proxy instancia PdfGenerator real
                                            solo al primer $this->pdfGenerator->generate()
```

---

## Cómo usar un Proxy

Solo agrega `\Proxy` al nombre de la clase en `di.xml`:

```xml
<!-- etc/di.xml -->
<type name="MiVendor\Blog\Controller\Post\Export">
    <arguments>
        <!-- Sin proxy — se instancia inmediatamente -->
        <argument name="postRepository" xsi:type="object">
            MiVendor\Blog\Model\PostRepository
        </argument>

        <!-- Con proxy — se instancia solo cuando se llame al primer método -->
        <argument name="pdfGenerator" xsi:type="object">
            MiVendor\Blog\Service\PdfGenerator\Proxy
        </argument>

        <argument name="emailService" xsi:type="object">
            MiVendor\Blog\Service\EmailService\Proxy
        </argument>
    </arguments>
</type>
```

El código PHP **no cambia** — el type hint sigue siendo la clase original:

```php
class PostController
{
    public function __construct(
        private readonly PostRepository $postRepository,
        private readonly PdfGenerator   $pdfGenerator,   // ← type hint normal
        private readonly EmailService   $emailService,   // ← type hint normal
    ) {}
    // Magento inyecta PdfGenerator\Proxy transparentemente
    // El proxy implementa la misma interfaz — tu código no sabe la diferencia
}
```

---

## Generación automática del Proxy

Magento genera el Proxy automáticamente con `setup:di:compile`:

```bash
php bin/magento setup:di:compile

# Genera:
# generated/code/MiVendor/Blog/Service/PdfGenerator/Proxy.php
```

El código generado se ve así:

```php
// generated/code/MiVendor/Blog/Service/PdfGenerator/Proxy.php
// (no edites este archivo — se regenera siempre)

namespace MiVendor\Blog\Service\PdfGenerator;

class Proxy extends \MiVendor\Blog\Service\PdfGenerator
    implements \Magento\Framework\ObjectManager\NoninterceptableInterface
{
    private ?\MiVendor\Blog\Service\PdfGenerator $subject = null;

    public function __construct(
        private readonly \Magento\Framework\ObjectManagerInterface $objectManager,
        private readonly string $instanceName = \MiVendor\Blog\Service\PdfGenerator::class,
        private readonly bool $shared = true
    ) {
        // No llama al constructor del padre — eso es el punto
    }

    private function getSubject(): \MiVendor\Blog\Service\PdfGenerator
    {
        if ($this->subject === null) {
            // Solo aquí se instancia la clase real (lazy)
            $this->subject = $this->objectManager->get($this->instanceName);
        }
        return $this->subject;
    }

    // Cada método delega al subject real:
    public function generate(array $data): string
    {
        return $this->getSubject()->generate($data);
    }
}
```

---

## Cuándo usar Proxy

```
✅ Usar Proxy cuando:
   - La clase tiene inicialización costosa (conexiones, I/O, carga de librerías)
   - La clase se inyecta en un lugar de alto tráfico pero se usa raramente
   - El constructor hace operaciones que no deberían ocurrir en cada request
   - Tienes dependencias circulares que no puedes resolver de otra forma

❌ NO usar Proxy cuando:
   - La clase es ligera (Repository, Service sin I/O en constructor)
   - Se usa en todas o casi todas las requests
   - Ya usas Factory (Factory ya resuelve el problema de instanciación lazy)
```

---

## Caso real: dependencia circular

Los Proxies son la solución estándar de Magento para dependencias circulares:

```
ClaseA depende de ClaseB
ClaseB depende de ClaseA
→ Error: circular dependency
```

```php
// ClaseA.php
public function __construct(
    private readonly ClaseB $claseB  // ← circular
) {}

// ClaseB.php
public function __construct(
    private readonly ClaseA $claseA  // ← circular
) {}
```

Solución: romper el ciclo con un Proxy en uno de los dos:

```xml
<type name="MiVendor\Blog\Service\ClaseA">
    <arguments>
        <!-- Proxy rompe el ciclo — ClaseB\Proxy no instancia ClaseB en el constructor -->
        <argument name="claseB" xsi:type="object">
            MiVendor\Blog\Service\ClaseB\Proxy
        </argument>
    </arguments>
</type>
```

---

## Proxy vs Factory — cuándo usar cada uno

| | Proxy | Factory |
|---|---|---|
| **Propósito** | Diferir instanciación de singleton | Crear múltiples instancias |
| **Cuántas instancias** | Una (singleton lazy) | Muchas (una por llamada) |
| **Cambio en código PHP** | Ninguno | Inyectar Factory, llamar `create()` |
| **Cambio en di.xml** | Agregar `\Proxy` al type | No necesario (auto-generada) |
| **Cuándo** | Dependencia costosa usada raramente | Model/entidad con estado |

## Verificar que el Proxy funciona

```bash
# Después de setup:di:compile, verificar que se generó:
ls generated/code/MiVendor/Blog/Service/PdfGenerator/
# Proxy.php

# Ver la configuración DI — verás el Proxy en lugar de la clase real:
php bin/magento dev:di:info "MiVendor\Blog\Controller\Post\Export"
# Constructor Parameters:
#   pdfGenerator    MiVendor\Blog\Service\PdfGenerator\Proxy    object
```

---

## Resumen

```
Proxy = clase generada que envuelve otra, instanciando la real solo al primer uso

Cómo usarlo:
  di.xml:  xsi:type="object">MiVendor\Modulo\Service\MiServicio\Proxy
  PHP:     type hint normal — MiServicio (sin \Proxy)

Casos de uso:
  1. Dependencias costosas usadas raramente
  2. Romper dependencias circulares

Generación:
  php bin/magento setup:di:compile
  → generated/code/.../MiServicio/Proxy.php
```
