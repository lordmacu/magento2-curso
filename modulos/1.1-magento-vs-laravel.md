# 1.1 — Magento vs Laravel: Mentalidad y Arquitectura

> **Objetivo**: Entender por qué Magento existe, qué problemas resuelve y cómo cambiar tu mentalidad de Laravel a Magento.
> **Estado**: ⬜ Pendiente

---

## ¿Por qué Magento es tan complejo?

La respuesta corta: **fue diseñado para enterprise, no para startups**.

Laravel fue creado para que los developers fueran felices — convención sobre configuración, código expresivo, curva de aprendizaje suave.

Magento fue creado para que una tienda de Fortune 500 pudiera:
- Tener **múltiples tiendas** en una instalación (multistore)
- Que **cualquier empresa tercera** pueda vender plugins sin romper el core
- Soportar **miles de productos** con atributos dinámicos
- **Reemplazar cualquier clase** del sistema sin modificar el código fuente original

Para lograr eso, Magento sacrificó la simplicidad.

---

## Historia rápida

```
2008 — Magento 1 (Varien) — se vuelve el estándar de ecommerce PHP
2015 — Magento 2 (reescritura total) — adopta patrones modernos: DI, SOLID, PSR
2018 — Adobe compra Magento por $1.68 billones
2020 — Magento 1 llega a end-of-life
2023 — Adobe Commerce (versión enterprise) + Magento Open Source (gratis)
```

Hoy en día, cuando decimos "Magento" nos referimos a **Magento 2 / Adobe Commerce**.

## Comparación Mental: Laravel vs Magento

### Estructura general

| Concepto | Laravel | Magento 2 |
|---|---|---|
| Unidad de extensión | Service Provider | **Módulo** |
| Configuración | `.env` + `config/*.php` | `env.php` + XML + Admin UI |
| ORM | Eloquent (ActiveRecord) | Model + ResourceModel + Collection |
| Vistas | Blade (`.blade.php`) | Layout XML + Block + `.phtml` |
| Routing | `routes/web.php` | `routes.xml` (XML) |
| Middleware | `app/Http/Middleware/` | Plugin / Observer |
| Eventos | `Event::dispatch()` / Listeners | `events.xml` + Observer |
| DI Container | `app/Providers/` | `di.xml` |
| CLI | `php artisan` | `php bin/magento` |
| Migrations | `php artisan migrate` | `declarative_schema.xml` |
| Testing | PHPUnit + feature tests | PHPUnit + MFTF |
| Frontend build | Vite / Mix | Grunt / RequireJS |

## La diferencia filosófica más importante

### En Laravel:
```php
// Modificas el código directamente o haces un trait
class UserController extends Controller
{
    public function show($id)
    {
        return User::find($id);
    }
}
```

### En Magento:
**NUNCA modificas el código del core**. Todo se hace por extensión:

```
¿Quieres cambiar cómo funciona el precio de un producto?
→ No editas Magento\Catalog\Model\Product
→ Creas un Plugin que intercepta el método
→ O creas una Preference que reemplaza la clase
→ O disparas un Observer en el evento correspondiente
```

💡 **TIP**: La regla de oro de Magento es: **"Nunca edites el core"**. Si lo haces, no podrás actualizar Magento sin perder tus cambios. Todo va en módulos.

---

## Multistore: el concepto más diferente a Laravel

En Laravel, una app = una tienda. En Magento:

```
Una instalación puede tener:
├── Website A (marca X)
│   ├── Store View: Español
│   └── Store View: Inglés
└── Website B (marca Y)
    ├── Store View: México
    ├── Store View: Colombia
    └── Store View: España
```

Cada Store View puede tener su propio catálogo, precios, idioma y configuración. Esto es nativo en Magento. En Laravel tendrías que construirlo desde cero.

## Cuándo usar Magento vs cuándo usar Laravel

| Usa **Magento** cuando... | Usa **Laravel** cuando... |
|---|---|
| Tienes un catálogo grande (100+ productos) | Tienes una tienda simple (< 50 productos) |
| Necesitas multistore | Es una sola tienda |
| Necesitas gestión de inventario compleja | Inventario simple |
| El cliente quiere un ecommerce enterprise | Quieres velocidad de desarrollo |
| Hay muchos módulos de terceros a integrar | Quieres control total del código |
| Necesitas B2B (cotizaciones, crédito) | Es B2C simple |

## La curva de aprendizaje (sé honesto contigo mismo)

```
Laravel:    ████░░░░░░  (2-4 semanas para ser productivo)
Magento 2:  ██████████  (3-6 meses para sentirte cómodo)
```

Magento tiene fama de ser difícil porque:
1. Mucho XML de configuración
2. Patrones de diseño más estrictos (Repository, Service Contracts, DI)
3. El ciclo de desarrollo es más lento (necesitas limpiar caché constantemente)
4. La documentación oficial es mediocre
5. Los errores a veces no dicen nada útil

Pero también tiene:
- Una arquitectura muy sólida y mantenible a largo plazo
- Un ecosistema enorme de módulos de terceros
- Altísima demanda laboral (developers de Magento cobran muy bien)

---

## El ciclo de desarrollo que vas a vivir

```bash
# En Laravel esto es tu día a día:
php artisan serve
# ... editas código ...
# ... recargas el browser ...
# ¡Funciona! 🎉

# En Magento esto es tu día a día:
php bin/magento deploy:mode:set developer
# ... editas código ...
php bin/magento cache:flush          # <-- esto lo harás 50 veces al día
php bin/magento setup:upgrade        # <-- cuando cambias schema/config
php bin/magento setup:di:compile     # <-- cuando cambias DI
# ... recargas el browser ...
# Error en blanco. Revisas los logs.
# php bin/magento cache:flush de nuevo
# ¡Funciona! 🎉 (a veces)
```

💡 **TIP**: En modo `developer`, Magento regenera automáticamente los archivos de DI y los assets. Siempre desarrolla en este modo, nunca en `production`.

---

## Resumen

- Magento es complejo **por diseño** — fue hecho para escalar y ser extensible
- Vienes de Laravel, lo cual es una ventaja: ya sabes PHP moderno, MVC, DI y patrones
- La diferencia más grande: en Magento **todo** está en módulos y **nunca** tocas el core
- El concepto de multistore no existe en Laravel — es único de Magento
- La curva es real, pero la demanda laboral es alta y vale la pena
