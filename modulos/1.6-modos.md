## Los 3 modos de Magento

🔄 **Laravel**: Laravel tiene `APP_ENV=local|production` y `APP_DEBUG=true|false`. Magento tiene algo equivalente pero con más impacto — el modo afecta la generación de código, el caché, los errores y la performance de maneras profundas.

```
default     ← Modo inicial tras instalar. Mezcla rara de dev y prod. Evítalo.
developer   ← Tu modo de trabajo diario. Errores visibles, sin caché agresivo.
production  ← Para el servidor live. Máxima performance, errores ocultos.
```

Cómo ver en qué modo estás:

```bash
php bin/magento deploy:mode:show
# Current application mode: developer
```

## Modo Developer — tu entorno de trabajo

### Qué hace diferente

```
✓ Errores PHP completos visibles en el browser
✓ Stack traces detallados
✓ Factories, Proxies e Interceptors se generan ON-DEMAND (al primer request)
✓ Assets estáticos (CSS/JS) se generan on-demand por symlinks
✓ Caché de layouts y templates deshabilitado
✓ Los archivos en generated/ se regeneran automáticamente cuando cambias di.xml
✗ Performance reducida (todo se calcula en cada request)
✗ No apto para producción
```

### Cómo activarlo

```bash
php bin/magento deploy:mode:set developer
```

### El ciclo de trabajo en modo developer

```bash
# 1. Editas código (Controller, Model, di.xml, etc.)

# 2. Limpias el caché (lo harás 50 veces al día)
php bin/magento cache:flush

# 3. Si modificaste di.xml, events.xml o cualquier XML de configuración:
php bin/magento setup:upgrade

# 4. Si modificaste la estructura del DI (nuevas clases, nuevas interfaces):
php bin/magento setup:di:compile  # opcional en dev, obligatorio en prod

# 5. Recargas el browser
# Si ves pantalla en blanco → revisa var/log/exception.log
```

💡 **TIP**: En modo developer NO necesitas correr `setup:di:compile` después de cada cambio — Magento regenera las Factories y Proxies automáticamente. Eso sí, si ves errores de "Class not found" raros, un `setup:di:compile` los soluciona.

### El error más común en modo developer

```
Error de pantalla en blanco sin mensaje.

Solución:
tail -f var/log/exception.log
tail -f var/log/system.log

# O desde Docker:
docker exec magento_app tail -f /var/www/html/var/log/exception.log
```

## Modo Production — el servidor live

### Qué hace diferente

```
✓ Máxima performance
✓ Todo el código DI está pre-compilado en generated/
✓ Assets estáticos desplegados en pub/static/
✓ Caché agresivo activado
✓ Errores PHP NO visibles en browser (solo en logs)
✗ Cualquier cambio de código requiere re-deploy completo
✗ Los archivos generated/ NO se regeneran automáticamente
```

### Proceso de deploy a producción

Este es el orden correcto. Si lo haces mal puedes dejar la tienda caída:

```bash
# 1. Activar maintenance mode (muestra página de mantenimiento a los usuarios)
php bin/magento maintenance:enable

# 2. Actualizar el código (git pull, composer install, etc.)
git pull origin main
composer install --no-dev --optimize-autoloader

# 3. Aplicar cambios de schema y datos
php bin/magento setup:upgrade

# 4. Compilar el DI container (genera Factories, Proxies, Interceptors)
php bin/magento setup:di:compile

# 5. Desplegar assets estáticos (CSS, JS, imágenes de tema)
php bin/magento setup:static-content:deploy es_MX en_US -f

# 6. Limpiar caché
php bin/magento cache:flush

# 7. Activar modo production
php bin/magento deploy:mode:set production

# 8. Desactivar maintenance mode
php bin/magento maintenance:disable

# 9. Verificar que todo esté bien
php bin/magento cache:status
```

⚠️ **Orden crítico**: `setup:upgrade` ANTES de `setup:di:compile`. Si lo inviertes, el compiler puede fallar porque las tablas/datos que necesita aún no existen.

💡 **TIP**: El paso `setup:static-content:deploy` es el más lento (puede tardar 5-15 minutos en una tienda grande). Para agilizarlo, especifica solo los locales que usas: `es_MX en_US` en lugar de desplegar todos.

## Modo Default — evítalo

```
✓ No requiere configuración
✗ En entornos de producción: muestra algunos errores (inseguro)
✗ En entornos de desarrollo: no regenera automáticamente el código
✗ Performance peor que production, debugging peor que developer
✗ Es el peor de los dos mundos
```

El único momento en que estás en modo `default` es recién instalado Magento. Lo primero que haces es cambiarlo:

```bash
# En tu máquina local:
php bin/magento deploy:mode:set developer

# En el servidor de producción:
php bin/magento deploy:mode:set production
```

## Comparativa completa

| Característica | default | developer | production |
|---|---|---|---|
| Errores en browser | Algunos | Todos | Ninguno (solo logs) |
| Generación de código DI | On-demand | On-demand | Pre-compilado |
| Assets estáticos | On-demand | Symlinks on-demand | Pre-desplegados |
| Caché de layouts | Habilitado | Deshabilitado | Habilitado |
| Full Page Cache | Habilitado | Deshabilitado | Habilitado |
| Performance | Media | Baja | Alta |
| `setup:di:compile` requerido | No | No | Sí |
| `static-content:deploy` requerido | No | No | Sí |

## El caché en cada modo

En modo `developer` el caché de configuración y layouts está deshabilitado, pero el caché de datos (productos, precios, etc.) sí está activo. Por eso siempre necesitas limpiar caché al cambiar código:

```bash
# Limpiar TODO el caché (el más común)
php bin/magento cache:flush

# Ver estado de cada tipo de caché
php bin/magento cache:status

# Limpiar solo un tipo específico
php bin/magento cache:clean config        # solo config
php bin/magento cache:clean layout        # solo layouts
php bin/magento cache:clean block_html    # solo bloques HTML
php bin/magento cache:clean full_page     # solo FPC

# Deshabilitar un tipo (útil en desarrollo)
php bin/magento cache:disable full_page

# Rehabilitar
php bin/magento cache:enable full_page
```

### Tipos de caché y cuándo limpiar cada uno

| Tipo | Cuándo limpiar |
|---|---|
| `config` | Cambiaste cualquier XML de `etc/` |
| `layout` | Cambiaste layout XML o di.xml |
| `block_html` | Cambiaste un Block o template |
| `collections` | Cambiaste colecciones o ResourceModels |
| `reflection` | Rara vez (cambios de clases profundos) |
| `db_ddl` | Cambiaste el schema de DB |
| `compiled_config` | Corriste `setup:di:compile` |
| `eav` | Cambiaste atributos EAV |
| `customer_notification` | Rara vez |
| `full_page` | Cambiaste templates o layouts del storefront |
| `config_integration` | Cambiaste integraciones de API |
| `config_webservice` | Cambiaste webapi.xml |
| `translate` | Cambiaste archivos de traducción |

💡 **TIP**: En desarrollo, si dudas qué caché limpiar, usa `cache:flush` (limpia todo). En producción, sé más quirúrgico para no impactar performance — limpiar `full_page` en una tienda grande puede causar un pico de carga.

## Cambiar entre modos: lo que ocurre internamente

```
developer → production:

1. Magento lee etc/di.xml de todos los módulos
2. Genera generated/code/ (Factories, Proxies, Interceptors)
3. Escribe el modo en app/etc/env.php:
   'MAGE_MODE' => 'production'

production → developer:

1. Elimina generated/code/ (para forzar regeneración on-demand)
2. Escribe el modo en app/etc/env.php:
   'MAGE_MODE' => 'developer'
```

En `app/etc/env.php` puedes verlo directamente:

```php
return [
    // ...
    'MAGE_MODE' => 'developer',  // o 'production'
    // ...
];
```

## Configuración del Docker para modo developer

En tu entorno Docker ya estás en modo developer (lo vimos en la instalación). Si necesitas verificarlo:

```bash
docker exec magento_app php /var/www/html/bin/magento deploy:mode:show

# Si necesitas setearlo:
docker exec magento_app php /var/www/html/bin/magento deploy:mode:set developer
```

Para agilizar el desarrollo, también conviene deshabilitar algunos caches pesados:

```bash
docker exec magento_app php /var/www/html/bin/magento cache:disable full_page block_html layout
```

## Variables de entorno como alternativa

En lugar de `env.php`, puedes usar variables de entorno del sistema. Útil para Docker y CI/CD:

```bash
# En docker-compose.yml o en el sistema
MAGE_MODE=developer

# Magento las lee automáticamente y tienen prioridad sobre env.php
```

En el `docker-compose.yml` ya tienes un buen punto de partida para agregar esto si necesitas.
