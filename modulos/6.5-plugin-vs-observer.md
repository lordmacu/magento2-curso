# 6.5 — Plugin vs Observer vs Preference: Cuándo Usar Cada Uno

> **Objetivo**: Tener una guía definitiva para elegir el mecanismo de extensión correcto en Magento — el error más común de los desarrolladores nuevos es usar Preference cuando debería ser Plugin, o Plugin cuando debería ser Observer.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [6.4 — Eventos del Core más importantes](6.4-core-events.md)

---

## El problema de la elección

Magento tiene tres mecanismos principales para modificar o extender comportamiento:

| Mecanismo | Qué hace |
|---|---|
| **Plugin** | Intercepta la ejecución de un método público |
| **Observer** | Reacciona a un evento ya disparado |
| **Preference** | Reemplaza una clase completa por otra |

El problema: los tres pueden usarse para lograr resultados similares — pero cada uno tiene un costo diferente en términos de mantenibilidad, compatibilidad y acoplamiento.

---

## El árbol de decisión

```
¿Qué necesitas hacer?
│
├─ ¿Modificar cómo funciona un MÉTODO específico?
│   │
│   ├─ ¿El método es público y no es final/static?
│   │   └─ ✅ USA PLUGIN
│   │
│   ├─ ¿Es protected, private, static o final?
│   │   └─ ¿Hay un evento disponible para este caso?
│   │       ├─ Sí → ✅ USA OBSERVER
│   │       └─ No → ⚠️ USA PREFERENCE (último recurso)
│   │
│   └─ ¿Necesitas cambiar la firma del método o tipo de retorno?
│       └─ ⚠️ USA PREFERENCE (único que puede hacerlo)
│
├─ ¿REACCIONAR a algo que ya sucedió?
│   └─ ✅ USA OBSERVER
│
├─ ¿Mapear una INTERFACE a una implementación?
│   └─ ✅ USA PREFERENCE (uso correcto)
│
└─ ¿Reemplazar COMPLETAMENTE una clase del core?
    └─ ¿Realmente no hay otra opción?
        ├─ Sí → ⚠️ USA PREFERENCE con mucho cuidado
        └─ No → Reconsiderar Plugin u Observer
```

---

## Plugin — cuándo es la respuesta correcta

**Plugin es la herramienta por defecto para modificar comportamiento.**

```
✅ USA PLUGIN cuando:
   - Necesitas ejecutar lógica ANTES de un método (validar, transformar input)
   - Necesitas ejecutar lógica DESPUÉS de un método (modificar resultado)
   - Necesitas envolver un método completamente (caché, circuit breaker, retry)
   - Quieres que otros módulos puedan seguir extendiendo el mismo método
   - El método es público y no es final/static
```

```php
// Ejemplo: agregar campo al resultado de getById() — Plugin after
class AddStockLabelPlugin
{
    public function afterGetById(
        ProductRepositoryInterface $subject,
        ProductInterface $result,
        $productId
    ): ProductInterface {
        $label = $this->getStockLabel($result->getId());
        $result->setCustomAttribute('stock_label', $label);
        return $result;
    }
}
```

**Ventaja clave**: múltiples módulos pueden tener Plugins sobre el mismo método — coexisten ordenados por `sortOrder`. Nadie se pisa.

---

## Observer — cuándo es la respuesta correcta

**Observer es para reaccionar, no para modificar.**

```
✅ USA OBSERVER cuando:
   - Necesitas reaccionar a un evento de negocio (pedido creado, cliente registrado)
   - Tu lógica es independiente del resultado — no modificas el retorno
   - Quieres desacoplarte completamente del código que dispara el evento
   - El evento ya existe en el core para lo que necesitas
   - Necesitas ejecutar lógica en un método protected/private (via su evento)
```

```php
// Ejemplo: sincronizar con ERP cuando se crea un pedido — Observer
class SyncOrderWithErp implements ObserverInterface
{
    public function execute(Observer $observer): void
    {
        $order = $observer->getEvent()->getOrder();
        $this->erpService->sync($order); // lógica desacoplada
    }
}
```

**Ventaja clave**: el código que dispara el evento no sabe nada de los Observers — máximo desacoplamiento. Ideal para integraciones con sistemas externos.

---

## Preference — cuándo es la respuesta correcta

**Preference es el último recurso para clases concretas.**

```
✅ USA PREFERENCE cuando (y SOLO cuando):
   - Mapeas tu propia interface a tu propia implementación (caso más común y correcto)
   - Implementas una interface del core (ej: CarrierInterface para un carrier custom)
   - Necesitas cambiar la firma de un método (Plugin no puede hacerlo)
   - El método target es final y no hay evento disponible
   - Controlas todo el stack (proyecto sin módulos de terceros)

❌ NO uses PREFERENCE cuando:
   - Plugin puede lograr lo mismo
   - Observer puede lograr lo mismo
   - Hay riesgo de conflicto con otros módulos
   - Estás desarrollando para Marketplace o distribución
```

```xml
<!-- Uso correcto: mapear tu interface a tu implementación -->
<preference for="MiVendor\Blog\Api\PostRepositoryInterface"
            type="MiVendor\Blog\Model\PostRepository"/>

<!-- Uso incorrecto: modificar comportamiento del core cuando Plugin bastaría -->
<!-- ❌ <preference for="Magento\Catalog\Model\Product" type="Mi\Product"/> -->
```

## Comparación directa: el mismo caso con los tres mecanismos

**Caso**: cuando se guarda un producto, enviar una notificación si el stock bajó a cero.

### Con Plugin (around) — ❌ incorrecto para este caso

```php
// Funciona pero es un abuso — estás "modificando" un método
// cuando en realidad solo quieres "reaccionar"
public function aroundSave(ProductRepositoryInterface $subject, callable $proceed, $product)
{
    $result = $proceed($product);
    if ($result->getExtensionAttributes()->getStockItem()->getQty() <= 0) {
        $this->notifier->notifyOutOfStock($result);
    }
    return $result;
}
```

Problemas: acoplamiento innecesario, bloquea si `$proceed()` falla, más difícil de testear.

### Con Observer — ✅ correcto para este caso

```php
// Reacción limpia y desacoplada
public function execute(Observer $observer): void
{
    $product = $observer->getEvent()->getProduct();
    $stockItem = $product->getExtensionAttributes()->getStockItem();
    if ($stockItem && $stockItem->getQty() <= 0) {
        $this->notifier->notifyOutOfStock($product);
    }
}
// events.xml: catalog_product_save_after
```

Limpio, desacoplado, fácil de testear, no bloquea el flujo.

### Con Preference — ❌ incorrecto para este caso

```php
// Reemplazar toda la clase para añadir una notificación es un cañón para matar moscas
class Product extends \Magento\Catalog\Model\Product
{
    public function afterSave() {
        parent::afterSave();
        // notificar...
    }
}
```

Conflictos con otros módulos, mantenimiento costoso, rompe la extensibilidad.

---

## Reglas nemotécnicas

```
Plugin  = "antes de / después de / en vez de" un MÉTODO
Observer = "cuando OCURRE algo" en el negocio
Preference = "esta INTERFAZ usa esta CLASE"

Si puedes completar la frase:
  "Cuando [evento de negocio] sucede, quiero [acción]"
  → Observer

  "Quiero que el método [X] haga [modificación] a su [input/output]"
  → Plugin

  "Cada vez que alguien pida [Interface], que reciban [Clase]"
  → Preference
```

---

## Compatibilidad entre módulos

| Mecanismo | Múltiples módulos | Conflictos |
|---|---|---|
| Plugin | ✅ Coexisten por sortOrder | Raro, controlable |
| Observer | ✅ Todos se ejecutan en orden | Muy raro |
| Preference (interfaz→clase) | ✅ Solo uno gana, pero es el esperado | No aplica |
| Preference (clase concreta) | ❌ Solo uno gana, el otro desaparece | **Muy frecuente** |

---

## Resumen final

```
PLUGIN
  Cuándo: modificar input/output de un método público
  Ventaja: coexiste con otros módulos, granular, reversible
  Limitación: no funciona en protected/private/static/final/__construct

OBSERVER
  Cuándo: reaccionar a eventos de negocio sin modificar resultado
  Ventaja: máximo desacoplamiento, múltiples observers coexisten
  Limitación: no puedes modificar el valor de retorno del método original

PREFERENCE
  Cuándo: interface→clase (siempre correcto), clase concreta (último recurso)
  Ventaja: control total de la clase
  Limitación: un solo ganador por clase — rompe extensibilidad

Orden de preferencia para modificar comportamiento del core:
  1. Plugin (si el método es interceptable)
  2. Observer (si hay un evento disponible)
  3. Preference (si no hay otra opción — con mucha precaución)
```

## Ejercicios

### Ejercicio 1 — Clasificar 8 escenarios

Para cada escenario, elige el mecanismo correcto (Plugin, Observer o Preference) y justifica.

```
A. Al crear un cliente, asignarle automáticamente un grupo de clientes
   según su dominio de email (@empresa.com → grupo "Corporativo").

B. Necesitas que ProductRepository::getList() también filtre productos
   con stock negativo — siempre, en todo el sistema.

C. Tienes una interfaz propia ShippingCalculatorInterface y una clase
   DhlShippingCalculator que la implementa.

D. Cuando se completa el pago de un pedido, enviar los datos al
   sistema de contabilidad externo.

E. Quieres que getPrice() en Product retorne siempre un float
   con exactamente 2 decimales, en todos los contextos.

F. Validar que el SKU de un producto no contiene caracteres especiales
   antes de guardarlo — lanzar excepción si falla.

G. Necesitas loguear cada vez que alguien llama a
   CustomerRepository::getById() con el ID consultado.

H. Reemplazar la lógica de cálculo de impuestos del core porque
   el sistema del core no soporta el esquema fiscal de tu país
   (no hay evento ni plugin disponible para lo que necesitas).
```

<details>
<summary>Ver solución</summary>

```
A. OBSERVER — customer_register_success o customer_save_after
   Reaccionar a un evento de negocio sin modificar el retorno.
   Filtrar para solo aplicar en nuevos registros.

B. PLUGIN (before o around) — en ProductRepository::getList()
   Necesitas modificar el comportamiento de un método específico.
   before: modificar los search criteria antes de la query
   around: ejecutar la query y filtrar el resultado

C. PREFERENCE — uso correcto
   <preference for="ShippingCalculatorInterface"
               type="DhlShippingCalculator"/>
   Mapear interface propia a implementación propia.

D. OBSERVER — sales_order_invoice_pay
   Reacción desacoplada a un evento de negocio.
   El sistema de contabilidad no necesita saber cómo funciona Magento.

E. PLUGIN (after) — afterGetPrice en Product o ProductRepository
   Modificar el valor de retorno de un método.
   public function afterGetPrice($subject, $result): float {
       return round((float) $result, 2);
   }

F. PLUGIN (before) — en ProductRepository::save()
   Validar el input antes de que se ejecute el guardado.
   Puedes lanzar una ValidationException que detenga el flujo.
   public function beforeSave($subject, $product): array {
       if (preg_match('/[^a-zA-Z0-9\-_]/', $product->getSku())) {
           throw new ValidationException(__('SKU inválido'));
       }
       return [$product];
   }

G. PLUGIN (before o after) — en CustomerRepository::getById()
   Logging quirúrgico de un método específico.
   Observer no aplica bien aquí — no hay un "evento" estándar para getById.

H. PREFERENCE — último recurso justificado
   No hay evento ni plugin disponible, la lógica del core es incompatible.
   Extender la clase de impuestos del core y registrar el preference.
   Documentar muy bien por qué se usa Preference aquí.
```

</details>

### Ejercicio 2 — Refactorizar un Preference innecesario

Este código usa Preference para algo que debería ser Plugin. Identifica el problema y reescríbelo correctamente.

```php
// Model/ProductRepository.php
namespace MiVendor\Blog\Model;

class ProductRepository extends \Magento\Catalog\Model\ProductRepository
{
    public function getById($productId, $editMode = false, $storeId = null, $forceReload = false)
    {
        $product = parent::getById($productId, $editMode, $storeId, $forceReload);
        $product->setCustomAttribute('viewed_at', date('Y-m-d H:i:s'));
        return $product;
    }
}
```

```xml
<!-- di.xml -->
<preference for="Magento\Catalog\Api\ProductRepositoryInterface"
            type="MiVendor\Blog\Model\ProductRepository"/>
```

<details>
<summary>Ver solución</summary>

**Problema**: se usa Preference para agregar un campo al resultado de `getById()` — exactamente para lo que sirve un after Plugin. Este Preference:
- Rompe la extensibilidad (nadie más puede hacer Preference en ProductRepository)
- Es frágil ante actualizaciones del core
- Es innecesariamente pesado

**Solución correcta — after Plugin**:

```php
// Plugin/AddViewedAtPlugin.php
namespace MiVendor\Blog\Plugin;

use Magento\Catalog\Api\ProductRepositoryInterface;
use Magento\Catalog\Api\Data\ProductInterface;

class AddViewedAtPlugin
{
    public function afterGetById(
        ProductRepositoryInterface $subject,
        ProductInterface $result
    ): ProductInterface {
        $result->setCustomAttribute('viewed_at', date('Y-m-d H:i:s'));
        return $result;
    }
}
```

```xml
<!-- di.xml — sin Preference, solo Plugin -->
<type name="Magento\Catalog\Api\ProductRepositoryInterface">
    <plugin name="mivendor_blog_add_viewed_at"
            type="MiVendor\Blog\Plugin\AddViewedAtPlugin"
            sortOrder="10"/>
</type>
```

**Resultado**: otros módulos pueden seguir extendiendo `ProductRepositoryInterface` con sus propios Plugins — nadie se pisa.

</details>
