# 5.1 — Plugin Overview: Qué Son y Cuándo Usarlos

> **Objetivo**: Entender qué son los Plugins (Interceptors), cómo funcionan internamente, la diferencia con Observers y Preferences, y cuándo es correcto usar cada mecanismo de extensión.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [4.9 — setup:di:compile](4.9-di-compile.md)

---

## Qué es un Plugin

Un Plugin (también llamado Interceptor) es un mecanismo que permite **ejecutar código antes, después o en lugar de cualquier método público** de cualquier clase, sin modificar la clase original.

Es el mecanismo de extensión más poderoso de Magento — permite que múltiples módulos modifiquen el mismo método sin conflictos, porque todos coexisten en una cadena.

```
Sin Plugin:
  ProductRepository::getById(5)  →  devuelve Product

Con Plugin:
  Plugin A (before) →  modifica argumentos
  ProductRepository::getById(5)  →  ejecuta método original
  Plugin B (after)  →  modifica resultado
  →  devuelve Product modificado
```

---

## Cómo funciona internamente

Cuando registras un Plugin sobre `ProductRepository`, Magento genera un **Interceptor** (vía `setup:di:compile`) que extiende la clase y envuelve cada método interceptado:

```php
// generated/code/Magento/Catalog/Model/ProductRepository/Interceptor.php
class Interceptor extends \Magento\Catalog\Model\ProductRepository
{
    use \Magento\Framework\Interception\Interceptor;

    public function getById($productId, $editMode = false, $storeId = null, $forceReload = false)
    {
        $pluginInfo = $this->pluginList->getNext($this->subjectType, 'getById');
        return $pluginInfo
            ? $this->___callPlugins('getById', func_get_args(), $pluginInfo)
            : parent::getById(...func_get_args());
    }
}
```

El ObjectManager inyecta el `Interceptor` en lugar de la clase original — tu código no nota la diferencia.

---

## Los tres tipos de Plugin

```
before  →  se ejecuta ANTES del método, puede modificar los argumentos
after   →  se ejecuta DESPUÉS del método, puede modificar el resultado
around  →  envuelve el método completamente, decide si llamarlo o no
```

Cada tipo tiene su propio caso de uso. No uses `around` para lo que puedes hacer con `before` o `after`.

## Registrar un Plugin en di.xml

```xml
<!-- etc/di.xml -->
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:ObjectManager/etc/config.xsd">

    <type name="Magento\Catalog\Model\ProductRepository">
        <plugin name="mivendor_blog_product_logger"
                type="MiVendor\Blog\Plugin\ProductRepositoryPlugin"
                sortOrder="10"
                disabled="false"/>
    </type>

</config>
```

- `name` — identificador único del plugin en todo el sistema
- `type` — tu clase PHP con los métodos before/after/around
- `sortOrder` — prioridad cuando hay múltiples plugins (menor = primero)
- `disabled` — para deshabilitar un plugin de otro módulo sin eliminarlo

## Estructura de la clase Plugin

```php
namespace MiVendor\Blog\Plugin;

use Magento\Catalog\Api\ProductRepositoryInterface;

class ProductRepositoryPlugin
{
    // Convención de nombres:
    // before{NombreMetodo}
    // after{NombreMetodo}
    // around{NombreMetodo}

    public function beforeGetById(
        ProductRepositoryInterface $subject,  // instancia interceptada
        int $productId,                       // argumentos del método original
        bool $editMode = false,
        ?int $storeId = null,
        bool $forceReload = false
    ): array {
        // Retorna array con los argumentos (modificados o no)
        return [$productId, $editMode, $storeId, $forceReload];
    }

    public function afterGetById(
        ProductRepositoryInterface $subject,
        \Magento\Catalog\Api\Data\ProductInterface $result  // resultado del método
    ): \Magento\Catalog\Api\Data\ProductInterface {
        // Retorna el resultado (modificado o no)
        return $result;
    }
}
```

## Plugin vs Observer vs Preference

| Mecanismo | Cuándo usarlo |
|---|---|
| **Plugin** | Modificar comportamiento de un método. Múltiples módulos coexisten. |
| **Observer** | Reaccionar a un evento de negocio sin cambiar el resultado. |
| **Preference** | Reemplazar completamente una clase. Solo uno puede existir. |

```
¿Necesitas modificar cómo funciona un método?        → Plugin
¿Necesitas reaccionar cuando algo sucede?             → Observer
¿Necesitas reemplazar una clase completamente?        → Preference (con cuidado)
```

---

## Flujo con múltiples plugins

```
before plugins (sortOrder ASC):
  → Plugin A before (sortOrder=10)
  → Plugin B before (sortOrder=20)

Método original ejecuta

after plugins (sortOrder DESC):
  → Plugin B after (sortOrder=20)
  → Plugin A after (sortOrder=10)
```

## Resumen

```
Plugin = código que corre antes/después/alrededor de cualquier método público

Registrar en di.xml:
  <type name="ClaseAInterceptar">
      <plugin name="nombre_unico" type="TuClasePlugin" sortOrder="10"/>
  </type>

Métodos en tu Plugin:
  before{Metodo}(subject, args...)           → retorna array de args modificados
  after{Metodo}(subject, result)             → retorna resultado modificado
  around{Metodo}(subject, callable, args...) → control total

Plugin   → modificar comportamiento de método (preferido)
Observer → reaccionar a evento sin cambiar resultado
Preference → reemplazar clase (último recurso)
```
