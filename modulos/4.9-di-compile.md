# 4.9 — setup:di:compile: Qué Hace y Por Qué Importa

> **Objetivo**: Entender exactamente qué genera `setup:di:compile`, por qué es obligatorio en producción, qué errores produce cuando falla y cómo diagnosticarlos.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [4.8 — Shared vs Non-Shared](4.8-shared-nonshared.md)

---

## Qué es la compilación del DI

En modo `developer`, Magento resuelve el DI container **en cada request** — lee todos los `di.xml`, los mergea, resuelve el grafo de dependencias. Es lento pero no requiere compilar.

En modo `production`, ese proceso se hace **una sola vez** y el resultado se guarda como código PHP optimizado en `generated/`. Las requests solo cargan ese código generado — sin leer XMLs, sin reflexión, sin resolución dinámica.

```bash
php bin/magento setup:di:compile
```

---

## Qué genera el compilador

### 1. Factories auto-generadas

```
generated/code/MiVendor/Blog/Model/PostFactory.php
generated/code/MiVendor/Blog/Model/ResourceModel/Post/CollectionFactory.php
generated/code/Magento/Catalog/Model/ProductFactory.php
```

Para cada clase que se pide como `ClaseFactory` en algún constructor del proyecto.

### 2. Interceptors (Plugins)

```
generated/code/MiVendor/Blog/Model/PostRepository/Interceptor.php
generated/code/Magento/Catalog/Model/Product/Interceptor.php
```

Cada clase que tiene al menos un Plugin registrado en `di.xml` recibe un Interceptor. Es una subclase generada que envuelve los before/around/after plugins.

### 3. Proxies

```
generated/code/MiVendor/Blog/Service/PdfGenerator/Proxy.php
```

Para cada clase referenciada como `ClaseProxy` en algún `di.xml`.

### 4. Metadata del DI container

```
generated/metadata/
├── global.ser       ← configuración DI global serializada
├── frontend.ser     ← configuración DI del área frontend
├── adminhtml.ser    ← configuración DI del área admin
└── webapi_rest.ser
```

Estos archivos contienen el grafo de dependencias ya resuelto — en producción se deserializan directamente sin leer ningún XML.

---

## El proceso completo

```bash
php bin/magento setup:di:compile
```

Internamente ejecuta estos pasos en orden:

```
1. Escanea todos los di.xml de todos los módulos (global + por área)
2. Mergea la configuración respetando áreas y prioridades
3. Resuelve el grafo completo de dependencias (detecta circulares aquí)
4. Genera Factories para todas las clases que las necesiten
5. Genera Interceptors para todas las clases con Plugins
6. Genera Proxies para todas las clases declaradas como Proxy en di.xml
7. Serializa el grafo resuelto en generated/metadata/
8. Valida que no hay errores de tipo, interfaces sin implementación, etc.
```

---

## Cuándo ejecutarlo

```bash
# SIEMPRE en producción — antes del deploy:
php bin/magento setup:upgrade        # 1. migraciones primero
php bin/magento setup:di:compile     # 2. luego compilar
php bin/magento setup:static-content:deploy -f  # 3. assets
php bin/magento cache:flush          # 4. caché

# En desarrollo — solo cuando hay errores extraños de DI:
# (el modo developer no lo requiere)
php bin/magento setup:di:compile
```

**En modo developer NO es necesario** — Magento resuelve todo on-demand. Solo lo necesitas si:
- Cambias a modo production
- Tienes errores de "Class X does not exist" en `generated/`
- Quieres verificar que tu configuración DI es válida antes de hacer deploy

## Errores comunes durante la compilación

### Error: interface sin implementación

```
[ERROR] Magento\Framework\Exception\RuntimeException:
  Source class "MiVendor\Blog\Api\PostRepositoryInterface" for
  "MiVendor\Blog\Api\PostRepositoryInterfaceFactory" generation does not exist.
```

**Causa**: Declaraste una Factory para una interfaz pero no hay `<preference>` que la mapee a una clase concreta.

**Solución**:
```xml
<preference for="MiVendor\Blog\Api\PostRepositoryInterface"
            type="MiVendor\Blog\Model\PostRepository"/>
```

---

### Error: dependencia circular

```
[ERROR] Circular dependency:
  MiVendor\Blog\Model\PostService depends on
  MiVendor\Blog\Model\CategoryService,
  MiVendor\Blog\Model\CategoryService depends on
  MiVendor\Blog\Model\PostService
```

**Solución**: Romper el ciclo con un Proxy (ver [4.5](4.5-proxies.md)):
```xml
<type name="MiVendor\Blog\Model\PostService">
    <arguments>
        <argument name="categoryService" xsi:type="object">
            MiVendor\Blog\Model\CategoryService\Proxy
        </argument>
    </arguments>
</type>
```

---

### Error: clase no encontrada

```
[ERROR] ReflectionException: Class MiVendor\Blog\Model\PostRepository does not exist
```

**Causa**: El namespace o el path del archivo no coinciden.

**Verificar**:
```bash
# El namespace en el archivo debe coincidir con la ruta:
# app/code/MiVendor/Blog/Model/PostRepository.php
# namespace MiVendor\Blog\Model;   ← debe ser exactamente esto

# Regenerar autoloader:
composer dump-autoload
php bin/magento setup:di:compile
```

---

### Error: tipo incorrecto en di.xml

```
[ERROR] InvalidArgumentException:
  Argument "timeout" of type "string" cannot be assigned to
  parameter of type "int" in MiVendor\Blog\Model\ApiClient
```

**Causa**: Declaraste `xsi:type="string"` pero el constructor pide `int`.

**Solución**:
```xml
<!-- Incorrecto -->
<argument name="timeout" xsi:type="string">30</argument>

<!-- Correcto -->
<argument name="timeout" xsi:type="number">30</argument>
```

---

## Limpiar y recompilar desde cero

Cuando hay errores persistentes que no se resuelven:

```bash
# Limpiar el código generado
rm -rf generated/code/ generated/metadata/

# Recompilar desde cero
php bin/magento setup:di:compile

# Limpiar caché
php bin/magento cache:flush
```

## Diferencia entre modos

```
Modo developer:
  - di.xml se lee en cada request
  - Factories/Proxies/Interceptors se generan on-demand
  - setup:di:compile no es necesario
  - Más lento pero más flexible para desarrollo

Modo production:
  - generated/metadata/*.ser se carga directamente
  - Factories/Interceptors/Proxies ya existen en generated/code/
  - setup:di:compile es OBLIGATORIO antes del deploy
  - Mucho más rápido en runtime
```

---

## Resumen

```
setup:di:compile genera:
  ├── generated/code/
  │   ├── *Factory.php          ← Factories para todos los constructores
  │   ├── */Interceptor.php     ← Wrappers para clases con Plugins
  │   └── */Proxy.php           ← Lazy loaders para Proxies declarados
  └── generated/metadata/
      └── *.ser                 ← Grafo DI serializado por área

Cuándo correrlo:
  - Siempre antes de deploy a producción
  - Cuando hay errores "Class X does not exist"
  - Para validar configuración DI antes de deploy

Si falla:
  1. Leer el error exacto
  2. rm -rf generated/
  3. Corregir el problema (interface sin preference, circular dep, type mismatch)
  4. php bin/magento setup:di:compile
  5. php bin/magento cache:flush
```
