# 6.4 — Eventos del Core más Importantes

> **Objetivo**: Conocer los eventos del core de Magento que más usarás en proyectos reales — cuándo se disparan, qué datos traen y para qué casos de uso sirven.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [6.3 — Disparar Eventos Propios](6.3-dispatch-events.md)

---

## Por qué conocer los eventos del core

Magento tiene más de 1,000 eventos. La mayoría no los usarás nunca. Pero hay un subconjunto de ~20 que cubren el 90% de los casos de negocio reales: pedidos, productos, clientes, carrito, pagos.

```bash
# Ver todos los eventos del core (muchos):
grep -r "dispatch(" vendor/magento/ --include="*.php" | grep "eventManager" | wc -l
# → 1000+

# Buscar eventos de un área específica:
grep -r "dispatch(" vendor/magento/module-sales/ --include="*.php" | grep "eventManager"
```

## Eventos de Pedidos (Sales)

### `sales_order_place_before` / `sales_order_place_after`

```php
// Dónde se dispara: Magento\Sales\Model\Order\Payment
// Datos disponibles:
$order = $observer->getEvent()->getOrder();
```

```
sales_order_place_before  → justo antes de que se confirme el pedido
                            Úsalo para: validación final, modificar el pedido
sales_order_place_after   → pedido ya confirmado en DB
                            Úsalo para: email de confirmación, ERP, puntos de fidelidad
```

### `checkout_submit_all_after`

```php
// Datos disponibles:
$order = $observer->getEvent()->getOrder();
$quote = $observer->getEvent()->getQuote();
```

```
Cuándo: después de que el checkout completo finaliza (incluyendo multi-shipping)
Diferencia con place_after: este tiene acceso tanto al order como al quote original
Úsalo para: limpiar datos del quote, notificaciones que necesitan info del carrito original
```

### `sales_order_invoice_pay`

```php
$invoice = $observer->getEvent()->getInvoice();
$order   = $invoice->getOrder();
```

```
Cuándo: cuando una factura se marca como pagada
Úsalo para: activar envío, notificar almacén, contabilidad
```

### `sales_order_shipment_save_after`

```php
$shipment = $observer->getEvent()->getShipment();
$order    = $shipment->getOrder();
```

```
Cuándo: cuando se crea o actualiza un envío
Úsalo para: notificar al cliente con número de tracking, actualizar ERP
```

### `sales_order_status_history_save_after`

```php
$statusHistory = $observer->getEvent()->getStatusHistory();
```

```
Cuándo: cuando cambia el estado del pedido
Úsalo para: triggers por estado (ej: "cuando pase a 'complete' hacer X")
```

## Eventos de Productos (Catalog)

### `catalog_product_save_before` / `catalog_product_save_after`

```php
$product = $observer->getEvent()->getProduct();
```

```
save_before  → antes de guardar en DB
               Úsalo para: validación, transformación de datos, calcular campos derivados
save_after   → después de guardar
               Úsalo para: reindexar, sincronizar con ERP, limpiar caché
```

### `catalog_product_load_after`

```php
$product = $observer->getEvent()->getProduct();
```

```
Cuándo: después de cargar un producto de la DB
Úsalo para: agregar datos dinámicos al producto (stock externo, precios especiales)
Nota: se dispara en CADA carga — ten cuidado con el performance
```

### `catalog_product_delete_before` / `catalog_product_delete_after`

```php
$product = $observer->getEvent()->getProduct();
```

```
delete_before → puedes lanzar excepción para cancelar el borrado
delete_after  → para limpiar datos relacionados (imágenes, datos custom, ERP)
```

### `catalog_product_import_finish_after`

```php
// No hay datos específicos — el import ya terminó
```

```
Cuándo: después de que termina una importación masiva de productos
Úsalo para: reindexar, notificar, sincronizar — más eficiente que save_after por producto
```

## Eventos de Clientes (Customer)

### `customer_save_before` / `customer_save_after`

```php
$customer = $observer->getEvent()->getCustomer();
```

```
save_after  → Úsalo para: sincronizar con CRM, crear registro en sistemas externos
save_before → Úsalo para: validar datos, normalizar campos (ej: formatear teléfono)
```

### `customer_login` / `customer_logout`

```php
$customer = $observer->getEvent()->getCustomer();
```

```
customer_login  → Úsalo para: actualizar last_login, auditoría de accesos, sesión ERP
customer_logout → Úsalo para: limpiar datos de sesión, log de sesión
```

### `customer_register_success`

```php
$customer    = $observer->getEvent()->getCustomer();
$accountController = $observer->getEvent()->getAccountController();
```

```
Cuándo: registro exitoso de un nuevo cliente
Úsalo para: email de bienvenida custom, alta en newsletter, CRM, puntos iniciales
```

---

## Eventos del Carrito (Quote)

### `checkout_cart_add_product_complete`

```php
$product = $observer->getEvent()->getProduct();
$request = $observer->getEvent()->getRequest();
```

```
Cuándo: después de agregar un producto al carrito
Úsalo para: upselling, cross-selling dinámico, tracking de analytics
```

### `sales_quote_save_after`

```php
$quote = $observer->getEvent()->getQuote();
```

```
Cuándo: cada vez que el quote (carrito) se guarda
Úsalo para: sincronizar carrito con sesión externa, analytics de abandono
```

---

## Eventos del Admin

### `adminhtml_block_html_before`

```php
$block = $observer->getEvent()->getBlock();
```

```
Cuándo: antes de renderizar cualquier bloque del admin
Úsalo para: modificar bloques del admin sin preference (con cuidado)
```

### `admin_user_authenticate_after`

```php
$user     = $observer->getEvent()->getUser();
$password = $observer->getEvent()->getPassword();
$result   = $observer->getEvent()->getResult(); // true/false
```

```
Cuándo: después de intentar autenticar un usuario admin
Úsalo para: 2FA custom, auditoría de logins, bloqueo por IP
```

---

## Eventos del Layout y Respuesta HTTP

### `controller_action_predispatch`

```php
$controller = $observer->getEvent()->getControllerAction();
$request    = $observer->getEvent()->getRequest();
```

```
Cuándo: antes de ejecutar cualquier action de cualquier controller
Úsalo para: autenticación global, rate limiting, logging de requests
Nota: úsalo en etc/frontend/events.xml o etc/adminhtml/events.xml según el área
```

### `controller_action_postdispatch`

```php
$controller = $observer->getEvent()->getControllerAction();
```

```
Cuándo: después de ejecutar cualquier action
Úsalo para: modificar la respuesta, logging de tiempos de respuesta
```

## Cómo encontrar eventos del core

```bash
# Buscar todos los dispatch() en un módulo:
grep -rn "dispatch(" vendor/magento/module-sales/ --include="*.php" | grep "eventManager"

# Buscar un evento específico por nombre:
grep -rn "sales_order_place_after" vendor/magento/ --include="*.php"

# Ver dónde se dispara un evento (para entender qué datos tiene):
grep -rn "'sales_order_place_after'" vendor/magento/ --include="*.php" -B2 -A5
```

## Patrón Observer completo para eventos del core

```php
// Observer/SyncOrderWithErp.php
namespace MiVendor\Blog\Observer;

use Magento\Framework\Event\Observer;
use Magento\Framework\Event\ObserverInterface;
use Psr\Log\LoggerInterface;

class SyncOrderWithErp implements ObserverInterface
{
    public function __construct(
        private readonly \MiVendor\Blog\Service\ErpService $erpService,
        private readonly LoggerInterface                    $logger,
    ) {}

    public function execute(Observer $observer): void
    {
        $order = $observer->getEvent()->getOrder();

        // Validar que tenemos datos válidos
        if (!$order || !$order->getId()) {
            return;
        }

        try {
            $this->erpService->syncOrder($order);

            $this->logger->info('Pedido sincronizado con ERP', [
                'order_id'       => $order->getId(),
                'increment_id'   => $order->getIncrementId(),
            ]);
        } catch (\Exception $e) {
            // NUNCA lanzar excepciones en un Observer — aborta el flujo principal
            $this->logger->error('Error al sincronizar pedido con ERP', [
                'order_id' => $order->getId(),
                'error'    => $e->getMessage(),
            ]);
        }
    }
}
```

```xml
<!-- etc/events.xml -->
<event name="sales_order_place_after">
    <observer name="mivendor_blog_sync_order_erp"
              instance="MiVendor\Blog\Observer\SyncOrderWithErp"/>
</event>
```

## Resumen

```
Los eventos más usados por categoría:

Pedidos:    sales_order_place_after, checkout_submit_all_after,
            sales_order_invoice_pay, sales_order_shipment_save_after

Productos:  catalog_product_save_after, catalog_product_load_after,
            catalog_product_delete_after

Clientes:   customer_save_after, customer_login, customer_register_success

Carrito:    checkout_cart_add_product_complete, sales_quote_save_after

Admin:      admin_user_authenticate_after

Global:     controller_action_predispatch

Regla:
  - NUNCA lanzar excepciones en un Observer → loguea y continúa
  - catalog_product_load_after → cuidado con performance (se llama en cada carga)
  - Usa el área correcta: etc/frontend/, etc/adminhtml/ o etc/events.xml global
```

## Ejercicios

### Ejercicio 1 — Elegir el evento correcto

Para cada requisito, indica qué evento del core usarías y por qué:

1. Al completar un pedido, enviar los datos al sistema de contabilidad.
2. Cuando un cliente se registra, agregarlo automáticamente a una lista de Mailchimp.
3. Cuando se guarda un producto con `status = disabled`, notificar al equipo de contenidos.
4. Cuando se agrega un producto al carrito, registrar el evento en Google Analytics.

<details>
<summary>Ver solución</summary>

```
1. sales_order_place_after
   Razón: el pedido ya está confirmado en DB. Es el momento seguro para enviar
   a contabilidad sin riesgo de que la transacción falle después.
   Alternativa si necesitas esperar el pago: sales_order_invoice_pay

2. customer_register_success
   Razón: específico para registros nuevos (no dispara en actualizaciones).
   customer_save_after también serviría pero dispara en CADA guardado del cliente,
   incluyendo actualizaciones de perfil — habría que filtrar manualmente.

3. catalog_product_save_after
   Razón: después de guardar hay acceso al estado final del producto.
   Filtrar en el Observer:
   if ((int) $product->getStatus() === \Magento\Catalog\Model\Product\Attribute\Source\Status::STATUS_DISABLED) {
       // notificar
   }

4. checkout_cart_add_product_complete
   Razón: específico para el momento de agregar al carrito. Tiene acceso al
   producto y al request. Usar en etc/frontend/events.xml (solo tienda).
```

</details>

### Ejercicio 2 — Observer con filtrado de condición

Crea un Observer para `catalog_product_save_after` que solo actúe cuando el producto cambia de `enabled` a `disabled`, y loguee el SKU y quién hizo el cambio.

<details>
<summary>Ver solución</summary>

```php
// Observer/LogProductDisabled.php
namespace MiVendor\Blog\Observer;

use Magento\Framework\Event\Observer;
use Magento\Framework\Event\ObserverInterface;
use Magento\Catalog\Model\Product\Attribute\Source\Status;
use Magento\Backend\Model\Auth\Session as AdminSession;
use Psr\Log\LoggerInterface;

class LogProductDisabled implements ObserverInterface
{
    public function __construct(
        private readonly AdminSession    $adminSession,
        private readonly LoggerInterface $logger,
    ) {}

    public function execute(Observer $observer): void
    {
        $product = $observer->getEvent()->getProduct();

        // Filtrar: solo cuando el producto se DESACTIVA
        // getOrigData() contiene el valor antes del guardado
        $wasEnabled  = (int) $product->getOrigData('status') === Status::STATUS_ENABLED;
        $isNowDisabled = (int) $product->getStatus() === Status::STATUS_DISABLED;

        if (!$wasEnabled || !$isNowDisabled) {
            return; // No es un cambio enabled→disabled, ignorar
        }

        $adminUser = $this->adminSession->getUser();
        $username  = $adminUser ? $adminUser->getUserName() : 'sistema';

        $this->logger->info('Producto desactivado', [
            'sku'        => $product->getSku(),
            'product_id' => $product->getId(),
            'by_user'    => $username,
        ]);
    }
}
```

```xml
<!-- etc/adminhtml/events.xml — solo en el admin -->
<event name="catalog_product_save_after">
    <observer name="mivendor_blog_log_product_disabled"
              instance="MiVendor\Blog\Observer\LogProductDisabled"/>
</event>
```

**Punto clave**: `$product->getOrigData('field')` devuelve el valor que tenía el campo **antes** del guardado. Es la forma correcta de detectar cambios de estado en un Observer.

</details>
