# 2.3 — Xdebug, Logging y Debugging

> **Objetivo**: Configurar Xdebug en Docker, dominar el sistema de logging de Magento y aprender las técnicas de debugging específicas del framework para resolver problemas rápidamente.
> **Estado**: ⬜ Pendiente
> **Prerequisito**: [2.2 — Crear Comandos CLI Propios](2.2-custom-cli-commands.md)

---

## Por qué debugging en Magento es diferente

En Laravel, un `dd()` en cualquier parte te muestra lo que necesitas. En Magento el flujo es más complejo: hay DI container, áreas, plugins, observers, caché de configuración... Un `var_dump()` a veces ni aparece porque el caché devuelve la versión anterior.

Necesitarás una combinación de:
1. **Xdebug** — para breakpoints reales
2. **Logging** — para trazar flujos complejos
3. **Template hints** — para encontrar templates y blocks
4. **`dev:di:info`** — para entender el DI
5. **Técnicas específicas** de Magento

## Parte 1 — Xdebug en Docker

### Configurar Xdebug en el Dockerfile

```dockerfile
# Agregar al Dockerfile, después de instalar extensiones:
RUN pecl install xdebug \
    && docker-php-ext-enable xdebug

COPY xdebug.ini /usr/local/etc/php/conf.d/xdebug.ini
```

### xdebug.ini

```ini
; docker/xdebug.ini
[xdebug]
xdebug.mode=debug
xdebug.start_with_request=yes
xdebug.client_host=host.docker.internal   ; Mac/Windows: conecta al IDE del host
xdebug.client_port=9003
xdebug.log=/tmp/xdebug.log
xdebug.idekey=PHPSTORM

; Performance: desactivar en producción
; xdebug.mode=off
```

### docker-compose.yml — agregar variables de entorno

```yaml
services:
  app:
    environment:
      - XDEBUG_MODE=debug
      - XDEBUG_CONFIG=client_host=host.docker.internal
      - PHP_IDE_CONFIG=serverName=magento-docker
```

### Configurar PHPStorm

```
1. Settings → PHP → Debug
   - Xdebug port: 9003

2. Settings → PHP → Servers → +
   - Name: magento-docker
   - Host: localhost
   - Port: 8181
   - Debugger: Xdebug
   - Path mappings:
     /Users/tu-usuario/magento  →  /var/www/html

3. Run → Start Listening for PHP Debug Connections (telefono verde)

4. Poner breakpoint en cualquier archivo PHP

5. Abrir http://localhost:8181 en el browser — Xdebug conecta automáticamente
```

### Configurar VS Code

```json
// .vscode/launch.json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Listen for Xdebug",
            "type": "php",
            "request": "launch",
            "port": 9003,
            "pathMappings": {
                "/var/www/html": "${workspaceFolder}"
            },
            "hostname": "localhost"
        },
        {
            "name": "Debug CLI Command",
            "type": "php",
            "request": "launch",
            "port": 9003,
            "pathMappings": {
                "/var/www/html": "${workspaceFolder}"
            }
        }
    ]
}
```

### Xdebug para comandos CLI

```bash
# Correr un comando con Xdebug desde Docker:
docker exec -e XDEBUG_SESSION=1 magento_app \
    php /var/www/html/bin/magento mimodulo:productos:sincronizar full

# O setear la variable permanente en el shell del contenedor:
docker exec -it magento_app bash
export XDEBUG_SESSION=1
php bin/magento cache:flush
```

## Parte 2 — Sistema de Logging de Magento

### Los archivos de log

```
var/log/
├── system.log          ← Logs del sistema (INFO, DEBUG, NOTICE)
├── exception.log       ← Excepciones no capturadas — EMPIEZA AQUÍ cuando algo falla
├── debug.log           ← Solo en modo developer
├── magento.log         ← Logs generales
└── {tu-modulo}.log     ← Tus logs custom
```

```bash
# En desarrollo, ten estos abiertos siempre:
tail -f var/log/exception.log var/log/system.log
```

### Usar LoggerInterface en tu código

```php
namespace MiVendor\MiModulo\Model;

use Psr\Log\LoggerInterface;

class MiServicio
{
    public function __construct(
        private readonly LoggerInterface $logger
    ) {}

    public function procesarPedido(int $orderId): void
    {
        // Niveles estándar PSR-3
        $this->logger->debug('Procesando pedido', ['order_id' => $orderId]);
        $this->logger->info('Pedido iniciado', ['order_id' => $orderId]);
        $this->logger->warning('Stock bajo', ['sku' => 'SKU-001', 'stock' => 2]);
        $this->logger->error('Fallo al procesar pago', ['order_id' => $orderId]);
        $this->logger->critical('Conexión DB caída', ['exception' => $e->getMessage()]);
    }
}
```

El DI inyecta automáticamente `Magento\Framework\Logger\Monolog` como implementación de `LoggerInterface`. Escribe en `var/log/system.log`.

### Logger con archivo custom

Para separar tus logs de los del sistema:

```xml
<!-- etc/di.xml -->
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:ObjectManager/etc/config.xsd">

    <!-- Definir un handler que escribe en tu propio archivo -->
    <virtualType name="MiVendor\MiModulo\Logger\Handler"
                 type="Magento\Framework\Logger\Handler\Base">
        <arguments>
            <argument name="fileName" xsi:type="string">/var/log/mimodulo.log</argument>
        </arguments>
    </virtualType>

    <!-- Definir el logger con ese handler -->
    <virtualType name="MiVendor\MiModulo\Logger\Logger"
                 type="Magento\Framework\Logger\Monolog">
        <arguments>
            <argument name="name" xsi:type="string">mimodulo</argument>
            <argument name="handlers" xsi:type="array">
                <item name="system" xsi:type="object">MiVendor\MiModulo\Logger\Handler</item>
            </argument>
        </arguments>
    </virtualType>

    <!-- Inyectar este logger en tu clase en lugar del genérico -->
    <type name="MiVendor\MiModulo\Model\MiServicio">
        <arguments>
            <argument name="logger" xsi:type="object">MiVendor\MiModulo\Logger\Logger</argument>
        </arguments>
    </type>

</config>
```

Resultado: tus logs van a `var/log/mimodulo.log` sin mezclar con los del sistema.

```bash
# Monitorear solo tus logs:
tail -f var/log/mimodulo.log
```

### Log de queries SQL

```bash
# Activar logging de queries (solo en developer mode)
php bin/magento dev:query-log:enable

# Desactivar
php bin/magento dev:query-log:disable
```

El log se guarda en `var/debug/db.log`. Muy útil para detectar N+1 queries.

## Parte 3 — Técnicas de Debugging Específicas de Magento

### Template Hints — encontrar cualquier template

El problema más común para un desarrollador nuevo: **¿dónde está el template que renderiza esto?**

```bash
# Activar (solo en developer mode)
php bin/magento dev:template-hints:enable
php bin/magento cache:flush

# Abrir el frontend → verás los paths de cada template superpuestos
# Cada elemento tiene: Block class + Template path

# Desactivar
php bin/magento dev:template-hints:disable
php bin/magento cache:flush
```

También puedes activarlo solo para tu IP desde la DB:
```sql
UPDATE core_config_data
SET value = 1
WHERE path = 'dev/debug/template_hints_storefront';
```

### `dev:di:info` — ver el DI de cualquier clase

```bash
# Ver qué se inyecta en el constructor de ProductRepository
php bin/magento dev:di:info "Magento\Catalog\Model\ProductRepository"

# Output:
# DI configuration for the class Magento\Catalog\Model\ProductRepository
# Preference: Magento\Catalog\Model\ProductRepository
# Constructor Parameters:
#   productFactory    Magento\Catalog\Model\ProductFactory    object
#   collectionFactory ...

# Ver los plugins que interceptan una clase
php bin/magento dev:di:info "Magento\Checkout\Model\Cart"
# Verás: Plugins: [...]
```

### Inspeccionar el ObjectManager directamente (solo para debug)

⚠️ **NUNCA en código de producción** — solo en scripts de debug temporales.

```php
// Script temporal: pub/debug.php (borrar después)
use Magento\Framework\App\Bootstrap;
require __DIR__ . '/../app/bootstrap.php';

$bootstrap = Bootstrap::create(BP, $_SERVER);
$objectManager = $bootstrap->getObjectManager();
$objectManager->get(\Magento\Framework\App\State::class)
              ->setAreaCode('frontend');

// Ahora puedes usar cualquier clase de Magento
$productRepo = $objectManager->get(\Magento\Catalog\Api\ProductRepositoryInterface::class);
$product = $productRepo->getById(1);
var_dump($product->getName());
```

```bash
php pub/debug.php
```

### Loguear desde cualquier lugar sin inyección

Solo para debug rápido en código que no tienes refactorizado:

```php
// Hack rápido — no dejar en producción
\Magento\Framework\App\ObjectManager::getInstance()
    ->get(\Psr\Log\LoggerInterface::class)
    ->debug('Mi valor: ' . print_r($miVariable, true));
```

### Debuggear el Layout XML

```php
// En cualquier Block o ViewModel — ver los handles activos
$handles = $this->_layout->getUpdate()->getHandles();
// ['default', 'catalog_product_view', 'catalog_product_view_id_5']

// Ver todos los blocks instanciados en el layout
$allBlocks = $this->_layout->getAllBlocks();
foreach ($allBlocks as $name => $block) {
    echo $name . ': ' . get_class($block) . "\n";
}
```

### Profiler de Magento

```php
// Activar en app/etc/env.php:
'profiler' => [
    'class' => '\Magento\Framework\Profiler\Driver\Standard',
    'capture_php' => true,
    'output' => [
        'baseDir' => BP . '/var/profiler',
        'class' => '\Magento\Framework\Profiler\Driver\Standard\Output\Html'
    ]
]
```

## Parte 4 — Errores comunes y cómo resolverlos

### Error: "Class X does not exist" en generated/

```bash
# Causa: el DI container está desactualizado
# Solución:
rm -rf generated/code/ generated/metadata/
php bin/magento setup:di:compile
php bin/magento cache:flush
```

### Error: página en blanco o 500

```bash
# 1. Revisar el log de excepciones PRIMERO
tail -n 50 var/log/exception.log

# 2. Si no hay nada, revisar el log del servidor web
# En Docker:
docker logs magento_app --tail=50

# 3. Activar modo developer para ver el error en pantalla
php bin/magento deploy:mode:set developer
# Ahora el error aparece en el browser con stack trace completo
```

### Error: cambié un XML y no aplica

```bash
# Magento cachea la configuración XML agresivamente
# Solución según el tipo de XML:

# di.xml, events.xml, routes.xml (configuration XMLs):
php bin/magento setup:upgrade
php bin/magento cache:flush

# layout XML (*.xml en view/frontend/layout/):
php bin/magento cache:clean layout block_html

# routes.xml:
php bin/magento cache:flush
```

### Error: no veo mis cambios en un template .phtml

```bash
# Causa 1: caché de blocks
php bin/magento cache:clean block_html full_page

# Causa 2: en modo production, los assets son estáticos
php bin/magento setup:static-content:deploy -f

# Causa 3: opcache de PHP
docker restart magento_app
```

### Error: "Area code not set" en CLI

```php
// Causa: olvidaste setear el área al inicio de execute()
// El área es OBLIGATORIA en comandos CLI

protected function execute(InputInterface $input, OutputInterface $output): int
{
    try {
        $this->appState->setAreaCode(\Magento\Framework\App\Area::AREA_FRONTEND);
    } catch (\Magento\Framework\Exception\LocalizedException $e) {
        // Ya estaba seteada — ignorar
    }
    // ... tu código
}
```

## Parte 5 — Logs Estructurados para Flujos Complejos

Para seguir un proceso a través de múltiples clases:

```php
namespace MiVendor\MiModulo\Service;

use Psr\Log\LoggerInterface;

class ProcesadorPedidos
{
    public function __construct(private readonly LoggerInterface $logger) {}

    public function procesar(array $pedidos): array
    {
        $ctx = ['proceso' => 'procesar_pedidos', 'total' => count($pedidos)];
        $this->logger->info('Inicio de procesamiento', $ctx);

        $resultados = [];
        foreach ($pedidos as $pedido) {
            try {
                $resultado = $this->procesarUno($pedido);
                $resultados[] = $resultado;

                $this->logger->debug('Pedido procesado', [
                    'order_id'  => $pedido['id'],
                    'resultado' => $resultado
                ]);

            } catch (\Exception $e) {
                $this->logger->error('Error en pedido', [
                    'order_id' => $pedido['id'],
                    'error'    => $e->getMessage(),
                    'trace'    => $e->getTraceAsString()
                ]);
            }
        }

        $this->logger->info('Procesamiento completado', [
            ...$ctx,
            'exitosos' => count($resultados)
        ]);

        return $resultados;
    }
}
```

Log en `var/log/mimodulo.log`:
```
[2024-01-15 10:23:45] mimodulo.INFO: Inicio de procesamiento {"proceso":"procesar_pedidos","total":50}
[2024-01-15 10:23:45] mimodulo.DEBUG: Pedido procesado {"order_id":1001,"resultado":"ok"}
[2024-01-15 10:23:45] mimodulo.ERROR: Error en pedido {"order_id":1005,"error":"SKU no encontrado"}
[2024-01-15 10:23:46] mimodulo.INFO: Procesamiento completado {"proceso":"procesar_pedidos","total":50,"exitosos":49}
```

## Resumen

| Herramienta | Cuándo usarla |
|---|---|
| Xdebug | Inspeccionar estado en tiempo real, flujos de DI complejos |
| `tail exception.log` | SIEMPRE el primer paso ante cualquier error |
| Logger custom | Trazar flujos en producción, un archivo por módulo |
| Template hints | Encontrar qué template renderiza qué parte del frontend |
| `dev:di:info` | Ver implementaciones inyectadas y plugins que aplican |
| `deploy:mode developer` | Ver stack traces completos en el browser |

### Flujo de debug recomendado

```
1. ¿Hay un error visible?
   → tail -f var/log/exception.log

2. ¿Comportamiento incorrecto sin error?
   → Template hints para problemas de frontend
   → $this->logger->debug() para trazar el flujo
   → Xdebug si el flujo es muy complejo

3. ¿Problema de DI o configuración?
   → php bin/magento dev:di:info "La\Clase\Problematica"
   → rm -rf generated/ + setup:di:compile

4. ¿Cambios que no aplican?
   → cache:flush siempre
   → setup:upgrade si es configuración XML
```

### Ejercicio 1 — Logger dedicado para tu módulo

Configura un logger que escriba en `var/log/blog.log` en lugar de `system.log`. Hazlo sin crear ninguna clase PHP nueva — solo con Virtual Types en `di.xml`.

<details>
<summary>Ver solución</summary>

```xml
<!-- app/code/MiVendor/Blog/etc/di.xml -->
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="urn:magento:framework:ObjectManager/etc/config.xsd">

    <!-- Handler: define el archivo de destino -->
    <virtualType name="MiVendor\Blog\Logger\Handler"
                 type="Magento\Framework\Logger\Handler\Base">
        <arguments>
            <argument name="fileName" xsi:type="string">/var/log/blog.log</argument>
        </arguments>
    </virtualType>

    <!-- Logger: usa el handler -->
    <virtualType name="MiVendor\Blog\Logger\Logger"
                 type="Magento\Framework\Logger\Monolog">
        <arguments>
            <argument name="name" xsi:type="string">blog</argument>
            <argument name="handlers" xsi:type="array">
                <item name="system" xsi:type="object">MiVendor\Blog\Logger\Handler</item>
            </argument>
        </arguments>
    </virtualType>

    <!-- Inyectar en tu servicio -->
    <type name="MiVendor\Blog\Model\PostService">
        <arguments>
            <argument name="logger" xsi:type="object">MiVendor\Blog\Logger\Logger</argument>
        </arguments>
    </type>

</config>
```

```php
// Model/PostService.php — usa LoggerInterface normal, no sabe que es un virtual type
class PostService
{
    public function __construct(
        private readonly \Psr\Log\LoggerInterface $logger
    ) {}

    public function publish(int $id): void
    {
        $this->logger->info('Post publicado', ['id' => $id]);
        // → escribe en var/log/blog.log
    }
}
```

```bash
php bin/magento cache:flush

# Ejecutar algo que llame a PostService y verificar:
tail -f var/log/blog.log
# [2024-01-15 10:23:45] blog.INFO: Post publicado {"id":1}
```

### Ejercicio 2 — Diagnosticar y resolver un error de DI

Ves este error en `exception.log`:

```
ReflectionException: Class MiVendor\Blog\Model\PostService does not exist
  in generated/code/MiVendor/Blog/Model/PostService/Interceptor.php
```

Identifica las causas posibles y los pasos exactos para resolverlo.

<details>
<summary>Ver solución</summary>

**Causa más probable**: el código generado en `generated/` está desactualizado o corrupto — hace referencia a una clase que ya no existe en esa ruta, o el namespace cambió.

**Pasos de diagnóstico y solución**:

```bash
# 1. Verificar que el archivo PHP existe con el namespace correcto
cat app/code/MiVendor/Blog/Model/PostService.php
# Confirmar que la primera línea es: namespace MiVendor\Blog\Model;

# 2. Verificar que el autoloader de Composer conoce la clase
composer dump-autoload

# 3. Eliminar el código generado desactualizado
rm -rf generated/code/ generated/metadata/

# 4. Recompilar el DI container desde cero
php bin/magento setup:di:compile

# 5. Limpiar la caché
php bin/magento cache:flush
```

**Si el error persiste**: el problema está en el código PHP mismo — el namespace en el archivo no coincide con la ruta de directorios.

```bash
# Verificar: app/code/MiVendor/Blog/Model/PostService.php
# Namespace debe ser exactamente: namespace MiVendor\Blog\Model;
# No: namespace MiVendor\Blog\Models; (plural)
# No: namespace Mi_Vendor\Blog\Model; (guión bajo)
```

</details>
