# 1.7 — Request Lifecycle: Del HTTP Request al Response

> **Objetivo**: Entender exactamente qué sucede desde que un usuario hace una petición HTTP hasta que Magento devuelve la respuesta. Este conocimiento es fundamental para debuggear y para saber dónde interceptar el flujo.

## Por qué importa entender el lifecycle

Cuando algo falla en Magento, tienes que saber **dónde** puede estar fallando. ¿Es el router? ¿El controller? ¿Un plugin que está interceptando? ¿El layout XML? Sin este mapa mental, debuggear es disparar a ciegas.

🔄 **Laravel**: En Laravel el lifecycle es: `public/index.php → bootstrap → Kernel → Middleware → Router → Controller → Response`. En Magento es más complejo pero sigue la misma lógica.

---

## El lifecycle completo

```
┌─────────────────────────────────────────────────────────────────┐
│  1. NGINX / Apache                                               │
│     Recibe HTTP request, redirige a pub/index.php                │
└───────────────────────────────┬─────────────────────────────────┘
                                 │
┌───────────────────────────────▼─────────────────────────────────┐
│  2. pub/index.php                                                │
│     Entry point. Crea el Bootstrap.                              │
└───────────────────────────────┬─────────────────────────────────┘
                                 │
┌───────────────────────────────▼─────────────────────────────────┐
│  3. Bootstrap::run()                                             │
│     - Carga el autoloader de Composer                            │
│     - Inicializa el ObjectManager (DI container)                 │
│     - Carga etc/di.xml de todos los módulos (global)             │
│     - Detecta el Area                                            │
│     - Carga etc/{area}/di.xml de todos los módulos               │
└───────────────────────────────┬─────────────────────────────────┘
                                 │
┌───────────────────────────────▼─────────────────────────────────┐
│  4. App::launch()                                                │
│     - Crea el Request object (URL, params, headers, body)        │
│     - Dispara evento: controller_front_send_response_before      │
└───────────────────────────────┬─────────────────────────────────┘
                                 │
┌───────────────────────────────▼─────────────────────────────────┐
│  5. FrontController::dispatch()                                  │
│     - Itera la lista de Routers (en orden de sortOrder)          │
│     - Cada router intenta hacer match con la URL                 │
│     - El primero que hace match gana                             │
└───────────────────────────────┬─────────────────────────────────┘
                                 │
┌───────────────────────────────▼─────────────────────────────────┐
│  6. Router::match()  (el que ganó)                               │
│     Standard Router: parsea module/controller/action de la URL   │
│     → Instancia la Action class correspondiente                  │
└───────────────────────────────┬─────────────────────────────────┘
                                 │
┌───────────────────────────────▼─────────────────────────────────┐
│  7. Action::execute()  (tu Controller)                           │
│     - Aquí corre tu código                                       │
│     - Llama a Services/Repositories                              │
│     - Retorna un ResultInterface                                 │
└───────────────────────────────┬─────────────────────────────────┘
                                 │
┌───────────────────────────────▼─────────────────────────────────┐
│  8. Result rendering                                             │
│     Según el tipo de resultado:                                  │
│     - Page: procesa Layout XML → Blocks → Templates              │
│     - Json: serializa el array a JSON                            │
│     - Redirect: setea header 302                                 │
│     - Raw: devuelve string directo                               │
└───────────────────────────────┬─────────────────────────────────┘
                                 │
┌───────────────────────────────▼─────────────────────────────────┐
│  9. Response                                                     │
│     - Setea headers HTTP                                         │
│     - Escribe el body                                            │
│     - Dispara evento: controller_front_send_response_after       │
│     - Envía al cliente                                           │
└─────────────────────────────────────────────────────────────────┘
```

## Paso a paso con código real

### 1. pub/index.php — El entry point

```php
// pub/index.php (simplificado)
use Magento\Framework\App\Bootstrap;

require __DIR__ . '/../app/bootstrap.php';

$bootstrap = Bootstrap::create(BP, $_SERVER);
$app = $bootstrap->createApplication(\Magento\Framework\App\Http::class);
$bootstrap->run($app);
```

🔄 **Laravel**: Equivalente a `public/index.php` en Laravel. Misma idea, diferente implementación.

---

### 2. Bootstrap — Arrancar el DI Container

El Bootstrap es el momento más costoso del proceso. Aquí Magento:

```
a) Carga el autoloader de Composer
b) Lee generated/metadata/ (el cache del DI container compilado)
c) Lee app/etc/config.php (lista de módulos habilitados)
d) Carga etc/di.xml de cada módulo (global)
e) Detecta el área (frontend, adminhtml, etc.)
f) Carga etc/{area}/di.xml de cada módulo
g) Instancia el ObjectManager configurado
```

En modo `production` el paso `b` es lo más importante — el container ya está compilado y esto es muy rápido.

En modo `developer` los pasos `d` y `f` leen los XML en cada request — más lento pero sin compilar.

---

### 3. Los Routers — Cómo Magento encuentra tu Controller

Hay varios routers y se prueban en orden:

```
sortOrder 10  →  Robots Router        (solo /robots.txt)
sortOrder 15  →  Admin Router         (URLs que empiezan por /admin/)
sortOrder 20  →  URL Rewrite Router   (URLs reescritas en la DB)
sortOrder 30  →  Standard Router      (module/controller/action)
sortOrder 60  →  CMS Router           (páginas CMS por URL key)
sortOrder 100 →  Default Router       (página 404)
```

#### El Standard Router — el más importante

Parsea la URL con este patrón:

```
/{frontName}/{controller}/{action}
    ↓             ↓           ↓
  blog          post         view

Magento busca:
app/code/[módulo con frontName "blog"]/Controller/Post/View.php
```

¿Cómo sabe qué módulo tiene `frontName="blog"`? Lo busca en los `routes.xml`:

```xml
<!-- app/code/MiVendor/Blog/etc/frontend/routes.xml -->
<config>
    <router id="standard">
        <route id="blog" frontName="blog">
            <module name="MiVendor_Blog"/>
        </route>
    </router>
</config>
```

#### El URL Rewrite Router

Antes del Standard Router, Magento revisa si la URL tiene un rewrite en la base de datos (tabla `url_rewrite`). Por eso `/mi-producto-bonito.html` puede mapear internamente a `/catalog/product/view/id/123`.

### 4. La Action — Tu Controller

```php
// app/code/MiVendor/Blog/Controller/Post/View.php
namespace MiVendor\Blog\Controller\Post;

use Magento\Framework\App\Action\HttpGetActionInterface;
use Magento\Framework\View\Result\PageFactory;
use Magento\Framework\App\RequestInterface;

class View implements HttpGetActionInterface
{
    public function __construct(
        private readonly PageFactory     $resultPageFactory,
        private readonly RequestInterface $request
    ) {}

    public function execute(): \Magento\Framework\Controller\ResultInterface
    {
        // Aquí corre tu código
        return $this->resultPageFactory->create();
    }
}
```

💡 **TIP**: En Magento 2.3+ usa las interfaces de verbo HTTP:
- `HttpGetActionInterface` — solo acepta GET
- `HttpPostActionInterface` — solo acepta POST
- `HttpPutActionInterface` — solo acepta PUT

Si la acción recibe un verbo diferente al declarado, Magento devuelve 404 automáticamente. Es más seguro y explícito que no declarar nada.

---

### 5. Los tipos de Result — Cómo Magento responde

El Controller devuelve un `ResultInterface`. Magento tiene varios tipos:

```php
use Magento\Framework\Controller\ResultFactory;

// En tu Controller (ResultFactory inyectado por DI):

// HTML completo con Layout XML, Blocks y Templates
$result = $this->resultPageFactory->create();                    // Page
$result->getConfig()->getTitle()->set('Mi título');

// JSON — para respuestas AJAX
$result = $this->resultFactory->create(ResultFactory::TYPE_JSON);
$result->setData(['success' => true, 'message' => 'Guardado']);

// Redirect — redirigir a otra URL
$result = $this->resultRedirectFactory->create();
$result->setPath('blog/post/index');

// Raw — string directo sin procesamiento
$result = $this->resultFactory->create(ResultFactory::TYPE_RAW);
$result->setContents('texto plano');

// Forward — delegar a otra Action (sin redirect HTTP)
$result = $this->resultFactory->create(ResultFactory::TYPE_FORWARD);
$result->forward('noroute');  // delega a la página 404
```

### 6. El Page Result y el Layout XML

Cuando el resultado es una `Page`, empieza el proceso más complejo:

```
ResultPage::renderResult()
    │
    ▼
Layout::generateXml()
    Fusiona TODOS los layout XMLs que aplican al handle actual:
    - default.xml                    (todas las páginas)
    - blog_post_view.xml             (solo esta página)
    - catalog_category_view.xml      (si es una categoría)
    - etc.
    │
    ▼
Layout::generateElements()
    Instancia los Blocks declarados en el XML
    Inyecta los ViewModels en los Blocks
    │
    ▼
Layout::render()
    Cada Block llama a su template .phtml
    Los templates se renderizan de afuera hacia adentro
    │
    ▼
HTML final
```

#### Handles de Layout

Un **handle** es un identificador que activa ciertos XMLs de layout. Magento carga el handle `default` siempre, y agrega handles específicos según el contexto:

```
Todas las páginas:        default
Categoría:                catalog_category_view
Producto:                 catalog_product_view
Producto ID 5:            catalog_product_view_id_5   ← solo para ese producto
Checkout:                 checkout_index_index
CMS Home:                 cms_index_index
Tu página custom:         blog_post_view              ← automático por ruta
```

## Dónde puedes interceptar el lifecycle

Este es el mapa de puntos de intervención:

```
1. Bootstrap         → Plugin en ObjectManager (raramente necesario)

2. FrontController   → Plugin en dispatch()
                     → Observer: controller_front_send_response_before

3. Router            → Crear un Router propio (módulo 7.7)

4. Action            → Plugin en execute() ← lo más común
                     → Observer: controller_action_predispatch
                     → Observer: controller_action_postdispatch

5. Layout            → Layout XML (módulo 9)
                     → Plugin en generateElements()

6. Block             → Plugin en toHtml() o en métodos específicos
                     → Observer: core_block_abstract_to_html_before/after

7. Response          → Observer: controller_front_send_response_after
```

### Ejemplo: interceptar ANTES de cualquier action del módulo Blog

```xml
<!-- etc/frontend/events.xml -->
<event name="controller_action_predispatch_blog">
    <!-- Se dispara antes de cualquier action del módulo Blog -->
    <observer name="blog_check_access"
              instance="MiVendor\Blog\Observer\CheckBlogAccess"/>
</event>

<event name="controller_action_predispatch_blog_post_view">
    <!-- Se dispara solo antes de Blog\Controller\Post\View::execute() -->
    <observer name="blog_track_view"
              instance="MiVendor\Blog\Observer\TrackPostView"/>
</event>
```

El nombre del evento sigue el patrón:
```
controller_action_predispatch_{frontName}_{controller}_{action}
```

---

## Eventos del lifecycle que más usarás

```
controller_action_predispatch
    → Antes de execute() en cualquier controller

controller_action_predispatch_{frontName}
    → Antes de execute() en cualquier controller del módulo

controller_action_predispatch_{frontName}_{controller}_{action}
    → Antes de execute() en una action específica

controller_action_postdispatch
    → Después de execute() en cualquier controller

controller_front_send_response_before
    → Justo antes de enviar la respuesta al cliente
    → Útil para modificar headers, comprimir output, etc.

controller_front_send_response_after
    → Después de enviar la respuesta
    → Útil para logging, analytics, cleanup
```

## Debuggear el lifecycle

### Ver qué router está manejando tu URL

```php
// En un Observer de controller_action_predispatch:
public function execute(\Magento\Framework\Event\Observer $observer)
{
    $request = $observer->getEvent()->getRequest();
    \Magento\Framework\App\ObjectManager::getInstance()
        ->get(\Psr\Log\LoggerInterface::class)
        ->debug('Route: ' . $request->getModuleName()
            . '/' . $request->getControllerName()
            . '/' . $request->getActionName());
}
```

### Ver los handles de layout activos

```php
// En cualquier Block o ViewModel:
$handles = $this->_layout->getUpdate()->getHandles();
// ['default', 'blog_post_view', ...]
```

### Trazar el flujo con Xdebug

Pon un breakpoint en estos archivos para trazar el flujo completo:

```
vendor/magento/framework/App/FrontController.php  → dispatch()
vendor/magento/framework/App/Router/Base.php      → match()
vendor/magento/framework/App/Action/Action.php    → dispatch()  (antes de execute)
```

## Lifecycle de una petición a la API REST

Para la API es más simple porque no hay Layout XML:

```
/rest/V1/products/5
    │
    ▼
pub/index.php
    │ área: webapi_rest
    ▼
Magento\Webapi\Controller\Rest::dispatch()
    │
    ▼
Router REST (lee webapi.xml)
    → Encuentra: GET /V1/products/:id
    → Mapea a: Magento\Catalog\Api\ProductRepositoryInterface::getById()
    │
    ▼
Service method ejecutado directamente (sin Action class)
    │
    ▼
Resultado serializado a JSON automáticamente
    │
    ▼
Response JSON al cliente
```

💡 **TIP clave**: En la API REST, Magento llama **directamente al Service Contract** (la interface del `Api/`), sin pasar por un Controller. Por eso es tan importante que tus Service Contracts estén bien definidos — son el punto de entrada de la API.

---

## Resumen del lifecycle

```
request HTTP
    → pub/index.php
        → Bootstrap (DI container, Areas)
            → FrontController
                → Routers (en orden de sortOrder)
                    → Action::execute() ← TU CÓDIGO
                        → ResultInterface
                            → si es Page: Layout XML → Blocks → .phtml
                            → si es JSON: serializar
                            → si es Redirect: header 302
                → Response HTTP al cliente
```

### Puntos de intervención más usados

| Dónde interceptar | Cómo |
|---|---|
| Antes de tu action | `controller_action_predispatch_{route}` observer |
| Durante la ejecución | Plugin en `execute()` |
| Modificar el HTML renderizado | Plugin en `Block::toHtml()` |
| Antes de enviar la respuesta | `controller_front_send_response_before` observer |
| Cambiar el routing | Router personalizado |
