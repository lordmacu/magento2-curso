## El problema que resuelve la arquitectura de Magento

En Laravel, una sola app sirve tanto el frontend como el panel de admin, las APIs y los jobs. Todo comparte el mismo contexto.

En Magento esto no funciona así porque:

- El **storefront** necesita caché agresivo, layouts de catálogo, precios por cliente
- El **admin** necesita autenticación diferente, sin caché, con ACL granular
- La **API REST/GraphQL** no necesita layouts ni templates HTML, solo datos
- El **cron** corre sin contexto HTTP — no hay request ni sesión

Magento resuelve esto con **dos conceptos fundamentales**: **Areas** y **Layers**.

```
Sin arquitectura por áreas:
┌─────────────────────────────────────────────┐
│  Todo mezclado: admin + frontend + api + cli │  ← caos imposible de mantener
└─────────────────────────────────────────────┘

Con Areas + Layers:
┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
│ frontend │ │adminhtml │ │ webapi   │ │  crontab │   ← Areas (contextos)
└────┬─────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘
     │             │             │             │
┌────▼─────────────▼─────────────▼─────────────▼────┐
│              Presentation Layer                     │
├────────────────────────────────────────────────────┤
│               Service Layer                         │
├────────────────────────────────────────────────────┤
│               Domain Layer                          │
├────────────────────────────────────────────────────┤
│              Persistence Layer                      │
└────────────────────────────────────────────────────┘
```

## Parte 1: Magento Areas

Un **Area** es un contexto de ejecución. Le dice a Magento qué configuración DI, qué layouts, qué plugins y qué configuración cargar.

### Las 6 Areas de Magento

```
magento/framework/App/Area.php

const AREA_GLOBAL      = 'global';       // Bootstrap, antes de que exista área
const AREA_FRONTEND    = 'frontend';     // La tienda pública
const AREA_ADMINHTML   = 'adminhtml';    // El panel de administración
const AREA_CRONTAB     = 'crontab';      // Tareas programadas
const AREA_WEBAPI_REST = 'webapi_rest';  // API REST
const AREA_WEBAPI_SOAP = 'webapi_soap';  // API SOAP (legacy)
const AREA_GRAPHQL     = 'graphql';      // API GraphQL
```

### ¿Por qué importa el Area?

Porque **el di.xml se carga por área**. Puedes tener un plugin que solo aplica en `frontend` y otro diferente para `adminhtml`.

```xml
<!-- etc/frontend/di.xml — Solo aplica cuando el área es "frontend" -->
<config>
    <preference for="Magento\Catalog\Block\Product\View"
                type="MiVendor\MiModulo\Block\Product\View"/>
</config>

<!-- etc/adminhtml/di.xml — Solo aplica en el admin -->
<config>
    <preference for="Magento\Catalog\Block\Product\View"
                type="MiVendor\MiModulo\Block\Admin\Product\View"/>
</config>
```

🔄 **Laravel**: No existe este concepto. Una sola clase se usa en todos los contextos y las diferencias las manejas con middlewares o condiciones dentro del código.

💡 **TIP**: El área `global` se carga **siempre**, sin importar el contexto activo. Úsala en `etc/di.xml` (sin subdirectorio) cuando tu configuración aplica a todos los contextos.

### Estructura de directorios por área

```
app/code/MiVendor/MiModulo/etc/
├── di.xml              ← global (aplica a todos los contextos)
├── module.xml          ← global
├── frontend/
│   ├── di.xml          ← solo storefront
│   ├── routes.xml      ← rutas del storefront
│   └── events.xml      ← observers solo en frontend
├── adminhtml/
│   ├── di.xml          ← solo admin
│   ├── routes.xml      ← rutas del admin
│   └── menu.xml        ← menú del admin
├── webapi_rest/
│   └── di.xml          ← solo API REST
├── graphql/
│   └── di.xml          ← solo GraphQL
└── crontab/
    └── di.xml          ← solo cron
```

### Cómo Magento detecta el área activa

```
Request entra
    │
    ▼
pub/index.php
    │
    ├── /rest/*         → Area: webapi_rest
    ├── /soap/*         → Area: webapi_soap
    ├── /graphql        → Area: graphql
    ├── /admin/*        → Area: adminhtml
    └── cualquier otra  → Area: frontend

Proceso de CLI (bin/magento):
    └── Se setea manualmente o queda en "global"
```

Puedes leer el área activa en tu código:

```php
use Magento\Framework\App\State;

class MiClase
{
    public function __construct(private readonly State $appState) {}

    public function ejecutar(): void
    {
        $area = $this->appState->getAreaCode();
        // 'frontend', 'adminhtml', 'webapi_rest', 'graphql', 'crontab'
    }
}
```

## Parte 2: Magento Layers (Las 4 Capas)

Magento divide el código en 4 capas. Cada capa tiene una responsabilidad específica y **solo puede comunicarse hacia abajo** — la capa superior llama a la inferior, nunca al revés.

```
┌─────────────────────────────────────────────────────────┐
│                  PRESENTATION LAYER                      │
│  Controllers, Blocks, ViewModels, Templates (.phtml)     │
│  Layout XML, UI Components, GraphQL Resolvers            │
│         — Lo que el usuario ve e interactúa —            │
└────────────────────┬────────────────────────────────────┘
                     │ llama a ↓
┌────────────────────▼────────────────────────────────────┐
│                   SERVICE LAYER                          │
│  Service Contracts (Interfaces en Api/), Repositories    │
│  Managers de negocio                                     │
│          — La API pública de tu módulo —                 │
└────────────────────┬────────────────────────────────────┘
                     │ llama a ↓
┌────────────────────▼────────────────────────────────────┐
│                   DOMAIN LAYER                           │
│  Models, Validators, Lógica de negocio pura              │
│       — Las reglas del negocio sin dependencias —        │
└────────────────────┬────────────────────────────────────┘
                     │ llama a ↓
┌────────────────────▼────────────────────────────────────┐
│                 PERSISTENCE LAYER                        │
│  ResourceModels, Collections, Setup, db_schema.xml       │
│      — Todo lo que toca base de datos o filesystem —     │
└─────────────────────────────────────────────────────────┘
```

---

### Layer 1: Presentation Layer

Todo lo que el usuario ve o con lo que interactúa directamente.

```
app/code/Vendor/Module/
├── Controller/           ← una clase por acción HTTP
│   ├── Index.php
│   ├── Post/View.php
│   └── Post/Save.php
├── Block/                ← preparan datos para templates
│   └── Post/View.php
├── ViewModel/            ← forma moderna de pasar datos (sin lógica en Block)
│   └── PostData.php
└── view/
    ├── frontend/
    │   ├── layout/       ← define estructura de la página en XML
    │   │   └── blog_post_view.xml
    │   └── templates/    ← archivos .phtml
    │       └── post/view.phtml
    └── adminhtml/
        └── ui_component/ ← grids y forms del admin en XML
            └── blog_post_listing.xml
```

🔄 **Laravel**: Es `Controllers` + `Views (Blade)` + `View Composers`. Pero en Magento son clases con responsabilidades más separadas — el Block/ViewModel reemplaza al View Composer de manera más estructurada.

### Layer 2: Service Layer

La **API pública** de tu módulo. Es lo que otros módulos pueden usar de manera segura. Si cambias la implementación interna pero mantienes la interfaz, nada externo se rompe.

```
app/code/Vendor/Module/
└── Api/
    ├── PostRepositoryInterface.php    ← contrato del repositorio
    └── Data/
        └── PostInterface.php          ← contrato de la entidad (DTO)
```

```php
// Api/PostRepositoryInterface.php
namespace MiVendor\Blog\Api;

use MiVendor\Blog\Api\Data\PostInterface;

interface PostRepositoryInterface
{
    public function getById(int $id): PostInterface;
    public function save(PostInterface $post): PostInterface;
    public function deleteById(int $id): bool;
}

// Api/Data/PostInterface.php — Data Transfer Object
namespace MiVendor\Blog\Api\Data;

interface PostInterface
{
    public function getId(): ?int;
    public function getTitle(): string;
    public function setTitle(string $title): self;
    public function getContent(): string;
    public function setContent(string $content): self;
}
```

💡 **TIP**: Los archivos en `Api/` son **promesas públicas**. Una vez que las publicas, otros módulos dependen de ellas. Cámbialas con cuidado. Los archivos en `Model/` son detalles internos — puedes cambiarlos libremente.

🔄 **Laravel**: Similar a Repositories e Interfaces de Service classes, pero en Magento es parte de la convención del framework, no algo opcional.

### Layer 3: Domain Layer

Los modelos de negocio y sus reglas. Aquí va la lógica de negocio **pura**, sin dependencias de HTTP, DB ni presentación.

```php
// Model/Post.php — El Model (lógica de negocio)
namespace MiVendor\Blog\Model;

use Magento\Framework\Model\AbstractModel;
use MiVendor\Blog\Api\Data\PostInterface;

class Post extends AbstractModel implements PostInterface
{
    // Constantes del dominio
    const STATUS_PUBLISHED = 'published';
    const STATUS_DRAFT = 'draft';

    protected function _construct(): void
    {
        // Conecta este Model con su ResourceModel
        $this->_init(\MiVendor\Blog\Model\ResourceModel\Post::class);
    }

    // Implementa PostInterface
    public function getId(): ?int { return $this->getData('post_id'); }
    public function getTitle(): string { return (string)$this->getData('title'); }
    public function setTitle(string $title): self { return $this->setData('title', $title); }
    public function getContent(): string { return (string)$this->getData('content'); }
    public function setContent(string $content): self { return $this->setData('content', $content); }

    // Lógica de negocio pura — no toca DB, no toca HTTP
    public function isPublished(): bool
    {
        return $this->getData('status') === self::STATUS_PUBLISHED;
    }

    public function getExcerpt(int $length = 150): string
    {
        return substr(strip_tags($this->getContent()), 0, $length) . '...';
    }
}
```

⚠️ **Diferencia crítica con Eloquent**:

```php
// Laravel/Eloquent — Model hace TODO
$post = Post::where('status', 'published')->first();  // DB query directo en el Model

// Magento — Model solo tiene lógica, el Repository hace queries
$post = $this->postRepository->getById(5);  // el Repository llama al ResourceModel
$post->isPublished();                        // lógica pura en el Model
```

### Layer 4: Persistence Layer

Todo lo que toca la base de datos.

```php
// Model/ResourceModel/Post.php — Mapea el Model a una tabla
namespace MiVendor\Blog\Model\ResourceModel;

use Magento\Framework\Model\ResourceModel\Db\AbstractDb;

class Post extends AbstractDb
{
    protected function _construct(): void
    {
        $this->_init('mivendor_blog_post', 'post_id');
        //           ↑ nombre de tabla     ↑ primary key
    }
}

// Model/ResourceModel/Post/Collection.php — Queries de múltiples registros
namespace MiVendor\Blog\Model\ResourceModel\Post;

use Magento\Framework\Model\ResourceModel\Db\Collection\AbstractCollection;

class Collection extends AbstractCollection
{
    protected function _construct(): void
    {
        $this->_init(
            \MiVendor\Blog\Model\Post::class,
            \MiVendor\Blog\Model\ResourceModel\Post::class
        );
    }

    // Métodos de query reutilizables (como Scopes en Eloquent)
    public function addPublishedFilter(): self
    {
        return $this->addFieldToFilter('status', 'published');
    }

    public function addAuthorFilter(int $authorId): self
    {
        return $this->addFieldToFilter('author_id', $authorId);
    }
}
```

🔄 **Laravel** (Eloquent scope vs Magento Collection):

```php
// Laravel
Post::published()->byAuthor(5)->get();

// Magento
$collection = $this->collectionFactory->create();
$collection->addPublishedFilter()->addAuthorFilter(5)->load();
```

## Parte 3: La Regla de Comunicación entre Capas

```
✅ Correcto:
Controller (Presentation)
    → llama a → PostRepositoryInterface (Service)
        → llama a → ResourceModel (Persistence)

✅ Correcto:
Block (Presentation)
    → llama a → PostRepositoryInterface (Service)
        → retorna → PostInterface (Domain)

❌ Incorrecto — nunca hagas esto:
ResourceModel (Persistence) → llama a → Controller (Presentation)
Model (Domain) → llama a → Block (Presentation)
Model (Domain) → hace query directa a DB sin pasar por ResourceModel
```

💡 **TIP**: Si tu Model tiene un `__construct` con muchas dependencias de servicios externos, probablemente estás poniendo lógica de Service Layer dentro del Domain Layer. Mueve esa lógica a un Repository o Service.

## Parte 4: Comparación visual con Laravel

```
LARAVEL MVC                    MAGENTO LAYERS
─────────────────              ──────────────────────────────────
                               ┌──────────────────────────────┐
Controller                     │ Controller                    │ PRESENTATION
View (Blade)                   │ Block + ViewModel + .phtml    │
                               │ UI Components                 │
                               ├──────────────────────────────┤
Service class (opcional)       │ Api/Interface + Repository    │ SERVICE
                               ├──────────────────────────────┤
Model (Eloquent)               │ Model (solo lógica)           │ DOMAIN
  ├── lógica de negocio        ├──────────────────────────────┤
  ├── queries de DB            │ ResourceModel + Collection    │ PERSISTENCE
  └── relaciones               │ db_schema.xml                 │
─────────────────              └──────────────────────────────┘

Laravel: 1 Model hace todo.
Magento: 3 capas con responsabilidades separadas.

Más verboso → más mantenible en proyectos de 100K líneas.
```

## Parte 5: Flujo completo de una petición HTTP

```
1. Cliente hace GET /blog/post/view/id/5
        │
2. pub/index.php
   ├── detecta área: frontend
   └── inicializa el DI container

3. App\FrontController::dispatch()
   └── itera los Routers registrados:
       ├── CMS Router (¿es una CMS page?) → No
       ├── URL Rewrite Router (¿hay rewrite?) → No
       └── Standard Router → Sí
           └── encuentra: module=Blog, controller=Post, action=View

4. MiVendor\Blog\Controller\Post\View::execute()  ← PRESENTATION
   └── $this->postRepository->getById(5)

5. MiVendor\Blog\Model\PostRepository::getById()  ← SERVICE
   └── $this->resourceModel->load($post, 5)

6. MiVendor\Blog\Model\ResourceModel\Post::load()  ← PERSISTENCE
   └── SELECT * FROM mivendor_blog_post WHERE post_id = 5
   └── retorna datos al Model

7. Model\Post  ← DOMAIN
   └── datos disponibles: getTitle(), getContent(), isPublished()...

8. Controller retorna PageResult  ← PRESENTATION
   └── Layout XML: blog_post_view.xml
   └── Block\Post\View prepara datos
   └── ViewModel\PostData formatea datos
   └── templates/post/view.phtml renderiza HTML

9. Response HTTP al cliente
```

## Resumen

| Concepto | Definición | Ejemplo |
|---|---|---|
| **Area** | Contexto de ejecución que define qué DI/layouts cargar | `frontend`, `adminhtml`, `graphql` |
| **Presentation** | Lo que el usuario ve | Controller, Block, Template |
| **Service** | API pública del módulo | `Api/PostRepositoryInterface.php` |
| **Domain** | Reglas de negocio puras | `Model/Post.php` → `isPublished()` |
| **Persistence** | Acceso a datos | `ResourceModel/Post.php`, `Collection` |

### Las 3 reglas de oro

1. **Nunca toques el core** — todo se extiende con módulos
2. **Programa contra interfaces** — `Api/*Interface.php`, no la implementación
3. **Respeta las capas** — cada una tiene su responsabilidad, no las mezcles
